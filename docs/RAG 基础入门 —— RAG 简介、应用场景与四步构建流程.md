# RAG 基础入门 —— RAG 简介、应用场景与四步构建流程

> 面试生普（LLM 500 题）· RAG 基础入门篇。本章覆盖 RAG 是什么、为什么需要 RAG、RAG 与微调的区别、RAG 工作流程（索引阶段与查询阶段）、RAG 的典型应用场景、以及用 Python 手撕一个最小可运行的 RAG 系统，共 30 个问题。正文面向“会一点编程语言和深度学习基础，除此之外没有任何其他背景”的读者，每个部分都配大白话解释、完整 Python 代码和 ASCII 图。

## Q1. RAG 的全称是什么？它解决什么问题？

**回答**

RAG 的全称是 **Retrieval-Augmented Generation**，中文叫**检索增强生成**。

用大白话说，RAG 就是给大模型装了一个“随身携带的图书馆+搜索引擎”。大模型平时只能凭记忆回答（那是“闭卷考试”），而 RAG 让大模型在回答之前，先到外部知识库里查找相关资料，再基于查到的资料生成答案（那是“开卷考试”）。

它主要解决三个痛点：

1. **知识过时**：大模型的训练数据有截止时间，比如只训练到 2024 年，那 2026 年发生的新事物它一无所知。RAG 可以随时把最新文档放进知识库，模型就能回答最新问题，不用重新训练。
2. **幻觉（胡说八道）**：大模型是概率预测机，有时候为了让句子通顺，会编造看似合理但不存在的事实。RAG 强迫模型“先查资料再回答”，答案有出处可查，大大减少编造。
3. **私有知识盲区**：大模型不知道你公司的内部手册、产品文档、昨天的会议纪要。RAG 可以把这些私有文档放进知识库，让模型回答与你业务相关的问题。

> 面试要点：RAG = 检索（先从外部知识库找相关资料）+ 生成（大模型基于资料写答案），解决知识过时、幻觉、私有知识盲区三大痛点。

## Q2. 大模型不能直接把整本文档“喂”进去吗？为什么还需要 RAG？

**回答**

这是很多初学者的第一反应：“大模型上下文窗口这么大（几十万甚至上百万 Token），我直接把几百页的产品手册连同问题一起发给它，让它直接看不就行了？”

理论上可以，但工程上有三个致命问题，大白话如下：

### 1. “鱼的记忆”——上下文窗口有限，信息太多反而丢重点

即使模型支持 100 万 Token 的上下文，当你塞进几十万字时，模型容易出现“迷失在中间（Lost in the Middle）”现象：文档开头和结尾记得比较清楚，中间的关键细节却容易被忽略。一句话在海量文本里，就像大海捞针。

### 2. “烧钱机器”——按 Token 付费，成本高昂

大多数大模型 API 是按输入 Token 数计费的。如果每次提问都带上几十万字的文档，一次对话的成本就可能是几毛钱甚至几块钱，用户量大了以后根本扛不住。

RAG 的做法相反：每次只检索出最相关的几个片段（比如 3-5 个，几百字到一两千字），只把这些精炼的“参考资料”送给模型，Token 用量极低。

### 3. “龟速响应”——输入太长，模型思考和生成都变慢

输入的文本越长，模型处理的时间越长，用户等待的时间越久，体验极差。

### 对比图

```
直接塞整本文档          RAG（检索增强）
┌─────────────┐         ┌─────────────────────┐
│ 用户问题    │         │ 用户问题              │
│ + 整本手册  │────────▶│ 检索相关片段（Top-K） │
│ （几十万字）│         │ （几百字～一两千字）  │
└─────────────┘         └─────────────────────┘
         │                        │
         ▼                        ▼
    成本高、慢、易丢重点      成本低、快、精准
    答案不可靠                答案有出处可查
```

> 面试要点：不能直接塞整本文档，因为上下文窗口有限（丢重点）、按 Token 计费（贵）、响应慢。RAG 每次只喂最相关的几个片段，又快又省又准。

## Q3. RAG 和微调（Fine-tuning）的区别是什么？应该选哪个？

**回答**

这是面试经典问题。两者都是让大模型“懂”更多知识，但思路完全不同：

| 维度 | RAG（检索增强生成） | 微调（Fine-tuning） |
|------|-------------------|-------------------|
| 做什么 | 给模型装“外挂图书馆”，回答前先查资料 | 把新知识“刻进”模型权重里 |
| 知识来源 | 外部知识库（文档、数据库） | 训练数据集（问答对） |
| 更新知识 | 新增文档，重新建立索引即可，秒级生效 | 重新收集数据、重新训练，耗时耗力 |
| 成本 | 主要是推理成本，较低 | 需要 GPU 训练资源，成本高 |
| 可解释性 | 答案可追溯到具体文档片段 | 黑箱，不知道模型凭什么这么回答 |
| 隐私 | 文档留在自己知识库，模型不见原始数据 | 训练数据可能泄露模型记忆 |

用大白话比喻：

- **RAG** 像“开卷考试”：考生不需要背诵所有教材，考试时允许带参考书，查到相关章节再答题。新教材出来，直接换书就行。
- **微调** 像“闭卷考试＋强制背诵”：把教材内容强行塞进考生大脑，考试时不准带书。新教材出来，得让考生重新背一遍。

**怎么选？**

- 如果你的知识**经常变化**（比如公司政策每周调整），选 **RAG**，因为更新只要丢新文档进知识库。
- 如果你希望模型掌握某种**固定的风格或技能**（比如永远用幽默口吻回答，或固定输出 JSON 格式），选 **微调**。
- 实战中最常见的做法是：**RAG 为主，微调为辅**——日常问答靠 RAG 检索公司文档，微调只用来把模型的回答语气、格式调得更顺手。

> 面试要点：RAG 是“开卷考试”，查外部知识库，更新快、便宜、可追溯；微调是“闭卷考试”，改模型权重，更新慢、贵、黑箱。知识经常变化选 RAG，固定风格/格式选微调，两者可混合使用。

## Q4. RAG 的整体工作流程是怎样的？

**回答**

一个完整的 RAG 系统可以分成两个阶段，就像图书馆的工作分成“平时整理书架”和“读者借书”两部分：

### 阶段一：索引阶段（离线，只做一次或定期做）

把杂乱的文档变成机器能快速查询的“索引”，相当于图书馆为每本书建立索引卡。

1. **加载文档**：读取 PDF、Word、TXT、Markdown、网页等各种格式的文件，把它们变成纯文本。
2. **文本分块（Chunking）**：长文档太厚，切成一个个小片段（Chunk），每个片段几百到一千字左右。
3. **向量化（Embedding）**：用 Embedding 模型把每个文本片段转成一串数字（向量），比如 `[0.23, -0.45, 0.87, ...]`。这串向量就是文本的“数学指纹”，语义相近的文本，向量也相近。
4. **存入向量数据库**：把向量和对应的原始文本一起存进向量数据库，建立索引，方便以后高速检索。

### 阶段二：查询阶段（在线，每次用户提问都做）

用户提问后，系统实时回答，相当于读者去图书馆找书。

1. **问题向量化**：用同样的 Embedding 模型，把用户的问题也转成向量。
2. **相似性检索**：在向量数据库里，找出与问题向量最接近的 Top-K 个文本片段。
3. **Prompt 增强**：把用户的问题和检索到的相关片段一起，拼进一个提示词（Prompt）模板里。
4. **生成回答**：把增强后的 Prompt 送给大模型，让模型基于这些“参考资料”回答问题。

### 两阶段对比图

```
阶段一：索引（离线，建图书馆）          阶段二：查询（在线，读者借书）
┌─────────────┐                      ┌─────────────┐
│ 文档加载    │                      │ 用户提问    │
│ 文本分块    │                      │ 问题向量化  │
│ 向量化      │──────▶ 向量数据库 ◀───│ 相似性检索  │
│ 入库建索引  │  (离线，做一次)      │ Top-K 片段  │
└─────────────┘                      │ Prompt 增强 │
                                     │ LLM 生成    │
                                     └─────────────┘
                                              │
                                              ▼
                                        回答用户
```

> 面试要点：RAG 分两阶段。索引阶段离线做：加载→分块→向量化→入库；查询阶段在线做：问题向量化→相似性检索→Prompt 增强→LLM 生成。两者共用同一个 Embedding 模型，保证“问题”和“文档”在同一个向量空间里能比较。

## Q5. RAG 中的“检索”具体做什么？

**回答**

检索是 RAG 的“眼睛”，负责从海量文档片段里，快速找出和用户问题最相关的那几段。

具体怎么做？

1. 用户提问：“公司报销流程是什么？”
2. 系统用 Embedding 模型把这个问题转成一个向量（一串数字）。
3. 在向量数据库里，计算这个“问题向量”与库里所有“文档片段向量”的距离（通常用余弦相似度）。距离越近，语义越相关。
4. 取距离最近的前 K 个片段（比如 K=3 或 K=5），作为检索结果。

举个例子：

- 知识库里有片段 A：“报销单需先经部门经理审批，再交财务。”
- 片段 B：“办公室空调温度设定为 26 度。”
- 用户问：“报销怎么走流程？”

系统算相似度，发现片段 A 与问题最接近，片段 B 无关，于是只返回片段 A 给大模型。大模型就不会被无关的空调温度干扰。

> 面试要点：检索就是把问题向量化，在向量数据库里按相似度找 Top-K 个最相关的文档片段，过滤掉无关信息，为生成阶段提供精准“参考资料”。

## Q6. RAG 中的“增强”具体做什么？

**回答**

“增强”（Augmentation）是指把检索到的相关资料和用户的问题，一起整理成一个结构化的提示词（Prompt），送给大模型。这一步决定了大模型是否会“老实”地基于资料回答，而不是继续“瞎编”。

一个典型的增强后 Prompt 长这样：

```
你是一个专业的助手，请严格基于以下参考资料回答用户的问题。
如果参考资料里没有答案，请诚实说“知识库中未找到相关信息”，不要编造。

【参考资料】
报销单需先经部门经理审批，再交财务部门。单餐报销不超过 200 元。

【用户问题】
公司报销流程是什么？单餐报销上限是多少？

【要求】
1. 只使用参考资料中的信息。
2. 回答时请标注信息来源。
```

增强的核心目的：

- **锚定注意力**：告诉模型“请主要看下面这些资料”，减少模型凭记忆乱发挥。
- **诚实兜底**：明确要求“资料里没有就说不知道”，遏制幻觉。
- **可追溯**：要求模型标注来源，方便用户核查。

> 面试要点：增强就是把“检索到的片段 + 用户问题”组装成带有明确指令的 Prompt，约束模型基于资料回答、无答案则诚实说明、并标注来源，这是防止幻觉的关键一步。

## Q7. RAG 中的“生成”具体做什么？

**回答**

生成是 RAG 的“嘴巴”，由大模型（LLM）完成。拿到增强后的 Prompt（包含问题 + 检索到的参考资料 + 指令），模型基于这些材料，组织语言生成最终答案。

与普通大模型对话的区别在于：普通模型只看到问题，全凭记忆“闭卷”作答；RAG 模型既看到了问题，也看到了检索到的真实材料，相当于“开卷”作答，答案更有依据。

比如：

- 用户问题：“单餐报销上限是多少？”
- 检索到的资料：“单餐报销不超过 200 元。”
- 模型生成：“根据知识库中的报销制度，单餐报销上限为 200 元。”

> 面试要点：生成由大模型完成，输入是“增强后的 Prompt”（问题+检索资料+指令），输出是基于真实资料的答案，比直接让模型闭卷作答更准确、更可信。

## Q8. 人们常说 RAG 让大模型从“闭卷考试”变成“开卷考试”，什么意思？

**回答**

这是一个非常形象的比喻，用来解释 RAG 的核心价值。

**闭卷考试（不使用 RAG）**：
大模型只能凭训练时记住的知识回答。它不认识你公司的新员工手册，不知道昨天的股价，也不知道你上周修改的报销政策。一旦遇到没背过的内容，它只能“硬编”，甚至编造一个看起来很真的错误答案——这就是幻觉。

**开卷考试（使用 RAG）**：
大模型在答题前，先被允许翻阅“参考书”（外部知识库）。它先找到和问题相关的章节，再基于这些章节作答。参考书内容更新了，模型立刻就能用新知识，不需要重新背书（重新训练）。

ASCII 图：

```
闭卷考试（大模型直接回答）        开卷考试（RAG）
┌──────────────┐                  ┌──────────────┐
│ 考题         │                  │ 考题         │
│   │          │                  │   │          │
│   ▼          │                  │   ▼          │
│ 凭记忆作答   │                  │ 先查参考书   │
│ （可能编造） │                  │ （检索片段） │
│   │          │                  │   │          │
│   ▼          │                  │   ▼          │
│  答案        │                  │ 基于资料作答 │
└──────────────┘                  │ （有出处可查） │
                                  └──────────────┘
```

> 面试要点：闭卷考试＝大模型凭记忆回答，容易不知道就编；开卷考试＝RAG 先让模型查外部知识库再作答，知识可更新、答案有依据，幻觉大幅降低。

## Q9. RAG 的回答为什么更可信？能不能做到答案可追溯？

**回答**

RAG 的回答更可信，因为它的每一句关键信息，都对应知识库里的一段真实文档，而不是模型凭空脑补的。

具体体现在三点：

1. **有据可查**：模型必须基于检索到的参考资料作答，不能凭空捏造。
2. **可追溯（带出处）**：系统在检索时知道每个片段来自哪个文档、哪一页、哪一段，可以在回答中标注来源，比如：“根据《报销制度》第 3 页，单餐上限 200 元。”用户可以直接去原文核实。
3. **可验证**：如果答案错了，可以追溯是检索阶段找错了片段，还是生成阶段模型理解错了，方便定位和修复。

简单示意：

```
用户问：单餐报销上限多少？

检索到片段：[文档：报销制度.pdf · 第3页] “单餐报销不超过200元”

模型回答：根据《报销制度》第3页，单餐报销上限为200元。
                                          ↑
                              用户可以直接打开 PDF 第3页核实
```

> 面试要点：RAG 答案基于真实检索资料，可标注文档来源和页码，用户可直接核实，这就是“答案可追溯”，也是 RAG 在企业、医疗、法律等对可信度要求高的场景中受欢迎的原因。

## Q10. Naive RAG、Advanced RAG、Modular RAG 的演进大概是什么？

**回答**

RAG 技术经过几年发展，业界粗略分成三代，每一代都在解决上一代的痛点：

### Naive RAG（基础版 / naive RAG）

最简单的“Indexing → Retrieval → Generation”流程。直接把文档切块、向量化、入库，查询时直接向量检索 Top-K，拼进 Prompt 给大模型。

**问题**：
- 切分不合理，语义被切断；
- 用户提问表达模糊，检索不到相关内容；
- 检索结果里夹杂大量无关信息，模型容易被干扰。

### Advanced RAG（进阶版）

在检索前后加上优化策略，解决 Naive RAG 的召回不准问题：

- **检索前（Pre-retrieval）**：查询改写（把模糊问题改写得更清晰）、多查询展开（一个问题变多个角度去搜）、HyDE（先生成一个假想的完美答案，再用答案去搜索）。
- **检索后（Post-retrieval）**：重排序（Reranker，用更精细的模型对检索结果重新排序）、压缩上下文（只保留和问题最相关的句子，去掉冗余）。

### Modular RAG（模块化版）

把 RAG 拆成可替换的模块，支持迭代、自适应检索。比如：不确定要不要检索时，模型可以自己决定（Self-RAG）；检索不到好结果时，可以主动重新提问或调用工具；多个检索器（向量+关键词+知识图谱）协同工作。

ASCII 演进图：

```
Naive RAG           Advanced RAG              Modular RAG
索引→检索→生成       预处理→检索→后处理→生成    可插拔模块，自适应迭代
  │                       │                         │
  ▼                       ▼                         ▼
简单粗暴              更精准，解决召回问题          灵活，支持复杂推理
适合入门demo          适合大多数生产场景            适合复杂知识密集型任务
```

> 面试要点：Naive RAG 是基础流程（索引-检索-生成），问题在于检索不精准；Advanced RAG 在检索前后加查询改写、多查询、重排序等优化；Modular RAG 把各环节做成可替换模块，支持自适应和多模块协作。入门先学 Naive RAG，生产通常用 Advanced RAG。

## Q11. RAG 有哪些典型的应用场景？

**回答**

RAG 最适合“对准确性有要求、且知识在外部文档里”的场景。常见的有：

1. **企业内部知识库问答**：员工问“报销流程是什么”“带薪年假怎么算”，模型基于公司 HR 手册回答，不用每次都去问人力。
2. **智能客服**：基于产品手册、FAQ、售后政策，自动回答用户问题，减少人工客服压力。
3. **法律/医疗/金融专业问答**：律师查询法条、医生查询诊疗指南、分析师查询财报，答案必须基于权威文档，不能胡编。
4. **新闻与实时信息问答**：模型知识有截止时间，RAG 可以把最新新闻、股价、天气放进知识库，回答“今天”“刚刚”发生的事。
5. **个人笔记/邮件助手**：接入自己的笔记、邮件、聊天记录，做个“懂我的”个人助手。
6. **编程助手/技术文档问答**：接入公司代码仓库、API 文档，开发者问“这个接口怎么调用”，模型基于最新文档回答。

应用场景选型一览表：

| 场景 | 知识来源 | 为什么适合 RAG |
|------|---------|--------------|
| 企业知识库 | 内部手册、Wiki | 私有知识，模型不懂，需准确回答 |
| 智能客服 | 产品FAQ、售后政策 | 问题固定，答案必须基于官方文档 |
| 法律/医疗/金融 | 法条、指南、财报 | 对准确性要求极高，不能幻觉 |
| 新闻问答 | 实时新闻源 | 知识时效性强，需即时更新 |
| 个人助手 | 笔记、邮件 | 私人数据，不能放进公共模型训练 |
| 编程助手 | API文档、代码库 | 文档频繁更新，需基于最新版本 |

> 面试要点：RAG 适合企业知识库、智能客服、法律/医疗/金融专业问答、新闻实时问答、个人笔记助手、编程助手等场景，共同特点是：知识在外部文档里、对准确性有要求、知识可能随时间变化。

## Q12. 为什么说 RAG 能降低大模型落地的成本？

**回答**

跟“让大模型学会新知识”的另一个主流方案——微调（Fine-tuning）相比，RAG 的成本低很多：

1. **不需要昂贵的训练资源**：微调需要大量标注数据和 GPU 集群，动辄数千到数万美元；RAG 只需要文档和一个向量数据库，几台普通服务器甚至笔记本电脑就能跑起来。
2. **知识更新几乎免费**：公司政策变了，微调得重新收集数据、重新训练，耗时耗钱；RAG 只要把新文档丢进知识库，重新向量化入库即可，秒级生效。
3. **推理 Token 费用低**：微调后的模型每次回答可能仍需要把大量上下文塞进 Prompt；RAG 每次只检索几个相关片段，输入 Token 很少，API 调用成本低。

> 面试要点：RAG 成本低体现在：无需 GPU 训练、知识更新只要换文档、每次推理只喂少量检索片段（Token 费用低），是中小团队落地大模型知识应用的首选方案。

## Q13. RAG 系统的核心组件有哪些？

**回答**

一个最小可用的 RAG 系统，通常由以下核心组件组成：

| 组件 | 作用 | 常见选择（初学者友好） |
|------|------|---------------------|
| 文档加载器 | 读取 PDF、Word、TXT、网页等，转成纯文本 | LangChain 文档加载器、pypdf、python-docx |
| 文本分割器 | 把长文档切成合适大小的片段（Chunk） | LangChain `RecursiveCharacterTextSplitter` |
| Embedding 模型 | 把文本转成向量（数学指纹） | sentence-transformers、BGE、OpenAI Embedding |
| 向量数据库 | 存储向量，支持高速相似度检索 | Chroma（轻量，适合入门）、FAISS、Milvus、Pinecone |
| 大语言模型（LLM） | 基于检索资料生成最终答案 | GPT、Claude、Llama、通义千问等 |
| Prompt 模板 | 组装问题+检索资料+指令，发给 LLM | 自定义模板字符串 |

> 面试要点：RAG 核心组件包括文档加载器、文本分割器、Embedding 模型、向量数据库、大语言模型、Prompt 模板六个环节，缺一不可。入门推荐 Chroma + sentence-transformers + LangChain 组合，轻量且易上手。

## Q14. 什么是 Embedding（向量嵌入）？为什么语义相近的文本，向量也相近？

**回答**

Embedding（中文常叫“向量嵌入”或“文本向化”）是把一段文字转成一串数字的过程。这串数字就是一个向量，比如：

```
"猫咪喜欢玩毛线球"  →  [0.23, -0.45, 0.87, ..., 0.12]   (比如 384 维或 768 维)
```

Embedding 模型是用海量文本训练出来的，它学到了一个规律：**意思相近的句子，转成的向量在数学空间里的距离也更近**。

举例：

- “猫爱玩毛线球” 和 “小猫喜欢撸绒线” → 意思相近，向量距离很近。
- “猫爱玩毛线球” 和 “明天股市会涨吗” → 意思完全不相关，向量距离很远。

因为 RAG 的检索就是基于“向量距离”来找相关文档的，所以 Embedding 质量直接决定检索好坏。Embedding 差，检索出来的片段就离题，后面大模型再强也没用。

ASCII 示意（二维简化，实际是几百维）：

```
        向量空间
          ↑
   [宠物类]      [财经类]
      ● A        ● D
    ●   B      ●   E
      ● C        ● F
          ↑
          →

A = "猫爱玩毛线球"
B = "小猫喜欢撸绒线"   → 与 A 很近（同一个簇）
C = "怎么给猫剪指甲"   → 与 A 较近
D = "明天股市会涨吗"
E = "比特币价格走势"   → 与 D 很近（另一个簇）
F = "如何理财"        → 与 D 较近
```

用户问题向量化后，落在向量空间的某个点，离 A/B/C 簇最近，于是检索到关于猫的文档，而不是股市文档。

> 面试要点：Embedding 就是把文本转成向量，意思相近的文本向量距离更近。RAG 检索正是利用这个特性，把问题向量化后在向量数据库里找最近的邻居，所以 Embedding 质量直接决定检索准不准。

## Q15. 什么是向量数据库？它和普通数据库有什么区别？

**回答**

普通数据库（比如 MySQL）是按“精确值”查找的：你查“姓名＝张三”，只能返回姓名严格等于“张三”的记录，找不到“张三丰”或“张三风”。

向量数据库是按“相似度”查找的：你给一个向量，它返回向量空间里距离这个向量最近的若干条记录，哪怕这些记录的原始文字不完全一样，只要语义相近就能找到。

区别对比表：

| 维度 | 普通数据库（MySQL 等） | 向量数据库（Milvus、Chroma、FAISS 等） |
|------|---------------------|-------------------------------------|
| 存什么 | 结构化数据（姓名、年龄、金额） | 高维向量 + 原始文本 + 元数据 |
| 怎么查 | 精确匹配、范围查询 | 相似度搜索（最近邻，Nearest Neighbor） |
| 查什么 | “等于”、“大于”、“like” | “和这个向量最像的 Top-K 个” |
| 适合场景 | 账单、用户表、订单 | RAG 知识库、语义搜索、推荐系统 |

举个 RAG 里的例子：

知识库里有句子：“榴莲被誉为热带水果之王，营养丰富。”
用户问：“水果之王是什么？”

普通数据库按关键词搜，如果文档里没有“水果之王”这四个字连在一起，可能搜不到。但向量数据库会算：“水果之王”这个问题的向量，和“榴莲被誉为热带水果之王”的向量语义很近，于是能检索出这句话。

> 面试要点：向量数据库按“语义相似度”而非“精确关键词”查找，适合 RAG 知识库；普通数据库按精确值查找，适合业务表单。两者常配合使用：向量库负责找相关片段，普通库负责存元数据（文档名、页码等）。

## Q16. RAG 的“四步构建流程”具体指哪四步？

**回答**

书里把 RAG 快速上手总结为“四步构建流程”，对应索引阶段的四个核心动作，像盖房子的地基一样，每一步都决定了最终效果：

**步骤 1：数据加载（Document Loading）**

把各种格式的文档（PDF、Word、TXT、Markdown、网页、HTML 等）读进来，转成纯文本。不同格式用不同的加载器，比如读 PDF 用 `pypdf`，读 Word 用 `python-docx`，读网页用 `BeautifulSoup`。

**步骤 2：文本分块（Text Chunking）**

长文档不能一次性全部向量化，太大了检索不准，也塞不进模型上下文。需要把文档切成一个个小片段（Chunk），每个片段几百到一千字，切的时候尽量别把一句话或一个完整概念切断。

**步骤 3：向量嵌入（Embedding）**

用 Embedding 模型把每个文本片段转成向量，作为这段文字的“数学指纹”。同样的模型也要在查询时把用户问题转成向量，才能跟文档向量比距离。

**步骤 4：向量存储与索引（Vector Store & Indexing）**

把向量和对应的原始文本一起存入向量数据库，并建立索引。以后查询时，在这个索引里按相似度高速检索，找出 Top-K 个最相关的片段。

四步图示：

```
步骤1：数据加载        步骤2：文本分块        步骤3：向量嵌入        步骤4：向量存储
┌─────────┐          ┌─────────┐          ┌─────────┐          ┌─────────┐
│ 产品手册.pdf│      │ [片段1]  │          │ 片段1 →  │          │ [向量1]  │
│ 员工手册.docx│      │ [片段2]  │   ---->  │ [0.23,..]│  ---->  │ [文本1]  │
│ FAQ.md    │      │ [片段3]  │          │ 片段2 →  │          │ [向量2]  │
└─────────┘          │ [片段4]  │          │ [0.67,..]│          │ [文本2]  │
                     └─────────┘          └─────────┘          │ ...    │
                                                              └─────────┘
                                                     (建立索引，供高速检索)
```

> 面试要点：四步构建流程＝数据加载→文本分块→向量嵌入→向量存储与索引。这是 RAG 离线索引阶段的标准流水线，做好这四步，才能支撑后面的在线查询。

## Q17. 文本分块（Chunking）为什么要做？切得太大或太小有什么问题？

**回答**

文档通常很长（几万字），直接整篇向量化检索会有两大问题：

1. **向量距离被稀释**：一篇几万字的文档转成一个向量，里面混杂了几十个不相关的主题，向量的“中心”就不代表任何一个具体主题，检索时很难命中用户真正想问的那一段。
2. **塞不进上下文窗口**：检索出来的片段要拼进 Prompt 送给大模型，如果每个片段都是几万字，几个片段就把上下文窗口撑爆了，模型也看不过来。

所以要把文档切成适当大小的块（Chunk），每块聚焦一个主题，几百到一千字左右。

但是切块也有讲究：

- **切得太大**：上面说的两个问题都会出现，检索不准，而且浪费 Token。
- **切得太小**：一句话一个块，上下文丢失。比如文档里写“报销单需先经部门经理审批，再交财务。”如果切成“报销单需先经部门经理审批”和“再交财务。”两块，单独看第二块就不知道交给谁了，语义破碎。

### 实用建议（大白话版）

- 一般推荐每块 **300～1000 字**。
- 相邻两块要有 **重叠（Overlap）**，比如重叠 50～200 字，避免信息在切分边界被切断。
- 尽量按段落、标题、句子等语义边界切，别把一个完整句子拦腰截断。

ASCII 示意（重叠分块）：

```
原文：报销单需先经部门经理审批，再交财务部门。单餐报销不超过200元。出差住宿可报销。

切块1（500字，含重叠）：[报销单需先经部门经理审批，再交财务部门。单餐报销不超过200元。]
                                                        ↑ 重叠部分
切块2（500字，含重叠）：                              [单餐报销不超过200元。出差住宿可报销。]
```

> 面试要点：分块是为了让每个向量聚焦一个主题，且能塞进模型上下文。太大检索不准且费 Token，太小语义破碎。建议每块 300～1000 字，相邻块重叠 50～200 字，按段落/标题等语义边界切。

## Q18. chunk_size 和 chunk_overlap 分别是什么？怎么选？

**回答**

在 LangChain 等 RAG 框架里，分块通常有两个核心参数：

- **chunk_size**：每个块的最大字符数（或 Token 数）。比如 `chunk_size=500` 表示每块最多 500 个字符。
- **chunk_overlap**：相邻两个块之间重叠的字符数。比如 `chunk_overlap=100` 表示块和块之间重叠 100 个字符。

### 怎么选？

- **chunk_size**：300～1000 字比较常用。如果文档是专业术语密集的（比如法律条文），可以小一点（300～500）；如果是叙述性文章，可以大一点（800～1000）。不要超过模型能一次性消化的上下文，也不要太小导致语义破碎。
- **chunk_overlap**：一般设为 chunk_size 的 10%～20%，即 50～200 字。重叠主要是防止一个完整意思被切成两半，分到不同块里丢失上下文。

### Python 示例（LangChain）

```python
from langchain.text_splitter import RecursiveCharacterTextSplitter

text = open("knowledge.txt", "r", encoding="utf-8").read()

splitter = RecursiveCharacterTextSplitter(
    chunk_size=500,      # 每块最多 500 字符
    chunk_overlap=100,   # 相邻块重叠 100 字符
    separators=["\n\n", "\n", "。", "！", "？", "；", "，", " ", ""],  # 按段落→句子→标点优先切
)

docs = splitter.create_documents([text])
print("切成多少块：", len(docs))
for i, d in enumerate(docs[:3]):
    print(f"--- 块 {i+1}（长度 {len(d.page_content)}） ---")
    print(d.page_content[:200])
```

> 面试要点：chunk_size 控制每块大小（建议 300～1000 字），chunk_overlap 控制相邻块重叠（建议 50～200 字，防止语义在边界被切断）。RecursiveCharacterTextSplitter 会优先按段落、句子、标点等语义边界切分，推荐入门使用。

## Q19. 什么是 Embedding 模型？常用的有哪些？怎么选？

**回答**

Embedding 模型就是把文本转成向量的“翻译官”。它把一段话编码成一串数字（比如 384 维或 768 维），语义相近的文本，向量距离更近。

常用的 Embedding 模型（按初学者友好程度）：

| 模型 | 特点 | 适合场景 |
|------|------|---------|
| sentence-transformers / all-MiniLM-L6-v2 | 开源、轻量、可本地运行，中英文都支持 | 入门 demo、隐私敏感、不想调云端 API |
| BGE（北京智源） | 中文效果好，开源 | 中文场景、企业内部知识库 |
| M3E | 国产优秀模型，中英双语 | 中文场景 |
| OpenAI text-embedding-3-small / large | 云端 API，效果强，按 Token 付费 | 对效果要求高、不介意调用 API 成本 |

**怎么选？**

- 刚入门、想免费本地跑：选 `sentence-transformers/all-MiniLM-L6-v2` 或 BGE。
- 中文文档为主：优先考虑 BGE、M3E。
- 对检索效果要求极高、预算充足：可选 OpenAI text-embedding-3 系列。

> 面试要点：Embedding 模型把文本转成向量，是 RAG 检索的基础。入门推荐开源轻量的 sentence-transformers 或 BGE，中文场景优先 BGE/M3E，追求极致效果可用 OpenAI Embedding。不同模型出的向量维度不同，建库和查询必须用同一个模型，否则向量空间不统一，检索不到东西。

## Q20. 向量数据库常见的有哪些？初学者该选哪个？

**回答**

向量数据库专门用来高效存储和检索高维向量，常见的有：

| 向量数据库 | 特点 | 初学者友好度 |
|-----------|------|-------------|
| **Chroma** | 轻量级，支持内存模式，无需复杂部署，Python 接口友好 | ⭐⭐⭐⭐⭐ 推荐入门 |
| **FAISS** | Facebook 开源，纯检索库，速度快，但更偏向底层工具 | ⭐⭐⭐⭐ |
| **Milvus** | 国产优秀，功能强大，支持分布式，适合生产规模 | ⭐⭐⭐（需部署） |
| **Pinecone** | 云端托管，免维护，按使用量付费 | ⭐⭐⭐⭐（需注册云端账号） |

> 面试要点：常见向量数据库有 Chroma、FAISS、Milvus、Pinecone、Qdrant。初学者推荐 Chroma（轻量、内存模式、无需部署）；生产环境数据量大可选 Milvus；不想运维可用 Pinecone 云端版。

## Q21. 查询阶段具体做哪四步？

**回答**

索引阶段把知识库准备好后，用户每次提问，系统走查询阶段（在线阶段），也分四步：

**步骤 1：问题向量化**

用和建库时**完全相同的** Embedding 模型，把用户的问题也转成一个向量。必须用同一个模型，因为不同模型的向量空间不一样，跨模型比距离没有意义。

**步骤 2：相似性检索（Top-K）**

在向量数据库里，把“问题向量”与库里所有“文档片段向量”计算相似度（通常用余弦相似度），取距离最近的前 K 个片段（比如 K=3 或 K=5）。

**步骤 3：Prompt 增强（增强生成）**

把用户问题和检索到的 Top-K 片段，组装成一个带指令的 Prompt，例如：

```
请基于以下参考资料回答问题。如果资料里没有，请诚实说不知道。

参考资料：
[片段1] ...
[片段2] ...

问题：用户的原始问题
```

**步骤 4：大模型生成答案**

把增强后的 Prompt 送给大模型，让它基于检索资料生成最终回答，并尽量标注来源。

四步图示：

```
用户提问
    │
    ▼
步骤1：问题向量化（同一Embedding模型）
    │
    ▼
步骤2：相似性检索（向量数据库，取Top-K片段）
    │
    ▼
步骤3：Prompt增强（问题+检索片段+指令）
    │
    ▼
步骤4：LLM生成最终答案
    │
    ▼
返回给用户
```

> 面试要点：查询阶段四步＝问题向量化→相似性检索（Top-K）→Prompt 增强→LLM 生成。问题必须和建库时用同一个 Embedding 模型向量化，否则向量空间不统一，检索出的结果会完全不对。

## Q22. 余弦相似度怎么算？值越大表示越相似吗？

**回答**

余弦相似度是衡量两个向量“方向是否接近”的指标，也是向量数据库里最常用的相似度算法之一。

公式：

```
相似度 = cos(θ) = (A · B) / (|A| × |B|)
```

其中 `A · B` 是两个向量的点积，`|A|` 和 `|B|` 是两个向量的长度（模）。

结果范围在 -1 到 1 之间：

- **1**：方向完全一致，语义最相似。
- **0**：正交，无相关性。
- **-1**：方向相反，完全相反。

在 RAG 里，文本经过 Embedding 后通常会被**归一化**（长度变成 1），所以余弦相似度其实等价于点积，值越大表示两段文字语义越接近。

### Python 示例

```python
import numpy as np

def cosine_similarity(a, b):
    return np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b))

# 两个简单向量（实际 Embedding 是几百维，这里用二维方便理解）
vec_a = np.array([1.0, 1.0])   # "猫爱玩毛线球"
vec_b = np.array([1.0, 0.9])   # "小猫喜欢绒线" —— 与 a 很像
vec_c = np.array([-1.0, 0.0])  # "明天股市涨跌" —— 与 a 不像

print("a 与 b 相似度：", round(cosine_similarity(vec_a, vec_b), 3))  # 接近 1
print("a 与 c 相似度：", round(cosine_similarity(vec_a, vec_c), 3))  # 接近 0 或负数
```

> 面试要点：余弦相似度衡量两个向量方向的接近程度，范围 -1～1，值越大（越接近 1）表示语义越相似。RAG 检索就是按这个分数给文档片段排序，取 Top-K 个分数最高的。

## Q23. RAG 的知识库怎么更新？需要重新训练模型吗？

**回答**

**不需要重新训练模型。** 这是 RAG 相比微调最大的优势之一。

知识库更新的操作非常简单：

1. **新增文档**：把新的 PDF、Word、TXT 文件丢进知识库文件夹。
2. **重新加载与分块**：跑一遍“数据加载 → 文本分块”，把新文档切成片段。
3. **向量化入库**：用 Embedding 模型给新片段生成向量，存入向量数据库（可以追加，不需要删掉旧数据）。
4. **立即生效**：下次用户提问时，检索阶段就会把新文档里的内容检索出来，模型就能基于新知识回答了。

整个过程通常是秒级到分钟级，取决于新文档多少，完全不需要 GPU 训练，也不需要发布新模型版本。

ASCII 示意：

```
旧知识库                          新增文档后
┌─────────────┐                   +  新文档.pdf
│ 文档A（向量）│                   │
│ 文档B（向量）│   ──▶  加载分块 ───▶  新片段（向量）追加入库
│ 文档C（向量）│      向量化       │
└─────────────┘                   └─────────────┘
                                 (立即生效，无需训练模型)
```

> 面试要点：RAG 更新知识库不需要重新训练模型，只需把新文档加载、分块、向量化、追加入向量数据库即可，秒级到分钟级生效。这也是 RAG 适合知识频繁变化场景的核心原因。

## Q24. RAG 系统能回答知识库里没有的问题吗？会怎样？

**回答**

理论上，大模型仍然可以利用它训练时的通用知识来回答，但是一个设计良好的 RAG 系统，**应该尽量只基于知识库回答**，且在知识库里找不到相关信息时，诚实地说“知识库中未找到相关信息”，而不是瞎编。

怎么做到？

在 Prompt 增强阶段，给模型明确指令：

```
请严格基于以下参考资料回答问题。
如果参考资料中没有答案，请直接说“知识库中未找到相关信息”，不要凭自己的知识编造。
```

这样做的好处：

1. **减少幻觉**：模型不会为了凑答案而编造不存在的公司政策或法条。
2. **边界清晰**：用户知道哪些是基于公司文档的准确答案，哪些是模型不知道的。
3. **方便反馈**：如果用户经常问某个知识库里没有的问题，说明知识库缺这部分内容，可以补全文档。

> 面试要点：RAG 本身可以回答知识库外的问题（靠模型通用知识），但生产系统通常通过 Prompt 指令约束模型“资料里没有就说不知道”，以减少幻觉、划清边界、便于发现知识库缺口。

## Q25. RAG 的回答不准确，通常是哪个环节出了问题？怎么排查？

**回答**

RAG 回答不准，通常不是大模型本身“笨”，而是前面的检索没找到好资料。排查顺序建议从“浅到深”：

1. **检索阶段（最常见）**：检索到的 Top-K 片段本身就和问题不相关，或者相关片段排名靠后被丢弃了。→ 检查 Embedding 模型是否和建库时一致；检查 chunk_size 是否合适；尝试增加 Top-K；引入重排序（Reranker）。
2. **分块阶段**：相关信息被切断，分到不同块，语义不完整。→ 调整 chunk_size 和 overlap，按语义边界切分。
3. **Prompt 增强阶段**：检索到了好资料，但 Prompt 组装得不好，模型没重点看。→ 优化 Prompt 模板，明确要求“基于参考资料回答”。
4. **生成阶段（较少见）**：资料都对了，模型理解错了或仍在瞎编。→ 更换更强的 LLM，或在 Prompt 中加强“无答案则诚实说明”的指令。

排查口诀：**先看检到了什么，再看送了什么，最后看模型答了什么。**

> 面试要点：RAG 答错优先怀疑检索阶段（片段不相关/排名靠后），其次是分块（语义被切断）、Prompt 增强（模型没重点看资料），最后才是生成模型本身。排查遵循“检到了什么 → 送了什么 → 答了什么”的顺序。

## Q26. 用 Python 手撕一个最小可运行的 RAG 系统，代码长什么样？

**回答**

下面是一个不依赖云端 API、完全在本地运行的最小 RAG 系统。使用的组件：

- `sentence-transformers`：Embedding 模型（本地运行，免费）。
- `chromadb`：向量数据库（内存模式，无需部署）。
- 模拟一个简单的“生成模型”：由于大多数读者没有付费的 LLM API，这里用一个规则函数模拟大模型基于检索资料回答；如果你有 OpenAI/通义千问等 API，把 `mock_generate` 替换成真实的 API 调用即可。

先安装依赖：

```bash
pip install sentence-transformers chromadb numpy
```

完整代码：

```python
import numpy as np
from sentence_transformers import SentenceTransformer
import chromadb

# ===================== 配置 =====================
EMBED_MODEL = "all-MiniLM-L6-v2"   # 本地 Embedding 模型，自动下载
TOP_K = 3                           # 检索返回的片段数量

# ===================== 1. 数据加载 =====================
# 模拟一个小知识库（实际可从 PDF/TXT 加载）
documents = [
    "公司报销制度：单餐报销不超过 200 元，需提供发票。",
    "出差住宿可报销，标准为每晚不超过 500 元。",
    "员工入职后享有 5 天带薪年假，需提前申请。",
    "办公室空调温度统一设定为 26 度，请勿私自调节。",
    "技术部每周五下午进行代码评审（Code Review）。",
]

# ===================== 2. 文本分块（这里每篇文档本身就短，当作一个块） =====================
chunks = documents
chunk_ids = [f"chunk_{i}" for i in range(len(chunks))]

# ===================== 3. 向量嵌入 =====================
embed_model = SentenceTransformer(EMBED_MODEL)
embeddings = embed_model.encode(chunks)  # shape: (len(chunks), 维度)
print(f"Embedding 完成，向量数量：{embeddings.shape[0]}，维度：{embeddings.shape[1]}")

# ===================== 4. 向量存储与索引（Chroma 内存模式） =====================
client = chromadb.Client()
collection = client.create_collection(name="company_docs")

collection.add(
    documents=chunks,
    embeddings=embeddings.tolist(),
    ids=chunk_ids,
)

# ===================== 查询阶段 =====================
def retrieve(query, top_k=TOP_K):
    """把问题向量化，在向量数据库里检索最相关的 Top-K 片段"""
    query_embedding = embed_model.encode([query])[0]
    results = collection.query(
        query_embeddings=[query_embedding.tolist()],
        n_results=top_k,
    )
    return results["documents"][0]  # 返回 Top-K 个片段文本

def mock_generate(query, context_chunks):
    """
    模拟大模型生成：基于检索到的片段组织答案。
    实际使用时，把这里替换成真实 LLM API 调用（如 OpenAI ChatCompletion）。
    """
    if not context_chunks:
        return "知识库中未找到相关信息。"

    context = "\n".join([f"- {c}" for c in context_chunks])
    answer = f"""基于知识库中的资料，为您回答：

{context}

综上所述，以上是根据知识库资料整理的答复（如资料未覆盖您的问题，请补充知识库）。"""
    return answer

def rag_query(query):
    """完整的 RAG 查询流程：检索 → 增强 → 生成"""
    relevant_chunks = retrieve(query, TOP_K)
    answer = mock_generate(query, relevant_chunks)
    return answer, relevant_chunks


# ===================== 运行示例 =====================
if __name__ == "__main__":
    while True:
        user_query = input("\n请输入您的问题（输入 quit 退出）：")
        if user_query.lower() == "quit":
            break
        answer, chunks = rag_query(user_query)
        print("\n===== 检索到的相关片段 =====")
        for i, c in enumerate(chunks, 1):
            print(f"{i}. {c}")
        print("\n===== 生成的回答 =====")
        print(answer)
```

运行效果示例：

```
请输入您的问题（输入 quit 退出）：单餐报销上限是多少？

===== 检索到的相关片段 =====
1. 公司报销制度：单餐报销不超过 200 元，需提供发票。

===== 生成的回答 =====
基于知识库中的资料，为您回答：

- 公司报销制度：单餐报销不超过 200 元，需提供发票。

综上所述，以上是根据知识库资料整理的答复...
```

### 如果要接入真实大模型

把 `mock_generate` 替换成调用 OpenAI / 通义千问 / 文心一言等 API，示例骨架：

```python
from openai import OpenAI

client = OpenAI(api_key="your-api-key")

def real_generate(query, context_chunks):
    context = "\n".join(context_chunks)
    prompt = f"""请基于以下参考资料回答问题。如果资料里没有，请诚实说不知道。

参考资料：
{context}

问题：{query}"""

    response = client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[{"role": "user", "content": prompt}],
    )
    return response.choices[0].message.content
```

> 面试要点：最小 RAG 系统由四步组成：加载文档 → 分块 → Embedding 向量化 → Chroma 存储索引；查询时问题向量化 → 相似度检索 Top-K → 拼 Prompt → 大模型生成。代码中 `sentence-transformers` 负责本地向量化，`chromadb` 负责向量存储检索。真实落地时只需把 `mock_generate` 换成真实 LLM API 调用即可。

## Q27. 运行上面的代码需要注意什么？（环境与常见坑）

**回答**

跑通这个最小 RAG 代码，初学者容易踩以下几个坑：

1. **首次运行会自动下载 Embedding 模型**：`sentence-transformers` 会从 Hugging Face 下载 `all-MiniLM-L6-v2`（约 80 MB），需要联网。如果无法访问外网，可以提前把模型文件下载好放到本地，用 `SentenceTransformer("本地模型路径")` 加载。
2. **建库与查询必须用同一个 Embedding 模型**：如果建库时用 `all-MiniLM-L6-v2`，查询时换成 `BGE`，向量空间不统一，检索结果会全错。
3. **Chroma 默认是内存模式**：程序退出后数据会丢失。如需持久化，初始化时指定 `chromadb.PersistentClient(path="./chroma_db")`，数据就会保存到磁盘。
4. **中文文档效果**：`all-MiniLM-L6-v2` 主要是英文训练，中文效果一般。中文场景建议换成 BGE 或 M3E 模型。
5. **没有真实 LLM API 时**：代码里的 `mock_generate` 只是规则模拟，不会像真正的大模型那样灵活回答。接入真实 API 需要申请 API Key 并按文档调用。

> 面试要点：跑本地 RAG demo 注意：首次需下载模型（需联网）、建库查询必须同一 Embedding 模型、Chroma 内存模式重启后数据丢失（可用 PersistentClient 持久化）、中文场景推荐 BGE/M3E、mock 生成只是演示，真实落地需接 LLM API。

## Q28. RAG 中的 Top-K 是什么？K 选多少合适？

**回答**

Top-K 是检索阶段返回的“最相关片段数量”。比如 `K=3` 表示检索阶段只把最像问题的 3 个文档片段返给大模型。

**K 选多少？**

- **K 太小（如 1）**：可能漏掉重要信息，答案不完整。
- **K 太大（如 20）**：引入太多无关信息，模型容易被干扰，而且 Prompt 变长，Token 费用和响应时间都增加。

**实用建议**：初学者先从 `K=3` 或 `K=5` 开始，根据实际效果调整。如果答案经常漏信息，适当加大；如果答案经常被无关信息干扰，适当减小或加一个重排序（Reranker）环节。

> 面试要点：Top-K 是检索返回的相关片段数量。建议从 3～5 开始，太小漏信息，太大引入噪声且浪费 Token，根据实际效果动态调整。

## Q29. RAG 能不能处理图片、表格等多模态内容？

**回答**

传统的文本 RAG 主要处理文字。要处理图片、表格、公式等多模态内容，需要做一些扩展：

1. **图片**：先用 OCR（光学字符识别）把图片里的文字识别出来，或者用多模态 Embedding 模型把图片直接转成向量，然后和文本一起存在向量数据库里。
2. **表格**：表格的行列结构如果直接切成文本，语义容易断。常见做法是把表格转成 Markdown 表格或 JSON，再按语义分块；或者先用大模型把表格内容总结成文字描述，再向量化。
3. **多模态嵌入（Omni Embedding）**：像 Jina v5-omni 这类模型，可以把图片和文本都编码到同一个向量空间，实现“以图搜文”“以文搜图”。

> 面试要点：基础 RAG 处理文本；处理图片可用 OCR 或多模态 Embedding，处理表格建议转成 Markdown/JSON 或先总结成文字。多模态 RAG（如基于 Jina omni 等）是进阶方向，不属于本章基础入门的核心范围。

## Q30. 本章小结：一个初学者应该怎么入门 RAG？

**回答**

如果你是第一次接触 RAG，建议按这个路径入门，不要试图一次性学完所有高级技术：

1. **先理解概念**：RAG 就是“先检索外部资料，再让大模型基于资料回答”，解决知识过时、幻觉、私有知识盲区。
2. **跑通一个 demo**：用 Python + sentence-transformers + Chroma，照着 Q26 的代码，搭一个能回答“公司报销制度”的最小知识库问答系统。能跑通比看十遍原理更重要。
3. **理解四步流程**：数据加载 → 文本分块 → 向量嵌入 → 向量存储与索引（索引阶段）；问题向量化 → 相似性检索 → Prompt 增强 → LLM 生成（查询阶段）。
4. **调参优化**：尝试不同的 `chunk_size`、`chunk_overlap`、`Top-K`，观察检索结果的变化。
5. **再学进阶**：等基础 demo 跑稳了，再学 Advanced RAG（查询改写、重排序）、Modular RAG、GraphRAG 等。

一句话总结：**RAG 不需要你成为算法专家，会一点 Python，花一个下午跑通 demo，就能搭出一个能回答公司私有知识的 AI 助手。**

> 面试要点：入门 RAG 不必一步登天，先理解概念、跑通本地 demo、掌握四步流程、调参优化，再逐步学进阶技术。会 Python 即可上手。
