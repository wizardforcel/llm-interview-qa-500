## Q1. GPU 的硬件层级结构是怎样的？

**回答**

GPU 的硬件不是一块单一的大芯片那么简单，它内部有层层嵌套的结构。从大到小，AMD GPU（以 RDNA/gfx12 架构为例）的层级是：

```
Agent（整颗 GPU 芯片）
  └─ Shader Array (SA)        着色器阵列，多个 WGP
        └─ Work-Group Processor (WGP)  工作组处理器，多个 CU（RDNA 引入）
              └─ Compute Unit (CU)     计算单元，多个 SIMD
                    └─ SIMD            单指令多数据流单元，执行 wavefront
```

用大白话比喻，GPU 像一个巨大的工厂：

- **SA（Shader Array）** 是工厂的一个大车间；
- **WGP（Work-Group Processor）** 是车间里的一条生产线；
- **CU（Compute Unit）** 是生产线上的一个工作站；
- **SIMD** 是工作站里的一个计算通道，负责真正按步骤执行指令。

每一层都有自己的缓存和资源，理解这层结构，才能搞清楚你的程序是怎么分发到 GPU 上跑的。

> 面试要点：AMD GPU 层级＝SA→WGP→CU→SIMD，层层嵌套，每层都有自己的缓存和资源，是理解程序如何分发到硬件上的基础。

## Q2. CU 和 SIMD 有什么关系？

**回答**

CU（计算单元）是 GPU 里比较小的计算单位，而 SIMD（单指令多数据流单元）是 CU 里面更细的计算通道。

一个 CU 里面包含多个 SIMD（通常是 4 个 SIMD16）。每个 SIMD 里有自己的向量算术逻辑单元（VALU）和寄存器文件，负责执行具体的指令。

可以把 CU 想象成一个“小组”，里面有 4 个“工人”（SIMD），每个工人可以同时干同一种活，只是处理的数据不同。CU 负责把任务分发给下面的 SIMD，SIMD 负责真正干活。

ASCII 图示：

```
        CU（计算单元，工作站）
   ┌─────────────────────────────┐
   │                             │
   │  SIMD0   SIMD1   SIMD2   SIMD3 │
   │  (工人0) (工人1) (工人2) (工人3) │
   │     │       │       │       │     │
   │     ▼       ▼       ▼       ▼     │
   │  执行 wavefront 片段（同一条指令，不同数据）│
   └─────────────────────────────┘
```

> 面试要点：CU 是工作站，SIMD 是里面的计算通道，一个 CU 通常包含多个 SIMD，SIMD 负责按“同一条指令、不同数据”的方式执行 wavefront。

## Q3. 什么是 wavefront？它和 CUDA 的 warp 有什么区别？

**回答**

wavefront（波前）是 AMD GPU 里的基本执行单位，可以简单理解为 **AMD 版本的 CUDA warp**。

一个 wavefront 是一组按“锁步”方式执行的线程，它们共享同一个程序计数器（PC），同一时刻执行同一条指令，只是处理的数据不同。

- 在 AMD GPU 里，这个执行组叫 **wavefront**。
- 在 NVIDIA GPU 里，同样的概念叫 **warp**。

两者的核心思想是一样的：把多个线程打成一组，一起执行，以提高并行效率。区别主要在大小和厂商术语上：

| 维度 | AMD wavefront | NVIDIA warp |
|------|--------------|------------|
| 大小 | RDNA 支持 wave32（32 线程）和 wave64（64 线程），gfx1201/RDNA4 两者都支持 | 固定 32 线程 |
| 术语 | wavefront | warp |
| 调度 | 由 SPI（Schedule Processor）分发到 CU | 由调度器分发到 SM |

> 面试要点：wavefront 是 AMD GPU 的基本执行单位，对应 NVIDIA 的 warp；它是一组锁步执行的线程，共享程序计数器，同一时刻执行同一条指令。

## Q4. wave32 和 wave64 有什么区别？怎么选？

**回答**

wavefront 有两种大小：wave32（32 个线程）和 wave64（64 个线程）。

- **wave32**：每组 32 个线程，一次周期就能执行完一条指令（在 RDNA 的原生宽度下），适合延迟敏感、规模较小的任务。
- **wave64**：每组 64 个线程，需要两个周期才能执行完一条向量指令（先算低 32 个，再算高 32 个），适合吞吐量要求高、能充分利用宽向量的任务。

**怎么选？** 通常不需要你手动强制指定，编译器和运行时会根据架构和 kernel 特性自动选择。但你可以通过编译选项或运行时设置偏好。关键原则是：**不要在代码里把 wavefront 大小硬编码成固定数值**，应该通过 `warpSize`（HIP 里对应的查询方式）动态获取，以保证代码在不同架构（wave32 或 wave64）上都能跑。

ASCII 图示（wave64 分两步执行）：

```
wave64（64 线程）的一次向量指令：
第1周期：处理线程 0～31  ──▶  低半波
第2周期：处理线程 32～63 ──▶  高半波

wave32（32 线程）的一次向量指令：
第1周期：处理线程 0～31  ──▶  一次性完成
```

> 面试要点：wave32 每组 32 线程，一次周期执行完；wave64 每组 64 线程，分两个周期执行。不要把 wavefront 大小硬编码，应动态查询 `warpSize`。

## Q5. GPU 怎么执行程序？（锁步执行、同一个程序计数器）

**回答**

GPU 执行程序的方式和 CPU 不太一样。CPU 的每个线程都有自己的程序计数器，可以独立跳转、独立循环；而 GPU 的 wavefront 里，所有线程**共享同一个程序计数器**，同一时刻执行同一条指令，这就是“锁步执行”（lockstep execution）。

用大白话比喻：

- **CPU 像一群独立工作的员工**：每个人手里有自己的任务清单，可以各自决定做什么，互不干扰。
- **GPU wavefront 像一队齐步走的士兵**：所有人听同一个口令，同一时刻做同一个动作，只不过每个人手里拿的数据（比如要加的数字）不一样。

锁步执行的好处是硬件设计简单、功耗低；代价是如果线程间出现分支（比如有的线程走 if 分支，有的走 else 分支），就需要通过“掩码”来处理，这会带来性能损失（下一题会讲）。

ASCII 图示：

```
CPU 多线程（独立 PC）：
线程A：PC_A ──▶ 指令1 ──▶ 指令2 ──▶ ...
线程B：PC_B ──▶ 指令X ──▶ 指令Y ──▶ ...
（各自跳转，互不干扰）

GPU wavefront（锁步，共享 PC）：
       共享 PC ──▶ 指令1 ──▶ 指令2 ──▶ ...
     ┌────┬────┬────┬────┐
     │ L0 │ L1 │ L2 │ L3 │  各线程（lane）数据不同，但执行同一指令
     └────┴────┴────┴────┘
```

> 面试要点：GPU wavefront 里所有线程共享同一个程序计数器，锁步执行同一条指令，只是处理的数据不同。这与 CPU 每个线程独立 PC 的模式根本不同。

## Q6. 什么是 EXEC mask？分支偏差怎么办？

**回答**

因为 wavefront 里所有线程锁步执行同一条指令，但如果代码里有 `if-else` 分支，不同线程可能想走不同的分支。这时候 GPU 不能真的让每个线程独立跳转（因为共享 PC），而是采用 **EXEC mask（执行掩码）** 来处理。

EXEC mask 是一个位掩码，每个 bit 对应 wavefront 里的一个线程（lane）：bit 为 1 表示该线程“活跃”，当前指令对它生效；bit 为 0 表示该线程“休眠”，当前指令对它不生效（当 NOP 处理）。

当遇到分支时，硬件会：
1. 先按“所有线程都走 if 分支”执行一遍，不满足条件的线程被 EXEC mask 屏蔽；
2. 再按“所有线程都走 else 分支”执行一遍，不满足条件的线程继续被屏蔽；
3. 两个分支都执行完后，汇合继续往下执行。

ASCII 图示（分支偏差处理）：

```
代码：if (a > 0) { x = 1; } else { x = 2; }

Wavefront 中 4 个线程：a = [5, -3, 0, 8]

第1阶段（执行 if 分支 x=1）：
EXEC = [1, 0, 0, 1]   只有 a>0 的线程（第0、3个）生效
   L0: x=1  ✓   L1: 跳过   L2: 跳过   L3: x=1  ✓

第2阶段（执行 else 分支 x=2）：
EXEC = [0, 1, 1, 0]   只有 a<=0 的线程（第1、2个）生效
   L0: 跳过   L1: x=2  ✓   L2: x=2  ✓   L3: 跳过

结果：两个分支都执行了一遍，只是每次只有一部分线程在干活
```

> 面试要点：EXEC mask 是按位掩码，控制 wavefront 里哪些线程参与当前指令。分支偏差时，硬件按“两个分支都执行一遍，只是每次只激活相应线程”的方式处理，导致部分周期浪费。

## Q7. 分支偏差对性能有什么影响？怎么避免？

**回答**

分支偏差（branch divergence）指 wavefront 内不同线程走不同分支的情况。由于两个分支都要“过一遍”，如果 8 个线程里只有 1 个走 if 分支、7 个走 else 分支，那么 if 分支那一轮只有 1/8 的线程在干活，其余 7/8 的周期在浪费。

**影响**：分支偏差越严重，GPU 的利用率越低，实际吞吐量越接近串行执行。

**避免方法：**

1. **尽量让 wavefront 内的线程走相同分支**：把相似的数据归到同一个 wavefront 里处理，减少同一 wavefront 内的分支差异。
2. **用 predication（谓词）代替分支**：对简单的条件赋值，用算术表达式或位运算代替 `if-else`，避免产生分支。
3. **把复杂分支拆成多个 kernel**：让每个 kernel 只处理一种情况，避免单个 kernel 里混杂太多分支。

大白话比喻：分支偏差就像一队士兵，一半人被命令“向左转”，一半人被命令“向右转”，军官只能先让“向左转”那半个人转（另一半站着不动），再让“向右转”那半个人转（第一半又站着不动），效率大打折扣。

> 面试要点：分支偏差会导致 wavefront 里部分线程空闲，降低利用率。避免方法：让同一 wavefront 里线程走相同分支、用谓词/算术表达式代替简单分支、把复杂分支拆成多个 kernel。

## Q8. 什么是 SGPR/VGPR/AGPR？

**回答**

GPU 里的寄存器比 CPU 复杂，分成了几类，对应不同的用途：

| 寄存器 | 全称 | 作用域 | 大白话 |
|--------|------|--------|--------|
| **SGPR** | Scalar General Purpose Register | 每个 wavefront 一份 | 存波前内共享的标量值，比如循环次数、基础指针、所有线程都一样的值 |
| **VGPR** | Vector General Purpose Register | 每个 lane 一份 | 存每个线程私有的数据，比如该线程要处理的数组元素 |
| **AGPR** | Accumulator VGPR | 每个 lane 一份 | 专门用于矩阵乘累加（MFMA）的累加器，存中间计算结果 |

可以把 SGPR 想象成“全班同学共用的公告板”，上面写的东西所有人都能看（比如今天的日期）；VGPR 想象成“每个学生自己的笔记本”，每个人记自己的内容；AGPR 则是“专门用来做长加法的草稿纸”，用于矩阵运算中的累加。

> 面试要点：SGPR 是波前内共享的标量寄存器，VGPR 是每个 lane 私有的向量寄存器，AGPR 是用于矩阵乘累加的累加器寄存器。

## Q9. 寄存器压力怎么影响占用率？

**回答**

寄存器是 GPU 里非常宝贵的资源，每个 CU 的寄存器文件大小是固定的。如果你的 kernel 用了太多 VGPR，那么一个 CU 能同时驻留（resident）的 wavefront 数量就会减少，因为寄存器不够了，放不下更多的 wavefront。

能同时驻留的 wavefront 越少，硬件就越难在某个 wavefront 等内存数据时“切换”去执行另一个 wavefront，从而失去了隐藏内存延迟的机会。这就是“寄存器压力”对占用率的影响。

举个例子（简化版）：

```
CU 寄存器总量：假设可容纳 256 个 wavefront 的 VGPR 总量

情况A：每个 wavefront 用 64 个 VGPR ──▶ 能驻留 4 个 wavefront
情况B：每个 wavefront 用 256 个 VGPR ──▶ 只能驻留 1 个 wavefront

情况A 的占用率更高，能更好地隐藏内存延迟。
```

> 面试要点：寄存器压力越大（每个 wavefront 用的 VGPR 越多），一个 CU 能同时驻留的 wavefront 越少，占用率越低，隐藏内存延迟的能力越差。

## Q10. 什么是占用率（occupancy）？怎么计算？

**回答**

占用率（occupancy）是指：**某一时刻，CU 上实际驻留的 wavefront 数量，除以硬件理论上最多能驻留的 wavefront 数量。**

它不是“GPU 繁忙程度”的直接度量，而是“硬件资源被多充分利用”的度量。占用率低，不一定代表程序慢，但通常意味着硬件没有被充分利用，有优化空间。

占用率受三个主要因素限制（取最小值）：

1. **寄存器限制**：每个 wavefront 用的 VGPR/SGPR 太多，放不下多个 wavefront。
2. **LDS 限制**：每个 work-group 用的 LDS 太多，放不下多个 work-group。
3. **wave slot 限制**：每个 CU 的硬件波前槽位数固定（比如最多 40 个 wavefront）。

计算公式（简化版）：

```
occupancy_per_CU = min(
    寄存器允许的 wavefront 数,
    LDS 允许的 wavefront 数,
    硬件 wave slot 上限
) / 硬件 wave slot 上限
```

> 面试要点：占用率＝实际驻留 wavefront 数 / 硬件理论最大驻留 wavefront 数。受寄存器、LDS、wave slot 三者限制，取最小值。占用率高不代表一定快，但低占用率通常有优化空间。

## Q11. GPU 的内存层级有哪些？

**回答**

GPU 的内存不是一块均匀的存储，而是按速度和距离分层的。从近到远、从快到慢：

```
寄存器（SGPR/VGPR/AGPR）  ── 最快，每个线程/波前私有
      │
      ▼
LDS（Local Data Share）  ── 快，work-group 内共享，片上 SRAM
      │
      ▼
L0 缓存 ──▶ L1 缓存 ──▶ L2 缓存 ──▶ 显存（VRAM/HBM）  ── 最慢，离 ALU 最远
  (每CU)     (WGP共享)    (全局共享)      (GDDR6/HBM)
```

用大白话比喻，GPU 的内存层级像一个人的记忆系统：

- **寄存器**：当下正在想的念头，瞬间想起来，但容量极小。
- **LDS**：桌上的草稿纸，桌边的同事（同一 work-group）都能看，速度很快。
- **L0/L1/L2 缓存**：书架上随手可及的书，比草稿纸慢一点，但比去图书馆快。
- **显存（VRAM）**：图书馆里的书，要走很远才能拿回来，速度最慢，但容量最大。

> 面试要点：GPU 内存层级从快到慢、从近到远：寄存器→LDS→L0缓存→L1缓存→L2缓存→显存。越靠近 ALU 越快但容量越小，越远容量越大但越慢。

## Q12. 什么是 LDS（局部数据共享）？和全局内存有什么区别？

**回答**

LDS（Local Data Share，局部数据共享）是 GPU 芯片内部的一块高速片上 SRAM，专门供同一个 work-group 里的 wavefront 之间共享数据。它比全局内存（显存）快一个数量级，但容量小，且只在 work-group 内可见。

| 维度 | LDS | 全局内存（显存） |
|------|-----|----------------|
| 位置 | 芯片内部 SRAM | 芯片外部 GDDR6/HBM |
| 速度 | 很快（约是全局内存 10 倍以上） | 较慢 |
| 容量 | 小（每 CU 几十 KB～百 KB） | 大（GB 级） |
| 可见范围 | 同一个 work-group 内 | 所有线程都能访问 |
| 用途 | work-group 内数据共享、中间结果缓存 | 存放大模型权重、大数组、输入输出 |

ASCII 图示：

```
全局内存（显存，慢，大）                      LDS（快，小，work-group内共享）
┌─────────────────┐                         ┌─────────┐
│ 模型权重        │                         │ work-group A 的共享数据 │
│ 大数组          │                         │ 中间结果缓存        │
│ 输入输出        │                         │                     │
└────────┬────────┘                         └─────────┬────────┘
         │                                   │
         ▼                                   ▼
    所有线程都能访问                     仅 work-group 内线程可见
```

> 面试要点：LDS 是芯片内部高速 SRAM，供 work-group 内共享数据，比全局内存快一个数量级但容量小；全局内存容量大但慢，所有线程可见。

## Q13. LDS 怎么在 work-item 之间共享数据？

**回答**

LDS 共享数据的典型流程分三步：

1. **写入 LDS**：每个 work-item 把自己计算出的中间结果写入 LDS 的一个位置（通常用线程的局部索引作为下标）。
2. **同步**：调用屏障（barrier），确保 work-group 里所有线程都把数据写完，没有线程跑得太快读到别人还没写的数据。
3. **读取 LDS**：每个 work-item 从 LDS 里读取其他线程写入的数据，继续计算。

用大白话比喻：LDS 就像一个公共黑板。每个学生（线程）先把自己的答案写在黑板上的指定位置，所有人写完后集体点头（同步屏障），然后每个学生再去抄别人的答案做后续计算。

Python 示例（模拟 LDS 共享+屏障，概念版）：

```python
# 模拟 LDS 共享数据的 work-group 协作（概念版，CPU 上模拟）
import threading

NUM_THREADS = 4
lds = [0] * NUM_THREADS          # 模拟 LDS，每个线程一个位置
barrier = threading.Barrier(NUM_THREADS)

def work_item(tid):
    # 步骤1：每个线程把自己的计算结果写入 LDS
    my_value = tid * 10
    lds[tid] = my_value
    print(f"线程 {tid} 写入 LDS[{tid}] = {my_value}")

    # 步骤2：屏障同步，等所有线程写完
    barrier.wait()
    print(f"线程 {tid} 通过屏障，开始读取 LDS")

    # 步骤3：读取其他线程的数据
    total = sum(lds)
    print(f"线程 {tid} 读取 LDS 总和 = {total}")

threads = [threading.Thread(target=work_item, args=(i,)) for i in range(NUM_THREADS)]
for t in threads:
    t.start()
for t in threads:
    t.join()
```

运行输出示例：
```
线程 0 写入 LDS[0] = 0
线程 1 写入 LDS[1] = 10
线程 2 写入 LDS[2] = 20
线程 3 写入 LDS[3] = 30
线程 0 通过屏障，开始读取 LDS
线程 0 读取 LDS 总和 = 60
...
```

> 面试要点：LDS 共享数据的三步＝写入 LDS→屏障同步（确保都写完）→读取 LDS。屏障是关键，没有它就会读到脏数据。

## Q14. 什么是成组访问（coalesced access）？为什么重要？

**回答**

成组访问（内存合并访问）是指 wavefront 里的多个线程访问全局内存时，如果它们访问的地址是连续的（或者说落在同一个缓存行里），硬件可以把这些访问合并成一次或少数几次内存请求，而不是每个线程单独发一次请求。

如果访问地址是散乱的（比如线程 0 访问地址 0，线程 1 访问地址 1000，线程 2 访问地址 2000），硬件就无法合并，每个线程都要单独去显存取数据，这叫“非合并访问”，会严重拖慢速度。

大白话比喻：成组访问就像“集体买团购券”，一群人要买相邻座位的电影票，票务员可以一次性打包处理；非合并访问就像“每人单独去柜台”，一个一个来，效率低得多。

ASCII 图示：

```
成组访问（好）：线程访问连续地址，合并成一次内存请求
线程0 ──▶ 地址 0   │
线程1 ──▶ 地址 1   │──▶ 一次内存请求，取 4 个连续 int
线程2 ──▶ 地址 2   │
线程3 ──▶ 地址 3   │

非合并访问（差）：线程访问散乱地址，每个都要单独请求
线程0 ──▶ 地址 0   ──▶ 请求1
线程1 ──▶ 地址 1000 ──▶ 请求2
线程2 ──▶ 地址 2000 ──▶ 请求3
线程3 ──▶ 地址 3000 ──▶ 请求4
```

> 面试要点：成组访问＝wavefront 里多个线程访问连续全局内存地址，硬件合并为一次请求，能极大提升带宽利用率。散乱访问会导致每个线程单独请求，速度慢。

## Q15. 全局内存访问怎么合并？Add-TID 寻址是什么？

**回答**

要让全局内存访问合并，最基本的原则是：**让相邻的线程访问相邻的内存地址**。

在 HIP/CUDA 编程里，最常见的写法是“Add-TID”寻址：每个线程用自己的线程 ID（tid）加上一个基础偏移，来确定自己要访问的数据。如果 tid 是连续的，访问的地址也就连续，自然能合并。

Python 示例（模拟合并 vs 不合并访问）：

```python
# 模拟全局内存访问（概念版，CPU 上演示地址模式）
NUM_THREADS = 8

# 情况1：合并访问（相邻线程访问相邻地址）
print("=== 合并访问（Add-TID，tid 连续）===")
for tid in range(NUM_THREADS):
    addr = 1000 + tid  # 基址 1000 + 线程 ID，地址连续
    print(f"线程 {tid:2d} 访问地址 {addr}")

# 情况2：非合并访问（相邻线程访问散乱地址）
print("\n=== 非合并访问（stride 大，地址散乱）===")
stride = 100
for tid in range(NUM_THREADS):
    addr = 1000 + tid * stride  # 地址跳跃很大
    print(f"线程 {tid:2d} 访问地址 {addr}")
```

输出示例：
```
=== 合并访问（Add-TID，tid 连续）===
线程  0 访问地址 1000
线程  1 访问地址 1001
线程  2 访问地址 1002
线程  3 访问地址 1003
...

=== 非合并访问（stride 大，地址散乱）===
线程  0 访问地址 1000
线程  1 访问地址 1100
线程  2 访问地址 1200
线程  3 访问地址 1300
...
```

> 面试要点：全局内存访问合并的核心原则＝相邻线程访问相邻地址。Add-TID 寻址（基址 + 线程 ID）是最常见的合并写法，能让 wavefront 的访问被硬件合并为少数几次内存请求。

## Q16. 什么是 LDS bank conflict？怎么避免？

**回答**

LDS 虽然快，但它内部被分成很多个“银行”（bank）。同一时刻，如果多个线程试图访问**同一个银行**里的不同数据，这些访问就得排队串行执行，这就叫 **bank conflict（银行冲突）**，会拖慢 LDS 访问速度。

用大白话比喻：LDS 像一个有多个柜员窗口的银行。如果每个客户都去不同的窗口，大家可以同时办理业务；如果多个客户都挤在同一个窗口前，后面的人就得排队。

**避免方法：**

1. **让相邻线程访问相邻的 LDS 地址**：这样它们会落在不同的银行，避免冲突。
2. **避免 stride 为银行数倍数的访问**：比如如果 LDS 有 32 个银行，线程 i 访问地址 `i * 32`，那所有线程都会落在同一个银行，造成最严重的冲突。
3. **填充（padding）**：在数组每行末尾多留几个空位，打破规律性的冲突。

ASCII 图示（bank conflict）：

```
LDS 有 4 个银行（Bank 0~3），地址按 4 循环分配：

地址：  0   1   2   3   4   5   6   7
银行： [0] [1] [2] [3] [0] [1] [2] [3]

无冲突：线程0→地址0(Bank0)，线程1→地址1(Bank1)，线程2→地址2(Bank2)，线程3→地址3(Bank3)
        4个线程同时访问，4个银行并行，一次完成

有冲突：线程0→地址0(Bank0)，线程1→地址4(Bank0)，线程2→地址8(Bank0)，线程3→地址12(Bank0)
        4个线程都访问 Bank0，必须排队串行，4次才完成
```

> 面试要点：LDS bank conflict 是指多个线程同时访问同一个 LDS 银行，导致串行化。避免方法：相邻线程访问相邻地址、避免 stride 等于银行数倍数的访问、必要时做 padding 填充。

## Q17. 标量内存和向量内存有什么区别？

**回答**

GPU 里访存分为标量访存（scalar memory）和向量访存（vector memory），对应两类指令和缓存：

| 维度 | 标量内存访存 | 向量内存访存 |
|------|-------------|-------------|
| 使用寄存器 | SGPR（标量寄存器） | VGPR（向量寄存器） |
| 访存粒度 | 每次访存一个标量值（整个 wavefront 共用同一个值） | 每个 lane 访存一个值，wavefront 里每个线程不同 |
| 典型用途 | 循环计数、基础指针、所有线程共用的常量 | 数组元素、每个线程私有的数据 |
| 缓存 | 标量 L0/L1 缓存 | 向量 L0/L1/L2 缓存 |

大白话：标量内存就像“老师黑板上写一个数字，全班同学都看同一个”；向量内存就像“每个学生桌上有自己的本子，上面记的数字不一样”。

> 面试要点：标量内存访存用 SGPR，整个 wavefront 共用一个值；向量内存访存用 VGPR，每个 lane 有自己的值。标量用于循环计数、基础指针；向量用于数组元素等私有数据。

## Q18. work-group 和 work-item 是什么？怎么映射到 GPU 硬件？

**回答**

在 HIP/OpenCL 编程模型里：

- **work-item（工作项）**：最小的执行单元，对应一条线程。它负责处理一小块数据。
- **work-group（工作组）**：一组 work-item 的集合，它们能通过 LDS 共享数据、通过屏障同步。

work-group 映射到 GPU 硬件上，通常对应一个或多个 wavefront，驻留在同一个 CU（或同一个 WGP）里。

ASCII 图示（映射关系）：

```
用户视角（编程模型）           硬件视角（执行）
┌─────────────┐                 ┌─────────────┐
│ work-group 0  │               │ CU 0        │
│   wi 0,1,2,3  │───────────────▶ wavefront 0 │
│   wi 4,5,6,7  │               │ wavefront 1 │
└─────────────┘                 └─────────────┘
│ work-group 1  │               │ CU 1        │
│   ...         │───────────────▶ wavefront 2 │
└─────────────┘                 └─────────────┘
```

> 面试要点：work-item 是最小执行单元（对应一条线程），work-group 是一组能共享 LDS、能屏障同步的 work-item。work-group 映射到 GPU 上通常驻留在同一个 CU 里，对应一个或多个 wavefront。

## Q19. dispatch 到底做了什么？

**回答**

dispatch（调度/下发）是指把 kernel 提交给 GPU 执行的过程。当你调用 `kernel<<<grid, block>>>`（HIP/CUDA 语法）时，后面发生了什么：

1. **命令处理器（CP）接收任务**：CPU 端提交 kernel 启动请求，GPU 的命令处理器收到。
2. **创建 wavefront**：CP 把 work-group 拆成一个个 wavefront，根据 work-group 的大小和 wavefront 大小（wave32/64）计算需要多少个 wavefront。
3. **分配资源**：为每个 wavefront 分配寄存器（SGPR/VGPR）和 LDS 空间，检查占用率是否超限。
4. **分发到 CU/SIMD**：把 wavefront 分发到空闲的 CU 和 SIMD 上去执行。
5. **执行并回写**：wavefront 在 SIMD 上执行指令，结果写回显存，最后通知 CPU 完成。

ASCII 图示：

```
CPU: kernel<<<grid, block>>>(...)
     │
     ▼
┌─────────────┐
│ 命令处理器 CP │────▶ 接收 kernel 启动请求
└──────┬──────┘
       │
       ▼
┌─────────────┐
│ 拆成 wavefront│────▶ 根据 work-group 大小算出需要多少个 wavefront
└──────┬──────┘
       │
       ▼
┌─────────────┐
│ 分配寄存器+LDS │────▶ 检查资源够不够（占用率）
└──────┬──────┘
       │
       ▼
┌─────────────┐
│ 分发到 CU/SIMD│────▶ 送到空闲计算单元执行
└──────┬──────┘
       │
       ▼
   结果写回显存，通知 CPU 完成
```

> 面试要点：dispatch 是把 kernel 下发到 GPU 执行的过程，包括 CP 接收、拆成 wavefront、分配寄存器和 LDS、分发到 CU/SIMD、执行并回写结果。

## Q20. HIP 里的 grid、block、thread 怎么映射到 GPU 的 wavefront、SIMD、CU？

**回答**

HIP 的线程层级命名和 CUDA 很像，映射关系如下：

| HIP 概念 | 含义 | 对应 GPU 硬件概念 |
|----------|------|------------------|
| thread | 最小执行单元 | wavefront 里的一个 lane（线程） |
| block | 一组 thread | 一个或多个 wavefront，驻留在同一个 CU |
| grid | 所有 block 的集合 | 整个 kernel 的执行范围，分发到多个 CU |

具体映射：
- 一个 `block`（work-group）里的线程会被拆成一个或多个 `wavefront`，这些 wavefront 驻留在同一个 `CU` 里。
- 一个 `grid` 里的多个 `block` 会被分发到不同的 `CU` 上并行执行。

ASCII 图示：

```
grid（所有 block）
│
├─ block 0 ──▶ wavefront 0 ──▶ CU 0
│            │
│            └─ wavefront 1 ──▶ CU 0（同一个 CU 里可能有多个 wavefront）
│
├─ block 1 ──▶ wavefront 2 ──▶ CU 1
│
└─ block 2 ──▶ wavefront 3 ──▶ CU 2
```

> 面试要点：HIP 的 thread 对应 wavefront 里的 lane，block 对应一个或多个 wavefront（同一个 CU），grid 对应分发到多个 CU 的整个执行范围。

## Q21. 怎么提高占用率？（减少寄存器、减少 LDS 使用、调整块大小）

**回答**

提高占用率的核心思路是：**让每个 wavefront 用更少的资源，这样一个 CU 能同时驻留更多的 wavefront，在等内存时切换去执行别的。**

具体做法：

1. **减少寄存器使用**：把不需要每个线程私有的值改成 SGPR（共用），或者简化算术表达式，降低 VGPR 数量。
2. **减少 LDS 使用**：如果每个 work-group 用的 LDS 太少，能放下更多 work-group，占用率就高。
3. **调整 block 大小**：block 太小（比如只有 32 个线程）可能浪费 wavefront 槽位；block 太大可能占用太多资源。通常选波前大小的倍数（如 256、512）。
4. **让 work-group 大小匹配 wavefront**：如果 work-group 大小是 wavefront 大小的整数倍，能减少浪费。

ASCII 图示（减少寄存器提高占用率）：

```
每个 wavefront 用 256 个 VGPR ──▶ CU 只能放 1 个 wavefront ──▶ 占用率低
      │
      ▼（优化：简化代码，减少 VGPR）
每个 wavefront 用 64 个 VGPR ──▶ CU 能放 4 个 wavefront ──▶ 占用率高
```

> 面试要点：提高占用率＝减少每个 wavefront 的寄存器和 LDS 使用，让一个 CU 能同时驻留更多 wavefront；调整 block 大小为 wavefront 倍数；在等内存时切换执行其他 wavefront，隐藏延迟。

## Q22. GPU 和 CPU 编程模型有什么根本区别？

**回答**

| 维度 | CPU 编程模型 | GPU 编程模型 |
|------|-------------|-------------|
| 执行单元 | 线程独立，各有 PC | wavefront 锁步，共享 PC |
| 控制流 | 复杂分支、循环、递归都擅长 | 分支偏差代价高，偏向数据并行 |
| 内存访问 | 缓存友好、随机访问较快 | 喜欢连续、成组访问，随机访问慢 |
| 核心数 | 少（几个到几十个） | 多（成千上万个核心） |
| 适合场景 | 逻辑复杂、串行依赖强的任务 | 数据量大、计算重复的任务（矩阵乘、卷积） |

大白话：CPU 像一个大学教授，擅长思考复杂问题；GPU 像一千个小学生，每个只会做加法，但一千个人一起加，速度极快。

> 面试要点：CPU 和 GPU 编程模型根本区别＝CPU 线程独立、擅长复杂逻辑；GPU wavefront 锁步、擅长数据并行、喜欢连续访存、核心数多。大模型的矩阵运算正适合 GPU。

## Q23. 什么是波前（wavefront）的调度？SPI 怎么分发？

**回答**

SPI（Schedule Processor，调度处理器）是 GPU 负责把 wavefront 分发到 CU 的硬件模块。它的工作就像工厂的调度员：把任务（wavefront）分配给空闲的工作站（CU）。

调度不是随机的，它会考虑：
- 哪个 CU 有空闲的 wave slot；
- 该 CU 的寄存器和 LDS 是否够分配给新 wavefront；
- 工作负载在多个 CU 之间是否均衡。

一旦 wavefront 被分发到 CU，它就会在 SIMD 上执行，直到完成或被挂起（比如等内存数据）。此时 SPI 可以把另一个 wavefront 调度到同一个 CU 上，从而实现延迟隐藏。

> 面试要点：SPI 是 GPU 的调度模块，负责把 wavefront 分发到空闲 CU。调度会考虑 wave slot 空闲情况和资源（寄存器/LDS）是否足够，波前调度是实现延迟隐藏的关键。

## Q24. 向量内存和标量内存怎么选？

**回答**

选哪种访存，取决于你的数据是不是“所有线程都一样”：

- **所有线程读同一个值**（比如循环上限、基础指针、常数）：用**标量内存**（SGPR），只需要广播一次，所有线程共用。
- **每个线程读不同的值**（比如数组 `a[tid]`、每个线程自己的中间结果）：用**向量内存**（VGPR），每个 lane 独立访存。

混用也很常见：先用 SGPR 存基础指针，再用 VGPR 存每个线程的偏移，最后合成最终地址访问全局内存。

ASCII 图示：

```
标量内存（SGPR，全班共用）：        向量内存（VGPR，每人一个）：
      公告板                        每个学生的笔记本
   ┌─────────┐                  ┌─────────┐
   │  基址=1000│                  │ L0: 1000│
   │         │                  │ L1: 1001│
   │  所有线程看同一个值  │      │ L2: 1002│
   └─────────┘                  │ L3: 1003│
                                └─────────┘
```

> 面试要点：所有线程读同一个值用标量内存（SGPR），每个线程读不同值用向量内存（VGPR）。实际编程中常混合用：SGPR 存基址，VGPR 存偏移，合成最终地址。

## Q25. 缓存（L0/L1/L2）在 GPU 访存里起什么作用？

**回答**

GPU 的缓存层级（L0/L1/L2）是为了弥补“算力快、显存慢”的矛盾。算术逻辑单元（ALU）算得飞快，但每次去显存取数据要等几百个周期，ALU 就会空等。缓存把常用数据留在靠近 ALU 的地方，减少去显存的次数。

- **L0 缓存**：每个 CU 私有，最快，容量最小。
- **L1 缓存**：WGP 内多个 CU 共享，速度次之。
- **L2 缓存**：整个 GPU 共享，最大，速度慢于 L1 但快于显存。

访存时，先查 L0，没命中查 L1，再查 L2，最后才去显存。命中率越高，程序越快。

> 面试要点：L0/L1/L2 缓存按距离 ALU 从近到远、从快到慢分层，用于缓存常用数据，减少去慢速显存的次数，提高访存效率。L0 每 CU 私有，L1 WGP 共享，L2 全 GPU 共享。

## Q26. 内存一致性模型在 GPU 里怎么理解？（s_wait_loadcnt 等）

**回答**

GPU 是并行执行的，多个 wavefront 可能同时读写同一块内存。如果不加控制，一个 wavefront 写完数据，另一个 wavefront 可能还没看到，这就是内存一致性问题。

为了解决这个问题，GPU 提供了屏障/等待指令，常见的有：

- `s_wait_loadcnt 0`：等待所有标量读取完成。
- `s_wait_storecnt 0`：等待所有标量写入完成。
- `s_wait_dscnt 0`：等待所有 LDS 操作完成。

这些指令告诉 GPU：“在继续执行下一条指令之前，先确保前面的内存操作都做完了。”

大白话：就像工厂流水线，工人 A 把零件放在传送带上，工人 B 要拿这个零件继续加工。如果 B 没等 A 放好就拿，就会拿空手。`s_wait_*` 指令就是那个“等 A 放好”的信号。

> 面试要点：GPU 内存一致性靠 `s_wait_loadcnt`/`s_wait_storecnt`/`s_wait_dscnt` 等屏障指令保证，确保前面的读写操作完成后再继续，避免多个 wavefront 并发访问同一内存时出现脏数据。

## Q27. 为什么要关心内存访问模式？（带宽利用率、70-90% vs 5-15%）

**回答**

内存访问模式决定了显存带宽能用多少。这是 GPU 性能优化里最重要的因素之一。

实测经验法则：
- **合并访问（连续地址）**：能达到峰值带宽的 70%～90%。
- **随机/散乱访问**：可能只有峰值带宽的 5%～15%。

差距巨大，因为散乱访问导致硬件无法合并请求，每次只能取很少的数据，大部分带宽被浪费在传输无关数据上。

> 面试要点：内存访问模式决定带宽利用率。合并访问可达峰值带宽 70%～90%，随机散乱访问可能只有 5%～15%。优化访存模式是提升 GPU 程序性能的最重要手段之一。

## Q28. HIP 和 CUDA 在线程层级命名上有什么映射？

**回答**

HIP 的线程层级命名和 CUDA 几乎一一对应，方便 CUDA 开发者迁移：

| CUDA 概念 | HIP 概念 | 对应硬件 |
|-----------|----------|----------|
| thread | thread | wavefront lane |
| block | block | work-group（1～多个 wavefront，驻留同一个 CU） |
| grid | grid | 整个 kernel 调用范围（多个 CU） |
| warp | wavefront | SIMD 执行的锁步线程组 |
| threadIdx.x | hipThreadIdx_x | lane 在 wavefront 里的索引 |
| blockIdx.x | hipBlockIdx_x | work-group 在 grid 里的索引 |
| blockDim.x | hipBlockDim_x | work-group 里的线程数 |

> 面试要点：HIP 和 CUDA 的线程层级命名几乎一一对应，thread 对应 lane，block 对应 work-group（wavefront 集合），grid 对应整个调用范围。CUDA 迁移到 HIP 时，把 `cuda` 前缀改成 `hip` 即可。

## Q29. 本章小结：GPU 体系结构核心知识点清单

**回答**

本章讲了 GPU 从硬件到编程模型的核心知识。如果只记住一张清单，那就是下面这条：

```
GPU 体系结构核心清单
┌─────────────────────────────────────────────────────────┐
│ 1. 硬件层级：SA → WGP → CU → SIMD，层层嵌套              │
│ 2. wavefront：AMD 版 warp，锁步执行，共享程序计数器      │
│ 3. wave32/wave64：32 或 64 线程，不要硬编码大小         │
│ 4. EXEC mask：分支偏差时控制哪些线程参与当前指令         │
│ 5. 寄存器：SGPR（波前共用）、VGPR（每线程私有）、AGPR    │
│ 6. 占用率：实际驻留 wavefront / 理论最大值，受寄存器/LDS │
│    /wave slot 限制                                      │
│ 7. 内存层级：寄存器 → LDS → L0/L1/L2 缓存 → 显存         │
│ 8. LDS：work-group 内高速共享，需屏障同步                │
│ 9. 成组访问：相邻线程访问相邻地址，硬件合并请求          │
│ 10. LDS bank conflict：多线程访问同一银行导致串行化      │
│ 11. work-item/work-item/block/grid：HIP 线程层级映射     │
│ 12. dispatch：把 kernel 拆成 wavefront 分发到 CU 执行    │
└─────────────────────────────────────────────────────────┘
```

一句话总结：**GPU 的本质是大规模数据并行，wavefront 是执行单元，LDS 是共享工作区，成组访问和占用率是性能的两个关键杠杆。**

> 面试要点：本章核心＝硬件层级 SA/WGP/CU/SIMD、wavefront 锁步执行、EXEC mask 分支处理、三类寄存器、占用率三要素、内存层级、LDS 共享与银行冲突、成组访问、HIP 线程层级映射、dispatch 流程。
