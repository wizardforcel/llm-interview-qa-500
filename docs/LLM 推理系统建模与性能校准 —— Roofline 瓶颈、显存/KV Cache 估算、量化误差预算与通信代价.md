## Q1. 什么是 Roofline 模型？它用来判断什么？

**回答**

Roofline 模型（屋顶图）是一种性能分析可视化模型，用来判断一个程序是**受计算能力限制（计算密集型）**还是**受内存带宽限制（存储密集型）**，以及还有多少优化空间。

它的横轴是 **算术强度（Arithmetic Intensity, AI）**，单位是 FLOP/Byte（每搬运一个字节数据做多少次浮点运算）；纵轴是 **可达性能（Attainable Performance）**，单位是 GFLOP/s。

图上有两条“屋顶”：
1. **斜线**：性能 = 算术强度 × 峰值内存带宽。算术强度低的时候，性能沿这条斜线上升，说明受内存带宽限制。
2. **水平线**：性能 = 峰值算力。算术强度高的时候，性能被这条水平线封顶，说明受计算能力限制。

两条线的交点叫 **拐点（Knee，也叫 Machine Balance 机器平衡点）**，是从“内存受限”转为“计算受限”的临界算术强度。

大白话比喻：Roofline 像一栋房子的屋顶。你站在屋外，算术强度决定你站得离房子多近；性能决定你能爬多高。斜面那边是“搬运工”（搬数据太忙，没力气干活），平顶那边是“架子工”（干活快，但架子本身高度有上限）。

ASCII 图示：

```
性能 (GFLOP/s)
   ▲
   │  ┌─────────────────┐  ← 峰值算力（水平屋顶）
   │  │                 │
   │  │                 │
   │  │                 │
   │  │                 │
   │  │                 │
   │  │                /│
   │  │               / │
   │  │              /  │ ← 斜线：峰值带宽 × 算术强度
   │  │             /   │
   │  │            /     │
   │  │           /       │
   │  │          /        │
   │  │         /         │
   │  │        /          │
   │  │       /           │
   │  │      /            │
   │  │     /             │
   │  │    /              │
   │  │   /               │
   │  │  /                │
   │  │ /                 │
   │  │/                  │
   └──┬───────────────────┴──▶ 算术强度 (FLOP/Byte)
      │
      拐点（Machine Balance）
      左边：存储密集型（受带宽限制）
      右边：计算密集型（受算力限制）
```

> 面试要点：Roofline 模型用算术强度（横轴）和可达性能（纵轴）作图，由“峰值带宽斜线”和“峰值算力水平线”组成。交点是拐点，左边是内存受限，右边是计算受限。它用来判断程序瓶颈在哪里，还有多少优化空间。

## Q2. 算术强度（Arithmetic Intensity）怎么算？向量加法和 GEMM 分别是多少？

**回答**

算术强度（Arithmetic Intensity, AI）是指 **每搬运一个字节数据，做多少次浮点运算**，单位是 FLOP/Byte。

公式：
```
算术强度 AI = 浮点运算次数 (FLOPs) / 数据搬运量 (Bytes)
```

**向量加法 `c[i] = a[i] + b[i]`**：
- 每个元素：1 次加法（1 FLOP）
- 数据搬运：读 `a[i]`（4 字节）+ 读 `b[i]`（4 字节）+ 写 `c[i]`（4 字节）= 12 字节
- AI = 1 / 12 ≈ **0.083 FLOP/Byte**

**GEMM（矩阵乘法 `C = A × B`，大方阵）**：
- 每个输出元素需要 K 次乘加（2K FLOP），读取 A 的一行和 B 的一列，但通过分块可以在片上反复复用。
- 理想情况下，大方阵的 AI 可达 `2n / (3s)`（n 是矩阵阶数，s 是每个元素字节数）。n 越大，AI 越高。例如 FP32 的 n=128 时 AI ≈ 21.3，n=2048 时 AI ≈ 341.3。

0.083 远小于大多数 GPU 的拐点（通常几十～上百 FLOP/Byte），所以向量加法是典型的**存储密集型**；大矩阵乘法则是典型的**计算密集型**。

> 面试要点：算术强度 = 浮点运算次数 ÷ 数据搬运量（FLOP/Byte）。向量加法 AI ≈ 0.083（存储密集型）；大矩阵乘法 AI 很高（计算密集型）。AI 越高，越不容易受内存带宽限制。

## Q3. 什么是峰值算力（Peak FLOPS）和峰值带宽（Peak Bandwidth）？

**回答**

- **峰值算力（Peak FLOPS）**：GPU 在理想情况下，每秒能做的最大浮点运算次数。由 GPU 架构、核心数、频率决定，是“算力天花板”。
- **峰值带宽（Peak Bandwidth）**：GPU 显存每秒能传输的最大数据量（如 1.5 TB/s）。由显存类型（GDDR6/HBM）和位宽决定，是“搬运天花板”。

这两个值决定了 Roofline 图的水平线高度和斜线斜率。它们通常可以在 GPU 的官方规格书里找到，或者通过经验测量工具（如 Empirical Roofline Toolkit ERT）测得。

> 面试要点：峰值算力是 GPU 每秒最大浮点运算数（水平屋顶）；峰值带宽是显存每秒最大传输量（决定斜线斜率）。两者都来自硬件规格或实测，是 Roofline 图的两条基准线。

## Q4. 什么是“计算密集型”和“存储密集型”？如何在 Roofline 图上区分？

**回答**

- **存储密集型（Memory-bound）**：算术强度低，位于拐点**左边**。程序大部分时间在等数据从显存搬运，算力闲着。典型例子：向量加法、归约、Softmax。
- **计算密集型（Compute-bound）**：算术强度高，位于拐点**右边**。程序大部分时间在算，内存带宽闲着。典型例子：大矩阵乘法（GEMM）。

判断口径：把你的算子的算术强度算出来，和拐点比一下。小于拐点就是存储密集型，大于拐点就是计算密集型。

ASCII 图示：

```
性能
   ▲
   │  ┌─────────────────┐  ← 计算密集型（右边，受算力限制）
   │  │      ● GEMM      │
   │  │        ●          │
   │  │      ●            │
   │  │    ●              │
   │  │   ●               │
   │  │  ●                │
   │  │ ●                 │
   │  ●                   │
   │ ●   ●  向量加法      │  ← 存储密集型（左边，受带宽限制）
   │●     ●               │
   └──┬──┬───────────────┴──▶ 算术强度
      │  │
      │  拐点（Machine Balance）
      │
   存储密集型 ←        → 计算密集型
```

> 面试要点：算术强度小于拐点 = 存储密集型（左边，受带宽限制）；算术强度大于拐点 = 计算密集型（右边，受算力限制）。向量加法是典型存储密集型，大矩阵乘法是典型计算密集型。

## Q5. 在 Roofline 图上，怎么判断一个 kernel 是受计算限制还是受内存限制？

**回答**

把你的 kernel 在 Roofline 图上画一个点（横坐标 = 它的算术强度，纵坐标 = 它的实际测得性能）：

- 如果点在 **斜线下方** 或 **贴近斜线**：说明它受**内存带宽限制**。优化方向是减少数据搬运、提高缓存命中、合并访存。
- 如果点在 **水平线下方** 或 **贴近水平线**：说明它受**计算能力限制**。优化方向是提高指令效率、向量化、利用张量核心、减少分支。
- 如果点远低于两条线：说明除了带宽和算力，还有其他瓶颈（如占用率低、分支偏差严重、同步开销大）。

> 面试要点：在 Roofline 图上把 kernel 打个点：在斜线附近 = 受内存带宽限制；在水平线附近 = 受计算能力限制；远低于两条线 = 还有其他瓶颈（占用率、同步、分支）。

## Q6. 第一次真机 Profile 与离线模拟有什么区别？为什么要“校准”？

**回答**

离线模拟（如用公式手算）只能给出“理论上限”，它基于理想假设：所有数据都完美命中缓存、所有线程完美均衡、没有任何操作系统干扰。现实中，GPU 时钟频率会波动（热节流）、缓存命中率不完美、操作系统有调度开销、内存控制器有争用。

第一次真机 Profile 是指：在真实硬件上跑一次实际工作负载，用工具（如 rocprofv3、Nsight Compute）采集真实的执行时间、硬件计数器（VALUBusy、占用率、内存带宽利用率等）。

**性能校准**是指：用真实测量结果来修正离线模型的参数。例如，离线模型预测峰值算力是 40 TFLOPS，但真实跑出来只有 30 TFLOPS，那么效率参数（MFU，Model FLOPs Utilization）就要调为 30/40 = 75%。校准后的模型才能用于可信的容量规划和性能预测。

> 面试要点：离线模拟给“理论上限”，第一次真机 Profile 测“真实耗时”，校准是用真实数据修正模型参数（如 MFU），使模型预测与真实测量一致，才能用于容量规划。

## Q7. 什么是 MFU（Model FLOPs Utilization）？怎么算？

**回答**

MFU（Model FLOPs Utilization，模型浮点运算利用率）是指实际达到的浮点运算速度占峰值算力的比例。

公式：
```
MFU = 实际吞吐量 (FLOP/s) / 峰值算力 (Peak FLOPS)
```

或者对于 LLM 推理，更常用的写法是：
```
MFU = (每 token 的浮点运算量 × 吞吐量 tokens/s) / 峰值算力
```

例如，某 70B 模型每 token 需要约 2×70B = 140 GFLOP（前向传播约 2×参数量），如果峰值算力是 100 TFLOPS，测得吞吐量是 1000 token/s，那么：
```
实际 FLOP/s = 140 × 10⁹ × 1000 = 140 × 10¹² = 140 TFLOPS
```
这就超过峰值了，说明参数或吞吐量有问题；如果测得是 35 TFLOPS，那么 MFU = 35/100 = 35%。

MFU 越高，说明硬件计算能力被越充分地利用。LLM 推理的 decode 阶段通常 MFU 很低（因为受内存带宽限制），prefill 阶段 MFU 通常较高。

> 面试要点：MFU = 实际浮点运算速度 / 峰值算力。LLM 推理中可用 `(参数量 × 2 × 吞吐量) / 峰值算力` 估算。它衡量硬件计算能力被充分利用的程度，decode 阶段通常 MFU 很低（受内存带宽限制）。

## Q8. LLM 推理分哪两个阶段？它们的瓶颈特征有什么不同？

**回答**

LLM 推理分两个阶段：

1. **Prefill（预填充/提示处理）**：把用户的整个输入提示（Prompt）一次性全部输入模型，计算所有 token 的 KV Cache，并生成第一个输出 token。这一阶段是**批量矩阵乘法**，计算量大，可以高度并行，通常是**计算密集型（Compute-bound）**，受算力限制，Roofline 图上点在右侧水平线附近。

2. **Decode（自回归生成）**：根据已经生成的 token，逐个生成下一个 token。每次只生成一个 token，需要把之前的 KV Cache 全部从显存读出来再算一次。这一阶段是**内存带宽受限（Memory-bound）**，因为每次只算很少的量，却要把整个模型权重和 KV Cache 从显存读一遍，Roofline 图上点在左侧斜线附近。

ASCII 图示（两阶段在 Roofline 上的位置）：

```
性能
   ▲
   │  ┌─────────────────┐  ← 峰值算力
   │  │        ● Prefill │  ← 计算密集型，靠近水平线
   │  │         ●        │
   │  │        ●         │
   │  │       ●          │
   │  │      ●           │
   │  │     ●            │
   │  │    ●             │
   │  │   ●              │
   │  │  ●               │
   │  │ ●   ● Decode     │  ← 存储密集型，靠近斜线
   │  ●●     ●           │
   └──┬──┬───────────────┴──▶ 算术强度
      │  │
      │  拐点
```

> 面试要点：LLM 推理分 Prefill（计算密集型，批量处理整个 prompt，受算力限制）和 Decode（存储密集型，逐个生成 token，受内存带宽限制，每次要把整个 KV Cache 读一遍）两个阶段。

## Q8(续). 什么是 KV Cache？它怎么估算显存占用？

**回答**

KV Cache（键值缓存）是自回归推理中为了避免重复计算而缓存的历史信息。每生成一个新 token，模型需要把之前所有 token 的注意力键（Key）和值（Value）缓存下来，下次生成时直接复用，不用重新计算之前所有 token 的注意力。

KV Cache 的显存占用公式：
```
KV Cache 显存 = 2 × 层数 × KV 头数 × 头维度 × 序列长度 × 每元素字节数 × 批次大小
```

更详细地：
- 因子 2：Key 和 Value 各一份。
- 如果使用 GQA（分组查询注意力）或 MQA（多查询注意力），KV 头数会比查询头数少，显存占用相应减少。
- 如果使用量化（如 INT8 KV Cache），每元素字节数从 2（FP16）降到 1（INT8）甚至更低，显存占用相应减半或更多。

Python 示例（估算 KV Cache 显存）：

```python
def estimate_kv_cache_gib(num_layers, num_kv_heads, head_dim, seq_len, batch_size, bytes_per_element=2):
    """
    估算 KV Cache 显存占用（GiB）
    """
    total_elements = 2 * num_layers * num_kv_heads * head_dim * seq_len * batch_size
    total_bytes = total_elements * bytes_per_element
    return total_bytes / (1024 ** 3)

# 示例：70B 模型，80 层，8 个 KV 头（GQA），头维度 128，序列长度 4096，批次 8，FP16
kv_gib = estimate_kv_cache_gib(
    num_layers=80,
    num_kv_heads=8,
    head_dim=128,
    seq_len=4096,
    batch_size=8,
    bytes_per_element=2
)
print(f"KV Cache 显存占用：{kv_gib:.2f} GiB")
# 输出：KV Cache 显存占用：16.38 GiB
```

> 面试要点：KV Cache 是自回归推理中缓存的历史 Key 和 Value，避免重复计算。显存占用 = 2 × 层数 × KV 头数 × 头维度 × 序列长度 × 每元素字节数 × 批次大小。GQA/MQA 会减少 KV 头数，量化会减少每元素字节数，都能显著降低 KV Cache 占用。

## Q9. 模型权重的显存占用怎么算？量化怎么影响？

**回答**

模型权重的显存占用 = 参数总数 × 每个参数的字节数。

不同数值格式的每参数字节数：
- FP32：4 字节
- FP16 / BF16：2 字节
- INT8：1 字节
- INT4：0.5 字节

例如，一个 70B 参数的模型：
- FP16：70B × 2 = 140 GB
- INT8：70B × 1 = 70 GB
- INT4：70B × 0.5 = 35 GB

量化可以显著降低权重显存占用，使得更大的模型能够装入更少的显存。但是量化会带来精度损失，需要通过误差预算来评估是否可接受。

> 面试要点：模型权重显存占用 = 参数总数 × 每参数字节数。FP16 2 字节，INT8 1 字节，INT4 0.5 字节。量化能大幅降低权重显存，使大模型能装入更小的显存，但会有精度损失，需要误差预算评估。

## Q10. 什么是激活值（Activations）显存？它在推理中占用多少？

**回答**

激活值（Activations）是前向传播过程中，每一层输出的中间张量。在推理阶段，虽然不需要保留用于反向传播的梯度，但为了计算下一层的输入，当前层的输出激活值需要暂时驻留在显存中。

激活值的显存占用取决于：
- 批次大小（batch size）
- 序列长度（seq_len）
- 隐层维度（hidden dimension）
- 层数
- 数值格式（FP16/BF16 等）

公式粗略估计：
```
激活值显存 ≈ 批次 × 序列长度 × 隐层维度 × 每元素字节数 × 常数因子
```

常数因子取决于模型架构（如是否有中间激活需要保留、是否有中间激活值需要用于后续计算等）。通常激活值占用相对于权重和 KV Cache 较小，但在大批次、长序列场景下也可能不容小觑。

> 面试要点：激活值是前向传播过程中的中间张量，推理时需要暂时驻留在显存中。占用与批次、序列长度、隐层维度、数值格式相关。通常比权重和 KV Cache 小，但大批次长序列场景下不可忽略。

## Q11. 推理显存总预算怎么算？怎么判断单机能否装下？

**回答**

推理显存总预算由三部分组成：
1. **模型权重**：参数总数 × 每参数字节数
2. **KV Cache**：2 × 层数 × KV 头数 × 头维度 × 序列长度 × 每元素字节数 × 批次大小
3. **激活值与系统开销**：激活值显存 + 运行时预留（通常 5-10% 余量）

总显存需求 = 权重 + KV Cache + 激活值 + 系统开销

判断单机能否装下：总显存需求 ≤ 单卡显存容量 × 安全系数（如 0.9，留一些余量）。如果超过了，需要考虑模型并行（张量并行 TP、流水线并行 PP）跨多卡部署。

Python 示例（完整显存估算）：

```python
def estimate_inference_vram_gib(
    num_params_b,        # 参数总数 (Billion)
    num_layers,
    num_kv_heads,
    head_dim,
    seq_len,
    batch_size,
    weight_bytes=2,      # FP16=2, INT8=1, INT4=0.5
    kv_bytes=2,
    act_bytes_per_token=2 * 8192,  # 粗略估计，每 token 每层激活值字节数
    num_layers_act=80,   # 激活值涉及层数
    system_overhead=0.1  # 10% 系统开销
):
    # 权重
    weight_gib = num_params_b * 10**9 * weight_bytes / (1024**3)
    
    # KV Cache
    kv_bytes_total = 2 * num_layers * num_kv_heads * head_dim * seq_len * batch_size * kv_bytes
    kv_gib = kv_bytes_total / (1024**3)
    
    # 激活值（粗略）
    act_gib = batch_size * seq_len * act_bytes_per_token * num_layers_act / (1024**3)
    
    # 系统开销
    total_raw = weight_gib + kv_gib + act_gib
    total_with_overhead = total_raw * (1 + system_overhead)
    
    return {
        "weight_gib": weight_gib,
        "kv_gib": kv_gib,
        "act_gib": act_gib,
        "total_gib": total_with_overhead
    }

# 示例：70B 模型，FP16，序列长度 4096，批次 8
result = estimate_inference_vram_gib(
    num_params_b=70,
    num_layers=80,
    num_kv_heads=8,
    head_dim=128,
    seq_len=4096,
    batch_size=8
)
print(f"权重：{result['weight_gib']:.2f} GiB")
print(f"KV Cache：{result['kv_gib']:.2f} GiB")
print(f"激活值：{result['act_gib']:.2f} GiB")
print(f"总计（含系统开销）：{result['total_gib']:.2f} GiB")
```

> 面试要点：推理显存总预算 = 模型权重 + KV Cache + 激活值 + 系统开销（通常 5-10%）。总和 ≤ 单卡显存 × 安全系数（如 0.9）才能单机部署，否则需要多卡模型并行。

## Q12. 什么是量化？常见的量化格式有哪些？各有什么优缺点？

**回答**

量化（Quantization）是指用更低精度的数据类型表示模型权重和激活值，以减少显存占用和带宽压力，同时尽量保持模型精度。

常见的量化格式：

| 格式 | 每参数字节 | 优点 | 缺点 |
|------|-----------|------|------|
| FP32 | 4 字节 | 精度最高，兼容性好 | 显存占用大，慢 |
| FP16 / BF16 | 2 字节 | 平衡精度和性能，生产常用 | 比 INT8 占用多一倍显存 |
| INT8 | 1 字节 | 显存减半，推理快 | 需要量化校准，轻微精度损失 |
| INT4 | 0.5 字节 | 显存最省，能跑更大模型 | 精度损失较大，需要仔细校准 |

量化的误差来源：
1. **权重量化误差**：把高精度权重映射到低精度，会丢失部分信息。
2. **激活值量化误差**：推理时激活值也量化，会引入额外误差。
3. **累积误差**：多层叠加后，误差可能放大，导致模型输出质量下降。

误差预算是指：在部署前，通过实验测试量化模型在基准数据集上的质量下降（如困惑度 PPL 增加、准确率下降），确保在可接受范围内。

> 面试要点：量化是用低精度数据类型表示权重和激活值，以减少显存和带宽。常见格式 FP32(4B)、FP16/BF16(2B)、INT8(1B)、INT4(0.5B)。量化会引入权重量化误差、激活值量化误差和累积误差，需要通过误差预算（实验测试质量下降）来评估可接受性。

## Q13. 什么是通信代价模型？在多卡推理中为什么重要？

**回答**

当模型太大放不下单卡，或者需要更高吞吐时，需要把模型切分到多个 GPU 上（模型并行）。这时候，不同卡之间需要频繁交换数据（如激活值、梯度、KV Cache 片段），这个数据搬运的时间就是**通信代价**。

通信代价主要取决于：
- **数据量**：需要传输多少字节。
- **带宽**：网络或互连的带宽（如 NVLink、PCIe、以太网）。
- **延迟**：每次通信的启动开销（latency）。

公式：
```
通信时间 ≈ 启动延迟 + 数据量 / 带宽
```

在多卡推理中，如果通信代价过大，会抵消并行带来的计算加速，甚至导致多卡反而比单卡慢。

> 面试要点：通信代价是多卡推理中不同卡之间交换数据的时间，取决于数据量和带宽。通信代价过大会抵消并行加速，甚至让多卡比单卡还慢，是多卡推理架构设计的核心考量。

---

## Q14. 什么是张量并行（Tensor Parallelism, TP）？它的通信特点是什么？

**回答**

张量并行（Tensor Parallelism, TP）是指把一个模型的每一层切分到多个 GPU 上。例如，一个大矩阵乘法 `C = A × B`，可以把 A 按行切分，B 按列切分，每个卡只算一部分，最后用 All-Reduce 把结果汇总。

TP 的通信特点：
- **频率高**：每一层都需要通信（矩阵乘法的 All-Reduce）。
- **数据量大**：每层需要交换的激活值和梯度量很大。
- **延迟敏感**：每层都要等待通信完成才能进入下一层，串行依赖强。

TP 适合单节点内多卡（NVLink 带宽高），跨节点通信开销太大通常不适合 TP。

> 面试要点：张量并行（TP）把每一层切分到多个卡上，每层都需要 All-Reduce 通信。通信频率高、数据量大、延迟敏感，适合单节点内多卡（NVLink），跨节点通常不适合。

---

## Q15. 什么是流水线并行（Pipeline Parallelism, PP）？它的通信特点是什么？

**回答**

流水线并行（Pipeline Parallelism, PP）是指把模型的不同层切分到不同的 GPU 上。例如，前 20 层在卡 0，后 20 层在卡 1，以此类推。每个请求（token）像在流水线上一样，从第一个卡经过，依次传递到最后一个卡。

PP 的通信特点：
- **频率低**：每层之间只需要传递一次激活值（forward）和一次梯度（backward，训练时）。
- **数据量大**：每次传递整个激活值张量（批次 × 序列长度 × 隐层维度）。
- **有气泡（Pipeline Bubble）**：流水线不同阶段处理不同 micro-batch 时，会有空闲等待，导致硬件利用率不足。

PP 适合跨节点（因为通信频率低），但气泡效应会降低整体吞吐。

> 面试要点：流水线并行（PP）把模型不同层切分到不同卡，每层间通信一次激活值。通信频率低但数据量大，有气泡（Pipeline Bubble）效应，适合跨节点部署。

---

## Q16. 什么是张量并行（TP）和流水线并行（PP）的混合方案？怎么选择？

**回答**

混合方案（Hybrid Parallelism）是指同时使用 TP 和 PP。例如，先用 PP 把模型切分到多个节点（每个节点负责若干层），再在每个节点内部用 TP 把每一层切分到多个卡上。

选择建议：
- **单节点内多卡**：优先 TP，因为 NVLink 带宽高，TP 的高频通信开销可接受。
- **多节点**：优先 PP，因为 TP 的跨节点高频通信会成为瓶颈；PP 的低频通信更适合跨节点网络。
- **超大模型（放不下单节点）**：必须用 PP 把模型切分到多节点，再在节点内用 TP 填满每个节点的所有卡。

ASCII 图示（混合并行）：

```
节点 0:       节点 1:       节点 2:
Layer 1-20   Layer 21-40   Layer 41-60
(TP×4)       (TP×4)        (TP×4)
   │             │             │
   │  PP 通信（低频，大数据量）  │
   └──────────┴─────────────┘
```

> 面试要点：混合并行（TP+PP）先用 PP 分节点，再用 TP 分节点内卡。单节点内多卡优先 TP，多节点优先 PP，超大模型必须用 PP 分节点，再用 TP 填满每个节点。

## Q17. 什么是 Scale-in 和 Scale-up？在推理系统中怎么用？

**回答**

- **Scale-up（纵向扩展）**：增加单机的资源（比如加更多 GPU 卡、换更大的显存卡、加内存）。适合单机性能瓶颈，但受单机物理限制（机箱、供电、散热、主板插槽数）。
- **Scale-in（横向缩小/收缩）**：通常指减少运行中的实例数量，释放资源。更常见的是 **Scale-out（横向扩展）**：增加更多机器，通过负载均衡分发请求。

在推理系统中：
- **Scale-up**：当单个模型放不下单卡，或者单卡吞吐不够时，加更多卡（TP/PP）或换更大显存卡。
- **Scale-out**：当并发请求变多，单实例排队变长时，部署更多模型副本，通过负载均衡器分发请求。

> 面试要点：Scale-up 是加单机资源（更多卡、更大显存），Scale-out 是加机器（更多副本）。推理系统中，模型放不下或单卡吞吐不够用 Scale-up；并发请求多、排队长用 Scale-out。

## Q18. 推理系统的排队模型怎么理解？TTFT 和 TPOT 分别是什么？

**回答**

推理系统可以建模为排队系统（如 M/M/1 队列）：用户请求到达，进入排队等候，调度器调度到可用的推理实例上执行，执行完后返回结果。

关键指标：
- **TTFT（Time-To-First-Token）**：从用户发送请求到收到第一个输出 token 的时间。包含排队等待 + Prefill 计算时间。对于长 Prompt，Prefill 计算量大，TTFT 通常较高。
- **TPOT（Time-Per-Output-Token）**：从第一个 token 到后续每个 token 的平均时间。对应 Decode 阶段，受内存带宽限制（每次要把整个 KV Cache 读一遍）。

排队模型帮助理解：当请求到达速率接近服务能力时，排队等待时间会急剧上升（P99 延迟飙升），此时需要增加副本（Scale-out）或优化单实例吞吐。

> 面试要点：推理系统可建模为排队系统。TTFT = 排队等待 + Prefill 计算（受 Prompt 长度影响大）；TPOT = Decode 阶段单 token 生成时间（受内存带宽限制）。请求到达率接近服务能力时，P99 延迟会飙升。

---

## Q19. 什么是 KV 亲和（KV Affinity）路由？为什么重要？

**回答**

KV 亲和（KV Affinity）是指把同一会话（同一个用户的多轮对话）的请求路由到同一个推理实例上，因为该实例已经缓存了该会话的 KV Cache（前文信息）。

如果没有 KV 亲和，同一会话的不同请求可能发到不同的实例，新实例没有之前的 KV Cache，需要重新计算 Prefill（重新处理整个历史上下文），导致 TTFT 大幅增加，且浪费计算资源。

KV 亲和路由可以显著提高多轮对话的 TTFT，减少重复计算，提升整体系统吞吐。

> 面试要点：KV 亲 affinity 路由把同一会话的请求路由到同一个推理实例，复用该实例已有的 KV Cache，避免重复 Prefill 计算，显著降低多轮对话的 TTFT，提升系统吞吐。

## Q20. 推理系统常见的评估指标有哪些？各表示什么？

**回答**

推理系统常见的评估指标：

| 指标 | 含义 | 说明 |
|------|------|------|
| TTFT | 首 token 时间 | 请求到首个输出 token 的延迟，受 Prefill 影响 |
| TPOT | 单 token 生成时间 | Decode 阶段每个 token 的平均时间，受内存带宽限制 |
| 总延迟 | 端到端时间 | 请求到完整回答的总时间 |
| 吞吐量 (TPS) | 每秒生成 token 数 | 系统整体处理能力 |
| 并发数 | 同时处理的请求数 | 受显存和 KV Cache 容量限制 |
| 错误率 | 请求失败率 | 模型崩溃、超时、OOM 等 |
| P99 延迟 | 99 分位延迟 | 尾部延迟，反映系统稳定性 |

生产环境通常关注 P99 延迟（保证最差情况也可接受）和吞吐量（成本效益）。

> 面试要点：推理系统评估指标包括 TTFT（首 token 时间）、TPOT（单 token 生成时间）、总延迟、吞吐量（TPS）、并发数、错误率、P99 延迟。生产环境重点关注 P99 延迟和吞吐量。

## Q21. 什么是连续批处理（Continuous Batching）？它比静态批处理好在哪里？

**回答**

静态批处理（Static Batching）：等一批请求都齐了才一起处理，处理完再下一批。短请求需要等长请求处理完，头阻塞（Head-of-Line Blocking）严重，GPU 利用率低。

连续批处理（Continuous Batching）：每个请求独立进出。一个请求的 Decode 完成后立即输出，新请求可以立即填补空出的位置，不用等整批完成。这样 GPU 始终有任务可做，利用率更高，短请求不需要被长请求阻塞。

vLLM、TensorRT-LLM 等现代推理框架都采用连续批处理，显著提升了交互式对话的 TTFT 和整体吞吐。

> 面试要点：连续批处理（Continuous Batching）让每个请求独立进出，不需要等整批完成，避免了静态批处理的头阻塞问题，GPU 利用率更高，短请求 TTFT 更低，整体吞吐更好。

## Q22. PagedAttention 是什么？它解决了什么问题？

**回答**

PagedAttention 是 vLLM 提出的 KV Cache 管理技术，借鉴操作系统虚拟内存的分页思想。

传统 KV Cache 分配需要预先为每个请求分配连续的、最大可能长度的显存空间，导致大量碎片和浪费（很多分配的空间没用完）。

PagedAttention 把 KV Cache 分成固定大小的“页”（blocks），按需分配，不需要连续。不同请求的 KV Cache 可以散落在不同的物理页框中，通过页表映射逻辑地址。这样：
1. 消除了外部碎片，显存利用率大幅提高。
2. 支持 KV Cache 共享（多个请求共享相同前缀的 KV Cache 页）。
3. 支持动态换入换出（Swapping），把不常用的 KV Cache 页换到 CPU 内存，腾出 GPU 显存。

> 面试要点：PagedAttention 借鉴操作系统分页思想，把 KV Cache 分成固定页按需分配，消除外部碎片，支持前缀缓存共享和动态换入换出，显著提高显存利用率和并发能力。

## Q23. 推理系统的常见瓶颈有哪些？怎么定位？

**回答**

推理系统常见瓶颈：

| 瓶颈 | 表现 | 定位方法 |
|------|------|---------|
| 显存不足 | OOM，无法加载模型或批次受限 | 监控显存占用，计算权重+KV Cache+激活值总和 |
| 内存带宽 | Decode 阶段 TPOT 很高，GPU 利用率低 | Roofline 图看是否在斜线附近，rocprofv3 看内存带宽利用率 |
| 计算不足 | Prefill 阶段延迟高，GPU 计算饱和 | Roofline 图看是否在水平线附近，MFU 是否很高 |
| 通信瓶颈 | 多卡 TP/PP 下延迟高，加速比低 | rocprofv3 看通信时间，对比单机和多卡差异 |
| 排队阻塞 | 高并发下 P99 延迟飙升 | 监控队列长度、排队时间，对比吞吐量曲线 |

定位流程：先看端到端延迟是否达标 → 若不达标，拆分为 Prefill/Decode 阶段 → Prefill 慢看计算带宽（Roofline 计算密集型）→ Decode 慢看内存带宽（Roofline 存储密集型）→ 多卡慢看通信时间 → 并发高慢看排队模型。

> 面试要点：推理系统瓶颈包括显存不足、内存带宽、计算不足、通信瓶颈、排队阻塞。定位流程：端到端延迟 → 拆分 Prefill/Decode 阶段 → Roofline 判瓶颈类型 → rocprofv3 看硬件计数器 → 排队模型看并发能力。

## Q23(续). 什么是 MFU（模型浮点利用率）？在推理中怎么用？

**回答**

MFU（Model FLOPs Utilization）是指实际浮点运算速度占峰值算力的比例。在 LLM 推理中，MFU 是衡量硬件计算能力被充分利用程度的重要指标。

计算公式：
```
MFU = (每 token 浮点运算量 × 吞吐量) / 峰值算力
```

每 token 浮点运算量约为 2 × 参数量（前向传播约 2× 参数量 FLOP）。

MFU 的典型表现：
- **Prefill 阶段**：MFU 通常较高（30%-70%），因为批量矩阵乘法计算密集。
- **Decode 阶段**：MFU 通常很低（5%-20%），因为每次只生成一个 token，受内存带宽限制，算力大部分时间闲等数据。

如果 MFU 过低，说明硬件浪费严重，需要优化批处理、增大批次、或使用更高效的算子融合。

> 面试要点：MFU = 实际浮点运算速度 / 峰值算力。LLM 推理中可用 `(参数量 × 2 × 吞吐量) / 峰值算力` 估算。Prefill 阶段 MFU 较高，Decode 阶段 MFU 通常很低（受内存带宽限制）。MFU 低说明硬件计算能力浪费。

## Q23(续). 本章小结：怎么做 LLM 推理系统的性能建模和校准？

**回答**

做 LLM 推理系统性能建模和校准，建议按以下步骤：

1. **收齐模型七元组**：参数量、层数、隐层维度、KV 头数、头维度、词表大小、数值格式。这些决定了权重显存和每 token 计算量。
2. **先算 Roofline 上限**：用峰值算力和峰值带宽算出理论性能天花板，判断系统是计算受限还是带宽受限。
3. **估算显存**：权重 + KV Cache + 激活值 + 系统开销，判断单机能否装下，否则规划多卡并行（TP/PP/DP/EP）。
4. **第一次真机 Profile**：用 rocprofv3/Nsight Compute 跑真实负载，测 TTFT、TPOT、MFU、显存占用、内存带宽利用率。
5. **校准模型**：用真实测量值修正离线模型的参数（如 MFU、带宽利用率、通信开销），使模型预测与真实测量一致。
6. **容量规划**：根据校准后的模型，计算目标 QPS 和 SLA 下需要多少卡、多少机器。
7. **闭环验证**：在真实流量上验证预测是否准确，发现偏差再回调模型参数。

ASCII 图示（建模校准闭环）：

```
模型七元组 ──▶ Roofline 上限 ──▶ 显存估算 ──▶ 多卡并行方案
   │                                       │
   ▼                                       ▼
真机 Profile ──▶ 模型校准 ──▶ 容量规划 ──▶ 真实流量验证
   ▲                                       │
   └───────────────────────────────────────┘
   (发现偏差回到模型校准)
```

一句话总结：**推理系统性能建模不是拍脑袋，而是“模型七元组 → Roofline 上限 → 显存估算 → 第一次真机 Profile → 参数校准 → 容量规划 → 真实流量验证”的闭环。**

> 面试要点：本章小结＝收齐模型七元组 → Roofline 算上限 → 显存估算（权重+KV Cache+激活值）→ 多卡并行方案 → 第一次真机 Profile（rocprofv3/Nsight Compute） → 模型校准（修正 MFU、带宽利用率、通信开销） → 容量规划（QPS/SLA 下需要多少卡） → 真实流量验证 → 发现偏差回调校准。建模要有数据支撑，校准是关键，不要只做离线拍脑袋。
