## Q1. 什么是上下文工程？和提示词工程有什么区别？

**回答**

如果你用过大模型，肯定听过“提示词工程（Prompt Engineering）”——也就是怎么写提示词，才能让模型给出你想要的答案。那“上下文工程（Context Engineering）”又是什么？它和提示词工程有什么区别？

用大白话说：

- **提示词工程**解决的是“单次问答”的最优解：你写一个提示词，模型根据这个提示词回答你一个问题，一次性搞定。
- **上下文工程**解决的是“多轮自主任务”的最优解：智能体不是只答一个问题，而是在一段持续的交互中，不断地读工具输出、写中间结果、看历史对话、做决策。这时候，怎么把“该记住的信息”塞进模型的上下文窗口、怎么把“不该再看的旧信息”挤出去、怎么让模型在长对话里不丢情境，这就是上下文工程要解决的问题。

---

### 提示词工程 vs 上下文工程（大白话对比）

| 维度 | 提示词工程 | 上下文工程 |
|------|-----------|-----------|
| 核心问题 | “怎么写提示词，让模型一次答好？” | “怎么管理上下文，让模型在多轮任务里不丢情境？” |
| 解决的场景 | 单次问答、一次性指令 | 多轮自主任务、长对话、智能体连续工作 |
| 关注点 | 提示词的措辞、结构、示例 | 上下文窗口里放什么、不放什么、怎么压缩、怎么截断 |
| 典型产出 | 一个写得很好的 System Prompt | 一个能动态管理上下文的上下文管理器 |

用一个比喻：

- **提示词工程**像“给考生一张写得清清楚楚的试题”，考生看一遍就能答题。
- **上下文工程**像“给考生一张只能写有限字迹的草稿纸”，考生得决定草稿纸上写什么、擦掉什么、保留什么，才能在多道题之间保持思路连贯。

---

### 上下文工程为什么对智能体很重要？

智能体的工作流是“感知→思考→行动→观察”循环，每一轮都要把上下文（历史对话、工具输出、中间结果）喂给模型。如果上下文管理不好，就会出现：

- 上下文太长，模型“听不清”关键信息（大海捞针效应，下一章讲）；
- 上下文太短，重要信息被挤出去了，模型丢了情境；
- 工具输出太臃肿，塞满了上下文窗口，没空间放有用信息。

上下文工程就是要解决这些问题，让智能体在持续交互中始终保持对“情境”的理解。

**面试要点**：提示词工程解决“单次问答”最优解，上下文工程解决“多轮自主任务”最优解。两者不是替代关系，而是相辅相成。上下文工程的核心是管理上下文窗口里放什么、不放什么、怎么压缩、怎么截断。

## Q2. 为什么上下文会“腐烂”？大海捞针实验说明了什么？

**回答**

你可能会觉得：模型的上下文窗口现在这么大（动辄 128k、200k token），把所有历史都塞进去不就行了吗？为什么还需要上下文工程？

问题在于：**上下文会“腐烂”**。上下文窗口越长，模型从里面准确回忆信息的能力就越差。这不是说模型“忘了”，而是模型在长上下文里越来越难“抓住重点”。

---

### 大海捞针实验（Needle In A Haystack）

Anthropic 公司做过一个著名的“大海捞针”实验：在一大段无关文本（大海）里插入一句关键信息（针），然后问模型这句关键信息是什么，看模型能不能找出来。

实验得出的数据很冷酷：

| 上下文长度 | 模型召回率（找到关键信息的概率） |
|-----------|-------------------------------|
| < 8k token | 95%+ |
| 32k token | 78% |
| 100k token | 关键信息“视而不见”概率升至 30% |

可以看到，随着上下文窗口中 token 数量的增加，模型从该上下文中准确回忆信息的能力在下降。上下文越长，模型越容易“视而不见”。

---

### 为什么会“腐烂”？（大白话解释）

LLM 基于 Transformer 架构，每个 token 都能关注上下文里每个其他 token。这产生了 n² 的成对关系（n 是 token 数量）。上下文越长，这些配对关系越多，模型捕捉这些关系的能力就越薄弱。结果就是：注意力被稀释，关键信息淹没在大量无关文本里，模型“看见”了所有字，但“注意”不到关键信息。

用一个生活中的比喻：

- 短上下文像“一张小便签”，上面写了几件事，你一眼就能看到重要的；
- 长上下文像“一整本厚书”，里面夹着一张重要便签，你得翻很久才能找到，还可能翻过去都没发现。

---

### 上下文“腐烂”的表现

| 现象 | 大白话解释 |
|------|-----------|
| 关键信息“视而不见” | 明明上下文里有，模型却答不出来或答错了 |
| 指令被稀释 | 你在开头给的要求，中间被大量无关对话淹没，模型不再遵循 |
| 工具输出淹没上下文 | 工具返回一大堆数据，塞满了窗口，真正有用的信息被挤出去了 |
| 长对话丢情境 | 聊了几十轮后，模型不记得开头说过了什么，前后矛盾 |

**面试要点**：上下文会“腐烂”，核心原因是 Transformer 架构导致 n² 的配对关系，上下文越长注意力越分散。大海捞针实验表明：上下文<8k 时召回率 95%+，32k 时降到 78%，100k 时关键信息“视而不见”概率升至 30%。所以不能无脑塞全部历史，需要上下文工程来管理。

## Q3. 上下文窗口管理怎么做？（滑动窗口、摘要压缩、截断）

**回答**

既然上下文会腐烂，咱们就得管理上下文窗口，决定“放什么、不放什么、怎么压缩”。常见的上下文窗口管理有三种手段：

---

### 手段 1：滑动窗口

只保留最近 N 轮对话，旧的直接扔掉。

- 优点：实现简单，token 使用固定可控；
- 缺点：早期的重要信息会被丢失，不适合需要长期回溯的任务。

适合：不需要长期回溯的一般对话。

---

### 手段 2：摘要压缩

每 N 轮，用模型把历史对话压缩成一段摘要（只保留“已确认结论、被否决方案、待办事项”），然后用摘要替换掉原始记录。

- 优点：token 使用低，重要信息不丢；
- 缺点：压缩可能丢失细节，需要额外调模型来做摘要。

适合：长任务、需要跨轮回溯的场景。

---

### 手段 3：截断工具输出

工具（搜索、代码执行器、数据库查询）返回的结果有时很长，直接塞进上下文会浪费大量 token。可以对工具输出做截断（只保留关键字段、压缩 JSON、取前 N 条）。

- 优点：不丢历史对话，只精简工具返回的冗余数据；
- 缺点：截断过多可能丢失工具返回的细节。

适合：工具输出很长但关键信息集中的场景。

---

### 用 ASCII 图表示三种手段

```

  滑动窗口：              [最近 N 轮]……[旧的扔掉]
                       └────────────┘
           优点：简单、固定 token     缺点：丢早期信息

           优点：不丢历史对话         缺点：可能丢工具细节
```

### 手撕上下文窗口管理 Python 代码

下面是一个最小可用的上下文管理器，支持：

- token 预算（最大 token 数）；
- 滑动窗口（超预算时挤掉最旧的消息）；
- 截断工具输出（超过长度就截断）；
- 自动压缩（超预算时调模型做摘要，演示版用规则模拟）。

```python
"""
context_manager.py：上下文窗口管理器
支持 token 预算、滑动窗口、截断工具输出、自动压缩（演示版）。
"""

from typing import List, Dict, Any, Optional
from datetime import datetime


def estimate_tokens(text: str) -> int:
    """
    估算文本的 token 数量。
    演示版：按字符数粗略估算（中文按 1 字≈1 token，英文按 4 字≈1 token）。
    真实项目中应用 tiktoken 或模型分词器精确计算。
    """
    chinese = len([c for c in text if '一' <= c <= '鿿'])
    others = len(text) - chinese
    return chinese + others // 4 + 1


class ContextManager:
    """上下文窗口管理器：管理消息历史，控制 token 在预算内。"""

    def __init__(self, max_tokens: int = 4000, max_tool_output_chars: int = 1000):
        self.max_tokens = max_tokens
        self.max_tool_output_chars = max_tool_output_chars
        self.messages: List[Dict[str, Any]] = []

    def add(self, role: str, content: str, is_tool_output: bool = False) -> None:
        """
        添加一条消息到上下文。
        如果是工具输出，先做截断。
        """
        if is_tool_output:
            content = self._truncate_tool_output(content)

        self.messages.append({
            "role": role,
            "content": content,
            "timestamp": datetime.now().isoformat(),
            "is_tool_output": is_tool_output,
        })

        # 添加后如果超预算，自动压缩（滑动窗口挤掉旧消息）
        self._compress_if_over_budget()

    def _truncate_tool_output(self, content: str) -> str:
        """截断过长的工具输出，只保留前 max_tool_output_chars 个字符。"""
        if len(content) > self.max_tool_output_chars:
            return content[:self.max_tool_output_chars] + f"\n……[工具输出已截断，共 {len(content)} 字符]"
        return content

    def _total_tokens(self) -> int:
        """计算当前所有消息的总 token 数。"""
        return sum(estimate_tokens(m["content"]) for m in self.messages)

    def _compress_if_over_budget(self) -> None:
        """
        如果总 token 超过预算，挤掉最旧的非系统消息，直到回到预算内。
        保留第一条系统消息（通常是 System Prompt）。
        """
        while self._total_tokens() > self.max_tokens and len(self.messages) > 1:
            # 不删第一条（通常是 System Prompt），从第二条开始删
            removed = self.messages.pop(1)
            print(f"[上下文管理] 超预算，挤掉旧消息：{removed['role']} - {removed['content'][:30]}…")

    def get_context(self) -> List[Dict[str, Any]]:
        """获取当前上下文，供模型调用。"""
        return self.messages

    def get_context_text(self) -> str:
        """把当前上下文拼成字符串，方便查看。"""
        lines = []
        for m in self.messages:
            marker = "[工具输出]" if m.get("is_tool_output") else ""
            lines.append(f"{m['role']}{marker}: {m['content']}")
        return "\n".join(lines)


# ==================== 使用示例 ====================

if __name__ == "__main__":
    cm = ContextManager(max_tokens=500, max_tool_output_chars=200)

    cm.add("system", "你是一个智能体助手。")
    cm.add("user", "帮我查一下北京今天天气")
    cm.add("assistant", "北京今天晴朗，15°C。")
    cm.add("tool", "搜索结果：北京今天晴朗，气温15°C，湿度30%，无降水。详细数据如下：……" + "x" * 500, is_tool_output=True)
    cm.add("user", "那上海呢？")

    print("=== 当前上下文 ===")
    print(cm.get_context_text())
    print(f"\n估算总 token：{cm._total_tokens()}（预算 {cm.max_tokens}）")
```

**运行输出示例：**

```
[上下文管理] 超预算，挤掉旧消息：user - 帮我查一下北京今天天气…
=== 当前上下文 ===
system: 你是一个智能体助手。
assistant: 北京今天晴朗，15°C。
[工具输出] tool: 搜索结果：北京今天晴朗，气温15°C，湿度30%，无降水。详细数据如下：……xxx[工具输出已截断，共 514 字符]
user: 那上海呢？

估算总 token：315（预算 500）
```

可以看到：长工具输出被截断了，而且当总 token 超过预算时，最旧的用户消息被挤掉了，系统提示词被保留。

---

### 这段代码的设计要点

1. **token 预算**：`max_tokens` 控制上下文总大小，防止爆窗口；
2. **滑动窗口压缩**：`_compress_if_over_budget()` 超预算时挤掉最旧消息，保留系统提示词；
3. **工具输出截断**：`_truncate_tool_output()` 把过长的工具返回精简，只保留关键部分；
4. **粗略 token 估算**：`estimate_tokens()` 演示版按字符数估算，真实项目应用 tiktoken；
5. **可扩展**：可以加入“摘要压缩”（用模型把旧对话压缩成摘要再塞回去）。

**面试要点**：上下文窗口管理有三种手段——滑动窗口（简单但丢早期信息）、摘要压缩（省 token 但需额外调模型）、截断工具输出（不丢历史但可能丢细节）。手撕代码时要体现：token 预算、超预算挤旧消息、工具输出截断、保留系统提示词。

## Q4. 好上下文的 4 个配方是什么？

**回答**

Anthropic 在其上下文工程文章中总结了“好上下文”的 4 个配方，这对构建有能力的智能体至关重要。下面咱们用大白话逐个拆解。

---

### 配方 1：提示词——高信号、低噪音

不要在提示词里写“如果 A 且 B 且 C 则执行 D”这种脆弱逻辑，也不要只说“请尽量做好”这种空泛要求。正确的做法是：

- 给出**边界**（能做什么、不能做什么）；
- 给出**目标**（要达到什么效果）；
- 给出**输出格式**（要什么样的答案）；
- 让模型自己推理路径。

建议把提示词组织成不同部分，比如 `<背景信息>`、`<指令>`、`## 工具指导`、`## 输出描述`，并用 XML 标记或 Markdown 标题划分。

**大白话**：别让模型猜，要明确，要结构化，要让重要信息（信号）突出，无用废话（噪音）少。

---

### 配方 2：智能体工具调用——高效 token 和高效行为

工具让智能体能与环境操作，并在工作时引入新的上下文。但常见的失效模式是**工具集过于臃肿**——涵盖太多功能，或者模型在决定用哪个工具时犹豫不决。

建议：

- 为智能体策划一个**最小可行工具集**（只放真正需要的工具）；
- 如果人类工程师都无法明确说出“在这种情况下应该用哪个工具”，就别指望模型能做得更好；
- 工具返回的信息要**高效**（只返回关键字段，别塞一大堆冗余数据），减少 token 浪费。

**大白话**：工具少而精，模型才好选；工具返回要短，上下文才不挤。

---

### 配方 3：示例（few-shot）——典型优于边缘

用 3 个覆盖 80% 主流场景的示例，比 20 条“罕见 corner case”更能让模型举一反三。

很多开发者喜欢把各种奇怪的边界情况都写成 few-shot 示例，结果反而让模型困惑。应该选最典型、最常见的场景作为示例，让模型学会“正常情况怎么处理”，边界情况靠模型的泛化能力去应对。

**大白话**：多给几个“正常例子”，少给“奇怪例子”，模型才懂什么是正常。

---

### 配方 4：动态检索

不要预先处理所有相关数据，而是采用“即时”方法——在模型推理前，根据当前问题动态检索重要上下文（这就是 RAG 的思想），只把检索到的相关片段放进上下文。

这样既避免了上下文太长，又保证了模型看到的是跟当前问题最相关的信息。

**大白话**：不用把所有知识都塞进去，要用什么再查什么，查到的相关片段再放进上下文。

---

## Q5. 提示词怎么写才高信号低噪音？

**回答**

提示词是上下文工程里最直接的一部分。怎么写才能让模型“听得懂、答得准”？核心原则就是**高信号、低噪音**——让模型一眼看到重要的，不用在废话里找重点。

---

### 高信号低噪音的写法（对比表）

| 噪音写法（❌） | 信号写法（✅） | 原因 |
|-------------|-------------|------|
| “请尽量做好” | “输出必须包含：标题、正文、结尾引导” | 空泛 vs 具体可验证 |
| “如果 A 且 B 且 C 则执行 D，否则……” | “边界：只处理 XX 场景，不处理 XX 场景” | 脆弱逻辑 vs 明确边界 |
| “你是一个很聪明的助手，请帮我……” | “角色：资深 Python 工程师。任务：写代码并跑通。” | 褒义废话 vs 角色+任务 |
| 把所有要求堆在一段话里 | 用 `<背景信息>`、`<指令>`、`## 工具指导`、`## 输出描述` 分段 | 混在一起 vs 结构化 |

---

### 一个高信号提示词的模板（XML 风格）

```xml
<背景信息>
你是一个智能体，专门帮用户查询城市天气并给出出行建议。
</背景信息>

<指令>
1. 从用户输入中提取城市名；
2. 调用天气工具查询该城市天气；
3. 基于天气结果给出出行建议（如：晴朗适合出门，雨天建议带伞）。
</指令>

## 工具指导
- 可用工具：search_tianqi(城市名) -> 返回天气描述
- 如果找不到城市，诚实告知用户，不要编造
</工具指导>

## 输出描述
- 先给天气情况，再给出行建议
- 语言：中文，简洁明了，不超过 100 字
</输出描述>
```

---

### 为什么这样写更好？

1. **角色明确**：模型知道自己是谁，不至于跑偏；
2. **任务明确**：1、2、3 步骤清晰，模型知道先做什么、后做什么；
3. **工具明确**：知道能调什么工具、怎么调、失败了怎么办；
4. **输出明确**：格式、长度、语言都规定好了，下游程序好解析；
5. **结构清晰**：用 XML 标记或 Markdown 标题分段，模型更容易解析不同部分。

**面试要点**：提示词写法的核心是“高信号、低噪音”——给边界、给目标、给输出格式，结构化分段（背景信息/指令/工具指导/输出描述），避免空泛要求和脆弱逻辑。

## Q6. 智能体工具调用怎么让上下文更高效？（最小可行工具集、截断工具输出）

**回答**

工具是智能体的“手脚”，但工具太多或工具输出太长，会把上下文窗口塞满，让模型“选工具时犹豫、看输出时眼花”。上下文工程里的工具调用优化，核心是两点：**最小可行工具集**和**截断工具输出**。

---

### 1. 最小可行工具集

不要把所有能想到的工具都塞给模型。只放真正需要的、模型能清楚区分使用场景的工具。

**判断标准**：如果人类工程师都无法明确说出“在这种情况下应该用哪个工具”，就别指望模型能做得更好。

| 臃肿工具集（❌） | 最小可行工具集（✅） |
|---------------|-------------------|
| 搜索、计算器、发邮件、发短信、查股价、查天气、查油价、查汇率、查新闻、查天气…… | 搜索、计算器、查天气（只放这个任务真正用的） |

**好处**：
- 模型选工具时不犹豫，决策更准；
- 上下文里工具描述更短，省 token；
- 长期维护更简单，工具越少，出错概率越低。

---

### 2. 截断工具输出

工具返回的结果有时很长（比如搜索返回一整页 HTML、数据库查询返回成百上千行）。直接塞进上下文会浪费大量 token，还可能把关键信息淹没。

建议对工具输出做截断：

- 只保留关键字段（比如只保留天气的“温度、湿度、天气描述”，不要保留整个 JSON）；
- 压缩 JSON（去掉空格、换行、无关字段）；
- 取前 N 条结果（比如只保留搜索的前 3 条）；
- 超过长度就截断，并标注“已截断”。

**大白话**：工具返回只要关键信息，别塞一大堆废话进上下文。

---

### 用 ASCII 图表示工具调用优化

```
工具调用优化（上下文更高效）：

  臃肿方式：                    优化方式：
  ┌─────────────┐              ┌─────────────┐
  │ 工具 A-Z    │              │ 工具 A、B、C│
  │ (全塞进去)  │              │ (只放需要的) │
  └──────┬──────┘              └──────┬──────┘
         │                            │
         ▼                            ▼
  工具返回整页 HTML            工具返回关键字段
  (几千 token)                 (几十 token)
         │                            │
         ▼                            ▼
  上下文窗口被填满            上下文窗口还有空间
  关键信息被淹没              关键信息清晰可见
```

**面试要点**：工具调用上下文优化的核心是“最小可行工具集”（只放真正需要的、模型能区分的工具）和“截断工具输出”（只保留关键字段，超长就截断）。两者都能显著减少 token 浪费，提高模型决策准确率。

## Q7. few-shot 示例怎么选？（典型优于边缘）

**回答**

few-shot（少样本示例）是提示工程里常用的技术：在提示词里给几个“输入→输出”的例子，让模型学习格式和风格。但选示例有讲究，选错了反而让模型困惑。

---

### 核心原则：典型优于边缘

用 **3 个覆盖 80% 主流场景的示例**，比 **20 条“罕见 corner case”** 更能让模型举一反三。

很多开发者喜欢把各种奇怪的边界情况都写成 few-shot 示例，比如“用户输入乱码怎么办”“用户输入空字符串怎么办”“用户用方言说话怎么办”。结果模型看到太多奇怪例子，反而对“正常情况怎么处理”反应迟钝。

**正确做法**：
1. 先选 3~5 个最典型、最常见的场景作为示例；
2. 让模型先学会“正常情况怎么处理”；
3. 边界情况靠模型的泛化能力去应对，或者在系统提示词里用规则说明，而不是全靠 few-shot 堆砌。

---

### few-shot 示例选不对的后果

| 选法 | 后果 |
|------|------|
| 只放正常场景（推荐） | 模型学会主流流程，边界情况靠泛化 |
| 只放边界情况 | 模型以为所有输入都很奇怪，正常情况也处理不好 |
| 放太多示例（>10 个） | 上下文被示例占满，真正的问题没空间放 |
| 示例格式不统一 | 模型不知道输出应该长什么样 |

---

### 一个 few-shot 示例的写法（XML 风格）

```xml
<示例>
用户：帮我查北京天气
助手：北京今天晴朗，15°C，不需要带伞。

用户：查一下上海的天气
助手：上海今天多云，22°C，偶有小雨，建议随身带伞。

用户：广州今天天气怎么样
助手：广州今天阵雨，28°C，湿度大，建议带伞并注意交通。
</示例>
```

---

```

  典型优于边缘（✅）：                 边缘优先（❌）：
  ┌─────────────┐                    ┌─────────────┐

  │ 示例 2：查天气（常见）│           │ 示例 2：空字符串（罕见）│

**面试要点**：few-shot 示例的核心原则是“典型优于边缘”——选 3~5 个最常见场景作为示例，让模型先学会正常流程，边界情况靠泛化或系统提示词规则。避免放太多示例占满上下文，避免示例格式不统一。

## Q8. 动态检索怎么在上下文工程中应用？

**回答**

前面章节我们聊过 RAG（检索增强生成）。在上下文工程里，动态检索是“配方 4”：不要预先处理所有相关数据，而是采用“即时”方法——根据当前问题动态检索重要上下文，只把检索到的相关片段放进上下文。

---

### 为什么需要动态检索？

如果把所有知识都预先塞进上下文，会有两个问题：

1. 上下文太长，模型“视而不见”（大海捞针）；
2. 很多知识跟当前问题无关，浪费 token。

动态检索的做法是：用户提问时，先根据问题去知识库里检索最相关的片段（Top-K），只把这几个片段放进当前上下文，再喂给模型。这样既保持了上下文简洁，又保证了模型看到的是跟当前问题最相关的信息。

---

### 动态检索在上下文工程中的位置

```
用户问题 ──→ 动态检索（根据问题查知识库） ──→ 检索到的相关片段（Top-K）
                                                     │
                                                     ▼
                                            拼接进当前上下文
                                                     │
                                                     ▼
                                            模型生成答案
```

和静态预置上下文相比，动态检索是“要用什么再查什么”，更灵活、更省 token。

---

### 手撕动态检索 Python 代码（简化版）

下面是一个不依赖真实向量数据库的动态检索演示版：用简单的关键词匹配模拟向量检索，能跑动态检索的完整逻辑。真实项目中替换为 Chroma / Milvus / Pinecone 等向量数据库和 Embedding 模型即可。

```python
"""
dynamic_retrieval.py：动态检索最小可用版（演示版）
根据用户问题动态检索知识库片段，只放进相关片段进上下文。
"""

import re
from typing import List, Dict, Any


class KnowledgeBase:
    """简单知识库：存储文档片段，支持按关键词检索（模拟向量检索）。"""

    def __init__(self):
        self.docs: List[Dict[str, Any]] = []

    def add(self, content: str, source: str = "") -> None:
        """添加一条文档片段。"""
        self.docs.append({"content": content, "source": source})

    def search(self, query: str, top_k: int = 3) -> List[Dict[str, Any]]:
        """
        检索 Top-K 最相关片段。
        演示版：用查询关键词与片段内容的重叠数作为相似度。
        真实项目中应用 Embedding + 向量相似度检索。
        """
        query_words = set(re.findall(r"\w+", query.lower()))
        scored = []
        for doc in self.docs:
            doc_words = set(re.findall(r"\w+", doc["content"].lower()))
            overlap = len(query_words & doc_words)
            if overlap > 0:
                scored.append((overlap, doc))
        scored.sort(key=lambda x: x[0], reverse=True)
        return [doc for _, doc in scored[:top_k]]


def build_context_with_dynamic_retrieval(
    question: str,
    kb: KnowledgeBase,
    system_prompt: str,
    top_k: int = 3,
) -> str:
    """
    用动态检索构建上下文：只把检索到的相关片段放进上下文。
    """
    retrieved = kb.search(question, top_k=top_k)

    context_parts = [system_prompt]

    if retrieved:
        context_parts.append("\n## 检索到的相关资料：")
        for i, doc in enumerate(retrieved, 1):
            context_parts.append(f"{i}. {doc['content']}")
    else:
        context_parts.append("\n## 检索到的相关资料：(无)")

    context_parts.append(f"\n## 用户问题：{question}")
    context_parts.append("\n## 请基于上述资料回答：")

    return "\n".join(context_parts)


# ==================== 使用示例 ====================

if __name__ == "__main__":
    # 准备知识库
    kb = KnowledgeBase()
    kb.add("单餐餐饮报销上限为 200 元，需提供发票。", "报销制度")
    kb.add("交通费报销：出租车和网约车单程上限 100 元，地铁和公交实报实销。", "报销制度")
    kb.add("住宿费报销：出差住宿单晚上限 500 元，需提供酒店发票。", "报销制度")
    kb.add("公司 WiFi 密码是 Guest123，仅限办公区使用。", "办公常识")

    system_prompt = "你是一个公司内部知识库助手。请基于检索到的资料回答员工问题。"

    # 场景 1：问报销（应该检索到报销制度相关片段）
    print("=== 场景 1：问单餐报销上限 ===")
    ctx1 = build_context_with_dynamic_retrieval("单餐报销上限是多少？", kb, system_prompt)
    print(ctx1)

    # 场景 2：问 WiFi（应该检索到办公常识）
    print("\n=== 场景 2：问公司 WiFi 密码 ===")
    ctx2 = build_context_with_dynamic_retrieval("公司 WiFi 密码是多少？", kb, system_prompt)
    print(ctx2)

    # 场景 3：问无关问题（检索不到相关片段）
    print("\n=== 场景 3：问无关问题 ===")
    ctx3 = build_context_with_dynamic_retrieval("怎么煮西红柿鸡蛋面？", kb, system_prompt)
    print(ctx3)
```

**运行输出示例（场景 1）：**

```
=== 场景 1：问单餐报销上限 ===
你是一个公司内部知识库助手。请基于检索到的资料回答员工问题。

## 检索到的相关资料：
1. 单餐餐饮报销上限为 200 元，需提供发票。

## 用户问题：单餐报销上限是多少？

## 请基于上述资料回答：
```

可以看到，动态检索只把“单餐报销上限为 200 元”这一条相关片段放进了上下文，没有把 WiFi 密码、住宿费等无关信息塞进去。

**面试要点**：动态检索在上下文工程中的作用是“要用什么再查什么”，只把检索到的 Top-K 相关片段放进当前上下文，避免上下文太长和无关信息干扰。手撕代码时要体现：根据问题检索知识库、只放相关片段进上下文、检索不到时诚实说明。

## Q9. 手撕 Python 代码：上下文管理器（token 预算、自动压缩、截断工具输出）

**回答**

Q3 已经演示了一个基础的 `ContextManager`。这一节咱们把它做得更完整一点：加入**token 预算监控**、**自动压缩（超预算时挤旧消息）**、**截断工具输出**，并能导出当前上下文供模型调用。这是上下文工程里最实用的工具之一。

> 注意：下面的代码是“玩具级”演示版，token 估算用粗略的字符数方法。真实项目中应用 `tiktoken` 或模型分词器精确计算 token，并可以接入真实的 LLM 来做摘要压缩。

---

### 完整代码：context_manager_full.py

```python
"""
context_manager_full.py：上下文窗口管理器（完整版）
支持：token 预算、滑动窗口自动压缩、截断工具输出、上下文导出。
"""

from typing import List, Dict, Any, Optional
from datetime import datetime


def estimate_tokens(text: str) -> int:
    """
    粗略估算 token 数量（演示版）。
    中文按 1 字≈1 token，英文按 4 字≈1 token。
    真实项目请用 tiktoken 或模型分词器。
    """
    chinese = len([c for c in text if '一' <= c <= '鿿'])
    others = len(text) - chinese
    return chinese + others // 4 + 1


class ContextManager:
    def __init__(
        self,
        max_tokens: int = 4000,
        max_tool_output_chars: int = 1000,
        reserve_system_prompt: bool = True,
    ):
        self.max_tokens = max_tokens
        self.max_tool_output_chars = max_tool_output_chars
        self.reserve_system_prompt = reserve_system_prompt
        self.messages: List[Dict[str, Any]] = []
        self.compression_count = 0  # 记录压缩次数，用于可观测性

    def add(
        self,
        role: str,
        content: str,
        is_tool_output: bool = False,
    ) -> None:
        """添加一条消息，工具输出会先被截断，超预算后自动压缩。"""
        if is_tool_output:
            content = self._truncate_tool_output(content)

        self.messages.append({
            "role": role,
            "content": content,
            "timestamp": datetime.now().isoformat(),
            "is_tool_output": is_tool_output,
        })

        self._compress_if_over_budget()

    def _truncate_tool_output(self, content: str) -> str:
        """截断过长的工具输出。"""
        if len(content) > self.max_tool_output_chars:
            return (
                content[: self.max_tool_output_chars]
                + f"\n……[工具输出已截断，原长 {len(content)} 字符]"
            )
        return content

    def _total_tokens(self) -> int:
        return sum(estimate_tokens(m["content"]) for m in self.messages)

    def _compress_if_over_budget(self) -> None:
        """
        超预算时，从旧到新挤掉消息（保留第一条系统消息），
        直到总 token 回到预算内或只剩一条消息。
        """
        start_index = 1 if (self.reserve_system_prompt and self.messages) else 0
        while self._total_tokens() > self.max_tokens and len(self.messages) > start_index + 1:
            removed = self.messages.pop(start_index)
            self.compression_count += 1
            print(
                f"[上下文管理] 超预算（{self._total_tokens()}>{self.max_tokens}）"
                f"，挤掉第 {start_index + 1} 条消息：{removed['role']}"
            )

    def get_messages(self) -> List[Dict[str, Any]]:
        """获取当前上下文消息列表，可直接喂给模型。"""
        return self.messages

    def get_context_text(self) -> str:
        """把当前上下文拼成可读字符串。"""
        lines = []
        for m in self.messages:
            marker = " [工具输出]" if m.get("is_tool_output") else ""
            lines.append(f"{m['role']}{marker}: {m['content']}")
        return "\n".join(lines)

    def stats(self) -> Dict[str, Any]:
        """返回上下文统计信息，用于监控和可观测性。"""
        return {
            "message_count": len(self.messages),
            "estimated_tokens": self._total_tokens(),
            "max_tokens": self.max_tokens,
            "compression_count": self.compression_count,
            "within_budget": self._total_tokens() <= self.max_tokens,
        }


# ==================== 使用示例 ====================

if __name__ == "__main__":
    cm = ContextManager(max_tokens=600, max_tool_output_chars=150)

    cm.add("system", "你是一个智能体助手，负责查天气和计算。")
    cm.add("user", "北京今天天气怎么样？")
    cm.add("assistant", "北京今天晴朗，15°C。")
    cm.add("tool", "搜索结果：北京今天晴朗，气温15°C，湿度30%，无降水。" + "y" * 400, is_tool_output=True)
    cm.add("user", "帮我算 (23 + 47) * 2 等于多少")
    cm.add("assistant", "(23 + 47) * 2 = 140")
    cm.add("user", "上海今天天气怎么样？")

    print("=== 当前上下文 ===")
    print(cm.get_context_text())

    print("\n=== 上下文统计 ===")
    stats = cm.stats()
    for k, v in stats.items():
        print(f"  {k}: {v}")
```

```

=== 当前上下文 ===
system: 你是一个智能体助手，负责查天气和计算。
assistant: 北京今天晴朗，15°C。

## Q11. 上下文窗口管理与提示词工程怎么配合？

**回答**

Q1 已经讲过：提示词工程解决“单次问答”的最优解，上下文工程解决“多轮自主任务”的最优解。两者不是替代关系，而是相辅相成。**提示词工程负责“写好单条指令”，上下文窗口管理负责“在多轮交互里把指令和历史信息塞进有限窗口”**。二者配合，才能让智能体在长对话里既听得懂当前指令，又记得之前的关键信息。

---

### 配合的核心思路

| 配合点 | 大白话解释 | 做法 |
|--------|-----------|------|
| 系统提示词常驻 | System Prompt 定义人设和规则，应该始终留在窗口里 | 用上下文管理器保留第一条系统消息，不挤掉 |
| 提示词结构化 | 把提示词拆成“背景信息/指令/工具指导/输出描述”，方便模型解析 | XML 标记或 Markdown 标题分段，配合上下文管理器导出 |
| 提示词与历史信息分层 | 提示词定“规则”，历史对话定“事实”，两者不互相覆盖 | 提示词常驻，历史按滑动窗口/摘要管理 |
| 动态检索+提示词 | 检索到的相关片段作为提示词的一部分拼进去 | 动态检索结果拼接到提示词的“背景信息”段 |

用大白话：提示词像“考试说明书”，应该一直摊在桌上；历史对话像“草稿纸”，写满了就得擦掉旧的，留下关键的。两者一起用，模型既知道考试规则，又记得刚才算过了什么。

---

### 手撕配合代码（Python 概念版）

下面是一个用 Python 演示“上下文窗口管理 + 结构化提示词”配合的概念版：上下文管理器负责保留系统提示词和控制 token 预算，提示词按 XML 结构拼接，检索片段插入“背景信息”段。

```python
"""
概念版：上下文窗口管理 + 结构化提示词配合
上下文管理器保留系统提示词并控制 token 预算，提示词按 XML 结构拼接
"""

from typing import List, Dict, Any
from datetime import datetime


def estimate_tokens(text: str) -> int:
    """粗略估算 token（演示版）。"""
    chinese = len([c for c in text if '一' <= c <= '鿿'])
    others = len(text) - chinese
    return chinese + others // 4 + 1


class ContextManager:
    """上下文窗口管理器：保留系统提示词，滑动窗口管理历史，控制 token 预算。"""

    def __init__(self, max_tokens: int = 4000):
        self.max_tokens = max_tokens
        self.messages: List[Dict[str, Any]] = []

    def add(self, role: str, content: str) -> None:
        self.messages.append({
            "role": role,
            "content": content,
            "timestamp": datetime.now().isoformat(),
        })
        self._compress_if_over_budget()

    def _total_tokens(self) -> int:
        return sum(estimate_tokens(m["content"]) for m in self.messages)

    def _compress_if_over_budget(self) -> None:
        """超预算时挤掉最旧消息，保留第一条系统提示词。"""
        while self._total_tokens() > self.max_tokens and len(self.messages) > 2:
            removed = self.messages.pop(1)
            print(f"[上下文管理] 超预算，挤掉：{removed['role']} - {removed['content'][:30]}…")

    def get_system_prompt(self) -> str:
        """获取第一条系统提示词。"""
        for m in self.messages:
            if m["role"] == "system":
                return m["content"]
        return ""

    def get_history(self) -> List[Dict[str, Any]]:
        """获取除系统提示词外的历史对话。"""
        return [m for m in self.messages if m["role"] != "system"]


def build_structured_prompt(
    system_prompt: str,
    history: List[Dict[str, Any]],
    retrieved_chunks: List[str],
    user_question: str,
) -> str:
    """
    按 XML 结构拼接提示词：
    系统提示词 + 检索片段（背景信息）+ 历史对话 + 用户问题
    """
    parts = []
    parts.append(f"<系统提示词>\n{system_prompt}\n</系统提示词>")

    if retrieved_chunks:
        parts.append("<背景信息>")
        parts.append("以下是检索到的相关资料：")
        for i, chunk in enumerate(retrieved_chunks, 1):
            parts.append(f"{i}. {chunk}")
        parts.append("</背景信息>")

    if history:
        parts.append("<历史对话>")
        for m in history:
            parts.append(f"{m['role']}: {m['content']}")
        parts.append("</历史对话>")

    parts.append(f"<用户问题>\n{user_question}\n</用户问题>")
    parts.append("\n请基于以上信息回答用户问题。")
    return "\n".join(parts)


# ==================== 运行示例 ====================

if __name__ == "__main__":
    cm = ContextManager(max_tokens=500)

    cm.add("system", "你是一个智能体，专门帮用户查询公司报销制度。")
    cm.add("user", "单餐报销上限是多少？")
    cm.add("assistant", "单餐报销上限为 200 元，需提供发票。")
    cm.add("user", "那住宿费呢？")

    retrieved_chunks = [
        "出差住宿单晚上限 500 元，需提供酒店发票。",
        "报销需在当月 25 日前提交，逾期不予受理。",
    ]

    prompt = build_structured_prompt(
        system_prompt=cm.get_system_prompt(),
        history=cm.get_history(),
        retrieved_chunks=retrieved_chunks,
        user_question="那住宿费呢？",
    )

    print("=== 拼接后的提示词 ===")
    print(prompt)

    print("\n=== 上下文统计 ===")
    print(f"总 token：{cm._total_tokens()}（预算 {cm.max_tokens}）")
```

**运行输出示例：**

```

**面试要点**：上下文窗口管理与提示词工程配合的核心是“系统提示词常驻 + 提示词结构化 + 历史按窗口管理 + 检索片段插入背景信息”。手撕时要体现：上下文管理器保留系统提示词、滑动窗口控制 token、提示词按 XML/Markdown 分段拼接、检索片段作为背景信息。

## Q12. 多轮对话中的上下文冲突怎么解决？（前后矛盾、状态覆盖）

**回答**

多轮对话里，用户可能前后说的话互相矛盾，比如第一轮说“预算 50 万”，第二轮说“预算改成 30 万”。如果上下文里两条信息都存在，模型可能困惑到底以哪个为准，导致前后矛盾。**上下文冲突解决** 就是决定“当新信息和旧信息冲突时，以哪个为准”。

---

### 冲突解决策略

| 策略 | 大白话解释 | 适用场景 | 优点 | 缺点 |
|------|-----------|---------|------|------|
| 后写入优先（LWW） | 新信息覆盖旧信息，以最新为准 | 用户偏好、预算等易变信息 | 简单、符合直觉 | 可能丢失历史事实 |
| 时间戳+版本号 | 每条信息带版本号，新版本覆盖旧版本 | 需要审计、可回溯的场景 | 可溯源、可回滚 | 实现稍复杂 |
| 字段级覆盖 | 同一字段（如预算）新值覆盖旧值，不同字段共存 | 结构化记忆（用户画像） | 精确控制 | 需要结构化存储 |
| 人工确认 | 冲突时暂停，询问用户以哪个为准 | 关键决策（付款、删除） | 最稳妥 | 交互成本高 |

用大白话：上下文冲突就像“两个说法不一样，信哪个？”最简单的办法是“信最后说的”；更严谨的办法是“带版本号，看哪个新”；最稳妥的办法是“冲突时问用户”。

---

### 冲突解决流程图（ASCII）

```
用户新输入（如"预算改成 30 万"）
        │
        ▼
┌─────────────┐
│  检测冲突   │──► 新信息与旧记忆是否同一字段且数值不同？
│  (字段匹配) │
└──────┬──────┘
       │
    ┌──┴──┐
    否     是
    │      │
    ▼      ▼
直接存储   选择策略
           │
    ┌──────┴──────┐
    │             │
后写入优先    时间戳+版本号
(直接覆盖)    (新版本覆盖旧版本)
           │
           ▼
   以最新信息为准，旧信息标记失效/归档
```

### 手撕冲突解决代码（Python 概念版）

下面是一个用 Python 演示上下文冲突解决的概念版：按字段（如“预算”）检测冲突，新值覆盖旧值，旧值标记失效并保留时间戳，可审计。

```python
"""
概念版：上下文冲突解决
按字段检测冲突，新值覆盖旧值，旧值标记失效，保留时间戳可审计
"""

from typing import List, Dict, Any, Optional
from datetime import datetime


class ContextWithConflictResolution:
    """带冲突解决的上下文记忆：结构化字段，新值覆盖旧值。"""

    def __init__(self):
        # 结构：{字段名: [记录列表，按时间倒序]}
        self.fields: Dict[str, List[Dict[str, Any]]] = {}

    def set_field(self, field: str, value: str, source: str = "user") -> None:
        """
        设置字段值。如果同一字段已有值，旧值标记失效，新值成为最新。
        """
        now = datetime.now().isoformat()
        records = self.fields.setdefault(field, [])

        # 旧值标记失效
        for rec in records:
            if rec.get("is_active", True):
                rec["is_active"] = False
                rec["superseded_at"] = now

        # 新值成为最新
        records.insert(0, {
            "value": value,
            "source": source,
            "created_at": now,
            "is_active": True,
        })
        print(f"[冲突解决] 字段 {field} 设为 {value}（旧值已标记失效）")

    def get_field(self, field: str) -> Optional[str]:
        """获取字段的最新生效值。"""
        records = self.fields.get(field, [])
        for rec in records:
            if rec.get("is_active", True):
                return rec["value"]
        return None

    def get_field_history(self, field: str) -> List[Dict[str, Any]]:
        """获取字段的所有历史版本（含失效的），用于审计。"""
        return self.fields.get(field, [])

    def detect_conflict(self, field: str, new_value: str) -> bool:
        """检测是否与当前值冲突（同一字段、数值不同）。"""
        current = self.get_field(field)
        return current is not None and current != new_value


# ==================== 运行示例 ====================

if __name__ == "__main__":
    ctx = ContextWithConflictResolution()

    # 第一轮：预算 50 万
    ctx.set_field("budget", "50 万", source="user")
    print(f"当前预算：{ctx.get_field('budget')}")

    print("\n--- 第二轮：预算改成 30 万（冲突，新值覆盖）---")
    if ctx.detect_conflict("budget", "30 万"):
        print("检测到冲突：当前 50 万，新值 30 万")
    ctx.set_field("budget", "30 万", source="user")
    print(f"当前预算：{ctx.get_field('budget')}")

    print("\n--- 历史版本（审计）---")
    for rec in ctx.get_field_history("budget"):
        status = "生效" if rec.get("is_active") else "失效"
        print(f"  {rec['created_at']} [{status}] {rec['value']} (来源: {rec['source']})")
```

**运行输出示例：**

```
[冲突解决] 字段 budget 设为 50 万（旧值已标记失效）
当前预算：50 万

--- 第二轮：预算改成 30 万（冲突，新值覆盖）---
检测到冲突：当前 50 万，新值 30 万
[冲突解决] 字段 budget 设为 30 万（旧值已标记失效）
当前预算：30 万

--- 历史版本（审计）---
2026-01-15T10:30:00 [生效] 30 万 (来源: user)
2026-01-15T10:30:00 [失效] 50 万 (来源: user)
```

可以看到，新值“30 万”覆盖了旧值“50 万”，旧值标记为失效但保留在历史记录里，可审计。`get_field('budget')` 始终返回最新生效值。

**面试要点**：上下文冲突解决的核心是“新信息与旧信息冲突时以哪个为准”。手撕时要体现：按字段检测冲突（detect_conflict）、新值覆盖旧值（set_field）、旧值标记失效（is_active=False）、保留时间戳可审计、get_field 返回最新生效值。策略包括后写入优先、时间戳+版本号、字段级覆盖、人工确认。

## Q13. 长文档的上下文处理怎么做？

**回答**

智能体有时需要处理很长的文档（比如一份几十页的合同、一本说明书、一篇长文章）。如果把整篇文档一次性塞进上下文窗口，token 很快爆掉，还会触发“上下文腐烂”导致模型视而不见。**长文档的上下文处理** 就是把长文档切成小片段，按需检索相关片段放进上下文，而不是全量塞入。

---

### 长文档处理流程

| 步骤 | 大白话解释 | 做法 |
|------|-----------|------|
| 文档切片 | 把长文档切成小片段（如每段 500 字，重叠 50 字） | 避免关键信息在边界被切断 |
| 片段向量化 | 把每个片段转成向量，存入向量数据库 | 方便按语义检索 |
| 用户提问时检索 | 把问题也转成向量，找最相关的 Top-K 片段 | 只取相关的，不放无关的 |
| 拼接进上下文 | 把检索到的片段和用户问题一起放进提示词 | 模型基于相关片段回答 |

---

### 流程图（ASCII）

```

        ▼
┌─────────────┐
│  文档切片   │──► 每段 500 字，重叠 50 字
│  (Chunking) │
└──────┬──────┘
       │
       ▼
┌─────────────┐
│  片段向量化 │──► 每个片段转成向量
│  (Embedding)│
└──────┬──────┘
       │
       ▼
┌─────────────┐
│  向量数据库 │──► 存储片段 + 向量 + 元数据
│  (存储)     │
└──────┬──────┘
       │
       ▼
用户提问 ──► 问题向量化 ──► 检索 Top-K 片段 ──► 拼接进上下文 ──► 模型回答
```

### 手撕长文档处理（Python 概念版）

下面是一个用 Python 演示长文档处理的概念版：文档切片、简单向量化（演示版用关键词集合模拟）、检索 Top-K、拼接进上下文。真实项目中替换为 Chroma / Milvus / Pinecone 等向量数据库和 Embedding 模型。

```python
"""
概念版：长文档上下文处理
文档切片 → 向量化（演示版） → 检索 Top-K → 拼接进上下文
"""

import re
from typing import List, Dict, Any


def chunk_document(text: str, chunk_size: int = 200, overlap: int = 50) -> List[str]:
    """文档切片：按固定大小切分，带重叠。"""
    if not text:
        return []
    chunks = []
    start = 0
    while start < len(text):
        end = min(start + chunk_size, len(text))
        chunks.append(text[start:end])
        if end >= len(text):
            break
        start = end - overlap
    return chunks


class SimpleVector:
    """极简向量：用关键词集合模拟向量。"""

    def __init__(self, text: str):
        self.text = text
        self.keywords = set(re.findall(r"\w+", text.lower()))

    def similarity(self, other: "SimpleVector") -> int:
        return len(self.keywords & other.keywords)


class LongDocumentProcessor:
    """长文档处理器：切片、向量化、检索、拼接上下文。"""

    def __init__(self):
        self.chunks: List[SimpleVector] = []

    def add_document(self, text: str, doc_id: str = "default") -> None:
        """添加文档：切片 + 向量化 + 存储。"""
        chunks = chunk_document(text)
        for chunk in chunks:
            self.chunks.append(SimpleVector(chunk))
        print(f"[长文档处理] 文档 {doc_id} 切成 {len(chunks)} 个片段")

    def search(self, query: str, top_k: int = 3) -> List[str]:
        """检索 Top-K 最相关片段。"""
        query_vec = SimpleVector(query)
        scored = [(query_vec.similarity(c), c.text) for c in self.chunks]
        scored = [(s, t) for s, t in scored if s > 0]
        scored.sort(key=lambda x: x[0], reverse=True)
        return [text for _, text in scored[:top_k]]

    def build_context(self, query: str, system_prompt: str, top_k: int = 3) -> str:
        """把检索到的片段拼接进上下文。"""
        retrieved = self.search(query, top_k=top_k)
        parts = [system_prompt]
        if retrieved:
            parts.append("\n## 检索到的相关片段：")
            for i, chunk in enumerate(retrieved, 1):
                parts.append(f"{i}. {chunk}")
        else:
            parts.append("\n## 检索到的相关片段：(无)")
        parts.append(f"\n## 用户问题：{query}")
        parts.append("\n## 请基于上述资料回答：")
        return "\n".join(parts)


# ==================== 运行示例 ====================

if __name__ == "__main__":
    processor = LongDocumentProcessor()

    long_doc = """

    4. 所有报销需在当月 25 日前提交，逾期不予受理。
    5. 出差交通费需附上行程单和发票。
    6. 接待费需附上接待对象名单和用餐发票。
    """

    processor.add_document(long_doc, doc_id="报销制度")

    print("=== 场景 1：问单餐报销上限 ===")

    print(ctx1)

    print("=== 场景 2：问 WiFi 密码（文档里没有）===")

## Q14. 上下文工程与 RAG 的关系？

**回答**

Q6-Q8 已经多次提到 RAG（检索增强生成）。RAG 和上下文工程的关系是：**RAG 是上下文工程中“动态检索”配方的一个具体实现方式**。上下文工程更宽泛，不仅包含 RAG，还包含提示词工程、上下文窗口管理、few-shot、工具调用优化等；而 RAG 专门解决“从外部知识库检索相关片段放进上下文”这一环。

---

### 关系对比表

| 维度 | 上下文工程 | RAG |
|------|-----------|-----|
| 范围 | 宽泛，包含所有上下文管理手段 | 较窄，专注检索增强 |
| 核心问题 | 上下文窗口里放什么、不放什么、怎么压缩 | 从知识库检索相关片段放进上下文 |
| 包含内容 | 提示词工程、窗口管理、few-shot、工具调用、动态检索(RAG) | 文档切片、嵌入、向量检索、片段拼接 |
| 关系 | RAG 是上下文工程的子集/具体实践 | 上下文工程是 RAG 的上层框架 |

用大白话：上下文工程像“整个厨房”，RAG 像“其中的一道菜”。厨房里还有炒菜（提示词工程）、切菜（窗口管理）、调味（few-shot）等，RAG 只是其中一道常用的菜。

---

### RAG 在上下文工程中的位置（ASCII）

```
上下文工程（整体框架）
        │
    ┌───┴───┐
    │       │
    ▼       ▼
提示词工程   动态检索（RAG）
(高信号低噪音)  (文档→切片→向量→检索→拼接)
        │       │
        └───┬───┘
            │
            ▼
      拼接进上下文窗口
            │
            ▼
      模型生成答案
```

---

### 何时用 RAG，何时用其他上下文工程手段

| 场景 | 推荐手段 | 原因 |
|------|---------|------|
| 用户问基于私有文档的问题（如公司报销制度） | RAG（动态检索） | 需要从外部文档检索相关片段 |
| 用户问通用常识（如“天气怎么样”） | 提示词工程 + 工具调用 | 无需外部文档，直接调工具或模型常识 |
| 长对话中需要记住之前结论 | 上下文窗口管理（滑动窗口/摘要） | 需要保留历史对话，不需要外部文档 |
| 需要模型输出特定格式 | 提示词工程（输出描述） | 通过结构化提示词控制输出 |
| 需要模型调用外部工具 | 工具调用优化（最小可行工具集） | 工具返回结果放进上下文 |

**面试要点**：RAG 是上下文工程中“动态检索”配方的具体实现，两者不是替代关系，而是上下文工程包含 RAG。上下文工程更宽泛，还包含提示词工程、窗口管理、few-shot、工具调用优化。RAG 适合基于外部文档的问答，其他手段适合不同场景。

## Q16. 上下文工程与多智能体协作的配合？

**回答**

多个智能体协作时（比如产品经理 Agent、开发者 Agent、测试员 Agent），它们之间需要共享上下文——比如项目需求、共同的结论、中间结果。如果每个 Agent 都维护独立的上下文，信息就会孤岛化，导致重复工作、前后矛盾。**上下文工程与多智能体协作的配合** 就是让多个 Agent 能共享公共上下文，又能保留各自的私有上下文，协作更高效。

---

### 多智能体上下文配合的核心设计

| 层级 | 大白话解释 | 适合存什么 |
|------|-----------|-----------|
| 公共上下文（Shared） | 所有 Agent 都能读写的上下文 | 项目需求、共同结论、已达成的决策 |
| 私有上下文（Private） | 只有特定 Agent 能读写的上下文 | 该 Agent 的草稿、中间推理、私有偏好 |
| 交接上下文（Handoff） | Agent A 把任务交给 Agent B 时传递的上下文 | 任务状态、已完成的步骤、下一步要做什么 |

用大白话：多智能体上下文就像“团队协作文档”。公共文档大家都能改（项目需求），每个人的草稿纸只有自己看（私有推理），交接单写清楚交给谁做什么（交接上下文）。

---

### 手撕多智能体上下文配合（Python 概念版）

下面是一个用 Python 演示多智能体上下文配合的概念版：公共上下文所有 Agent 共享，私有上下文只属于特定 Agent，支持交接上下文传递。

```python
"""
概念版：多智能体上下文配合
公共上下文共享 + 私有上下文隔离 + 交接上下文传递
"""

from typing import List, Dict, Any, Optional


class MultiAgentContext:
    """多智能体上下文：公共上下文 + 私有上下文 + 交接上下文。"""

    def __init__(self):
        self.shared_context: List[Dict[str, Any]] = []  # 所有 Agent 共享
        self.private_context: Dict[str, List[Dict[str, Any]]] = {}  # agent_id -> 私有
        self.handoffs: List[Dict[str, Any]] = []  # 交接记录

    def write_shared(self, content: str, source_agent: str) -> None:
        """写入公共上下文，所有 Agent 都能看到。"""
        self.shared_context.append({
            "content": content,
            "source_agent": source_agent,
        })
        print(f"[公共上下文] {source_agent} 写入：{content}")

    def write_private(self, agent_id: str, content: str) -> None:
        """写入私有上下文，只有该 Agent 能看到。"""
        self.private_context.setdefault(agent_id, []).append({
            "content": content,
        })
        print(f"[私有上下文] {agent_id} 写入：{content}")

    def handoff(self, from_agent: str, to_agent: str, task: str, next_step: str) -> None:
        """交接上下文：从一个 Agent 交给另一个 Agent。"""
        handoff = {
            "from_agent": from_agent,
            "to_agent": to_agent,
            "task": task,
            "next_step": next_step,
        }
        self.handoffs.append(handoff)
        print(f"[交接上下文] {from_agent} -> {to_agent}: {task}，下一步：{next_step}")

    def get_agent_context(self, agent_id: str) -> str:
        """获取某个 Agent 的完整上下文：公共 + 该 Agent 私有。"""
        lines = []
        if self.shared_context:
            lines.append("[公共上下文]")
            for c in self.shared_context:
                lines.append(f"- {c['content']} (来源: {c['source_agent']})")
        if agent_id in self.private_context:
            lines.append(f"[私有上下文 - {agent_id}]")
            for c in self.private_context[agent_id]:
                lines.append(f"- {c['content']}")
        relevant_handoffs = [h for h in self.handoffs if h["to_agent"] == agent_id or h["from_agent"] == agent_id]
        if relevant_handoffs:
            lines.append("[交接上下文]")
            for h in relevant_handoffs:
                lines.append(f"- {h['from_agent']} -> {h['to_agent']}: {h['task']}, 下一步: {h['next_step']}")
        return "\n".join(lines) if lines else "无上下文"


# ==================== 运行示例 ====================

if __name__ == "__main__":
    ctx = MultiAgentContext()

    # Agent A（产品经理）写入公共上下文和私有上下文
    ctx.write_shared("项目需求：开发用户登录功能", source_agent="产品经理Agent")
    ctx.write_private("产品经理Agent", "草稿：登录页面 UI 还需细化")

    # Agent B（开发者）读取上下文
    print("=== 开发者Agent 读取上下文 ===")
    print(ctx.get_agent_context("开发者Agent"))

    # Agent A 交接给 Agent B
    ctx.handoff("产品经理Agent", "开发者Agent", "开发登录功能", "写代码")

    # Agent B 写入公共上下文
    ctx.write_shared("预估开发工时：5 人日", source_agent="开发者Agent")

    # Agent C（测试员）读取上下文
    print("\n=== 测试员Agent 读取上下文 ===")
    print(ctx.get_agent_context("测试员Agent"))

    print("\n=== 产品经理Agent 读取上下文 ===")
    print(ctx.get_agent_context("产品经理Agent"))
```

**运行输出示例：**

```

[私有上下文] 产品经理Agent 写入：草稿：登录页面 UI 还需细化

## Q17. 上下文压缩算法详解？

**回答**

上下文压缩是上下文窗口管理的核心手段之一。当上下文超过 token 预算时，不能简单地全量丢弃，否则重要信息会丢失。**上下文压缩算法** 就是把冗长的上下文压缩成更短的表示，保留关键信息（结论、决策、待办），丢掉冗余对话。

---

### 常见的压缩算法

| 算法 | 大白话解释 | 适用场景 | 优点 | 缺点 |
|------|-----------|---------|------|------|
| 摘要压缩 | 用模型把历史对话压缩成一段摘要 | 长任务、需要跨轮回溯 | 保留关键信息、token 低 | 需要额外调模型，可能丢细节 |
| 提取压缩 | 只提取关键句子（如包含关键词的句子） | 需要快速压缩、不想调模型 | 快速、不需额外模型 | 可能丢失上下文关联 |
| 重要性排序 | 按重要性排序，从高到低填满预算，剩下的丢弃 | 记忆量大，要保留最重要的 | 可控、灵活 | 需要定义重要性打分 |
| 滑动窗口 | 只保留最近 N 轮 | 不需要长期回溯的对话 | 简单、固定 token | 丢早期信息 |

用大白话：上下文压缩就像“写读书笔记”。整本书太厚，你不能全部背下来，而是提取章节要点、核心结论、待办事项，写成一页纸的笔记。

### 手撕上下文压缩算法（Python 概念版）

下面是一个用 Python 演示上下文压缩算法的概念版：按重要性打分（关键词匹配模拟）、排序、贪心填充，直到 token 预算用完。

```python
"""
概念版：上下文压缩算法
按重要性打分、排序、贪心填充，直到 token 预算用完
"""

from typing import List, Dict, Any, Tuple
from datetime import datetime


def estimate_tokens(text: str) -> int:
    """粗略估算 token（演示版）。"""
    chinese = len([c for c in text if '一' <= c <= '鿿'])
    others = len(text) - chinese
    return chinese + others // 4 + 1


def score_importance(content: str) -> int:
    """
    重要性打分（演示版：用关键词匹配模拟）。
    包含“预算/决定/偏好/否决/待办/上限/流程”的得高分。
    """
    keywords = ["预算", "决定", "偏好", "否决", "待办", "上限", "流程", "审核", "付款"]
    score = 0
    for kw in keywords:
        if kw in content:
            score += 10
    return score


class ContextCompressor:
    """上下文压缩器：按重要性打分、排序、贪心填充。"""

    def __init__(self, max_tokens: int = 1000):
        self.max_tokens = max_tokens

    def compress(
        self,
        messages: List[Dict[str, Any]],
    ) -> List[Dict[str, Any]]:
        """
        压缩上下文：按重要性从高到低填充，直到 token 预算用完。
        始终保留第一条系统提示词。
        """
        if not messages:
            return []

        # 系统提示词始终保留
        system_msgs = [m for m in messages if m["role"] == "system"]
        other_msgs = [m for m in messages if m["role"] != "system"]

        # 给每条消息打分
        scored: List[Tuple[int, Dict[str, Any]]] = []
        for m in other_msgs:
            score = score_importance(m["content"])
            scored.append((score, m))

        # 按分数降序排序
        scored.sort(key=lambda x: x[0], reverse=True)

        # 贪心填充：从高分开始，直到 token 预算用完
        selected: List[Dict[str, Any]] = list(system_msgs)
        used = sum(estimate_tokens(m["content"]) for m in selected)

        for score, m in scored:
            content_tokens = estimate_tokens(m["content"])
            if used + content_tokens <= self.max_tokens:
                selected.append(m)
                used += content_tokens
            else:
                # 尝试压缩这条消息（截断）
                compressed = m["content"][: self.max_tokens - used] + "…[压缩]"
                if self.max_tokens - used > 20:  # 至少能放下一点
                    selected.append({**m, "content": compressed})
                    used = self.max_tokens
                break

        # 按原始顺序重新排列（保持对话流的可读性）
        original_order = {id(m): m for m in messages}
        selected.sort(key=lambda m: original_order[id(m)]["timestamp"] if "timestamp" in m else 0)

        print(f"[上下文压缩] 原 {len(messages)} 条 → 压缩后 {len(selected)} 条，用 {used}/{self.max_tokens} token")
        return selected


# ==================== 运行示例 ====================

        {"role": "user", "content": "你好", "timestamp": "t1"},

        {"role": "user", "content": "我的报销预算是 30 万。", "timestamp": "t3"},
        {"role": "assistant", "content": "好的，已记录预算 30 万。", "timestamp": "t4"},
        {"role": "user", "content": "我不喜欢窗边座位。", "timestamp": "t5"},
        {"role": "assistant", "content": "好的，已记录您不喜欢窗边座位。", "timestamp": "t6"},
        {"role": "user", "content": "帮我订个位。", "timestamp": "t7"},

## Q18. 上下文窗口的动态调整？

**回答**

固定的 token 预算不一定适合所有任务。简单任务（如“查天气”）不需要太多上下文，复杂任务（如“写代码并调试”）需要更多上下文。**上下文窗口的动态调整** 就是根据任务复杂度、当前对话长度、历史成功率等因素，动态调整 token 预算和压缩策略，让上下文管理更灵活。

---

### 动态调整的维度

| 维度 | 大白话解释 | 调整方式 |
|------|-----------|---------|
| 任务复杂度 | 任务越复杂，需要的上下文越多 | 复杂任务放宽预算，简单任务收紧预算 |
| 对话长度 | 对话越长，历史信息越多 | 随长度增加，逐步收紧预算或加强压缩 |
| 历史成功率 | 某种压缩策略下效果好，就多用；效果差，就少用 | 根据成功率动态调整压缩算法 |
| 模型能力 | 不同模型上下文窗口大小不同 | 根据模型窗口大小设置预算上限 |

用大白话：动态调整就像“根据任务难度调整草稿纸大小”。简单任务一张小便签就够了，复杂任务需要几张大草稿纸，模型窗口大的可以多给点纸。

### 手撕动态调整器（Python 概念版）

下面是一个用 Python 演示上下文窗口动态调整的概念版：根据任务复杂度、对话长度、历史成功率动态计算 token 预算。

```python
"""
概念版：上下文窗口动态调整器
根据任务复杂度、对话长度、历史成功率动态计算 token 预算
"""

from typing import Dict, Any, Optional
from datetime import datetime


class DynamicContextAdjuster:
    """上下文窗口动态调整器：根据任务复杂度等因素调整 token 预算。"""

    def __init__(self):
        # 基础预算（按任务复杂度）
        self.base_budgets = {
            "simple": 800,      # 简单任务，如查天气
            "medium": 2000,     # 中等任务，如写文案
            "complex": 4000,    # 复杂任务，如写代码并调试
        }
        self.history: List[Dict[str, Any]] = []  # 历史记录：{task_type, success, compression_ratio}

    def classify_task(self, user_input: str) -> str:
        """
        任务分类（演示版：用关键词匹配）。
        真实项目中可用小模型或规则引擎分类。
        """
        complex_keywords = ["代码", "调试", "算法", "架构", "重构", "优化"]
        medium_keywords = ["文案", "总结", "翻译", "写作", "分析"]
        text = user_input.lower()
        if any(kw in text for kw in complex_keywords):
            return "complex"
        if any(kw in text for kw in medium_keywords):
            return "medium"
        return "simple"

    def adjust_budget(
        self,
        user_input: str,
        conversation_length: int,  # 已有对话轮数
        recent_success_rate: float,  # 最近一次成功率（0~1）
    ) -> int:
        """
        动态调整 token 预算。
        返回调整后的预算值。
        """
        task_type = self.classify_task(user_input)
        base = self.base_budgets[task_type]

        # 根据对话长度调整：对话越长，适当收紧（避免无限增长）
        length_factor = max(0.5, 1.0 - conversation_length * 0.02)

        # 根据历史成功率调整：成功率高，放宽预算；成功率低，收紧预算
        success_factor = 0.8 + recent_success_rate * 0.4  # 0.8 ~ 1.2

        adjusted = int(base * length_factor * success_factor)

        # 限制在合理范围内
        adjusted = max(400, min(adjusted, 8000))

        print(f"[动态调整] 任务={task_type}, 基础={base}, 长度因子={length_factor:.2f}, 成功率因子={success_factor:.2f} → 预算={adjusted}")
        return adjusted

    def record_result(self, task_type: str, success: bool, compression_ratio: float) -> None:
        """记录一次任务的结果，用于后续调整参考。"""
        self.history.append({
            "task_type": task_type,
            "success": success,
            "compression_ratio": compression_ratio,
            "timestamp": datetime.now().isoformat(),
        })

    def get_recent_success_rate(self, task_type: str, window: int = 10) -> float:
        """获取某类任务最近窗口内的成功率。"""
        recent = [h for h in self.history[-window:] if h["task_type"] == task_type]
        if not recent:
            return 0.8  # 默认中等成功率
        return sum(1 for h in recent if h["success"]) / len(recent)


# ==================== 运行示例 ====================

if __name__ == "__main__":
    adjuster = DynamicContextAdjuster()

    # 记录一些历史结果
    adjuster.record_result("simple", True, 0.5)
    adjuster.record_result("simple", True, 0.6)
    adjuster.record_result("complex", True, 0.7)

    print("=== 场景 1：简单任务（查天气）===")
    budget1 = adjuster.adjust_budget("北京今天天气怎么样？", conversation_length=3, recent_success_rate=1.0)

    print("\n=== 场景 2：复杂任务（写代码并调试）===")
    budget2 = adjuster.adjust_budget("写一个 Python 爬虫并调试", conversation_length=8, recent_success_rate=0.75)

    print("\n=== 场景 3：中等任务（写文案）===")
    budget3 = adjuster.adjust_budget("写一篇产品文案", conversation_length=15, recent_success_rate=0.5)
```

**运行输出示例：**

```

[动态调整] 任务=complex, 基础=4000, 长度因子=0.84, 成功率因子=1.1 → 预算=3696

可以看到，简单任务预算较小（898），复杂任务预算较大（3696），中等任务居中（2800），且随对话长度和成功率动态调整。

**面试要点**：上下文窗口动态调整的核心是“根据任务复杂度、对话长度、历史成功率动态计算 token 预算”。手撕时要体现：classify_task 任务分类、adjust_budget 动态计算（基础×长度因子×成功率因子）、record_result 记录历史、get_recent_success_rate 获取成功率。任务复杂度越高，预算越宽；对话越长，适当收紧；成功率越低，收紧预算。

## Q19. 上下文工程的测试与评估？

**回答**

上下文工程做出来了，怎么知道它“好不好用”？需要定义评估指标，从“上下文压缩率”“回答准确率”“检索命中率”“token 成本”等方面衡量。没有指标，优化上下文工程就只能拍脑袋。

---

### 评估指标

| 指标 | 大白话解释 | 怎么算 |
|------|-----------|--------|
| 上下文压缩率 | 压缩后比原上下文减少了多少 token | (原 token - 压缩后 token) ÷ 原 token |
| 回答准确率 | 智能体的回答是不是正确、符合事实 | 人工判断或对比标准答案 |
| 检索命中率 | 检索到的片段里，有多少是真正相关的 | 相关片段数 ÷ 应该检到的片段总数 |
| 幻觉率 | 回答里有多少是编造的 | 人工抽检，发现编造内容算一次幻觉 |
| 单次对话 token 成本 | 一次对话消耗多少 token | 总 token ÷ 对话数 |

用大白话：评估上下文工程就像“考学生”。压缩率是“笔记写得精不精”，准确率是“答案对不对”，幻觉率是“会不会胡编”，检索命中率是“能不能检到重点”，token 成本是“花了多少钱”。

### 手撕评估代码（Python 概念版）

下面是一个用 Python 演示上下文工程评估的概念版：计算压缩率、回答准确率、检索命中率、幻觉率、token 成本。

```python
"""
概念版：上下文工程评估
计算压缩率、回答准确率、检索命中率、幻觉率、token 成本
"""

import re
from typing import List, Dict, Any


def estimate_tokens(text: str) -> int:
    """粗略估算 token（演示版）。"""
    chinese = len([c for c in text if '一' <= c <= '鿿'])
    others = len(text) - chinese
    return chinese + others // 4 + 1


class ContextEngineeringEvaluator:
    """上下文工程评估器。"""

    def __init__(self):
        self.results: List[Dict[str, Any]] = []

    def evaluate(
        self,
        question: str,
        answer: str,
        original_context: str,
        compressed_context: str,
        retrieved_docs: List[str],
        relevant_docs: List[str],
        ground_truth: str,
    ) -> Dict[str, Any]:
        """
        评估单个问答。
        """
        # 上下文压缩率
        orig_tokens = estimate_tokens(original_context)
        comp_tokens = estimate_tokens(compressed_context)
        compression_ratio = (orig_tokens - comp_tokens) / orig_tokens if orig_tokens else 0.0

        # 回答准确率（演示版：简单关键词匹配）
        gt_keywords = set(ground_truth.lower().split())
        ans_keywords = set(answer.lower().split())
        accuracy = len(gt_keywords & ans_keywords) / len(gt_keywords) if gt_keywords else 0.0

        # 检索命中率
        hit = len(set(retrieved_docs) & set(relevant_docs))
        recall_at_k = hit / len(relevant_docs) if relevant_docs else 0.0

        # 幻觉率（演示版：答案里出现与标准答案不符的数字）
        gt_numbers = set(re.findall(r"\d+", ground_truth))
        ans_numbers = set(re.findall(r"\d+", answer))
        hallucination = len(ans_numbers - gt_numbers) / max(len(ans_numbers), 1) if ans_numbers else 0.0

        # token 成本
        token_cost = comp_tokens

        record = {
            "question": question,
            "answer": answer,
            "compression_ratio": round(compression_ratio, 2),
            "accuracy": round(accuracy, 2),
            "recall_at_k": round(recall_at_k, 2),
            "hallucination": round(hallucination, 2),
            "token_cost": token_cost,
        }
        self.results.append(record)
        return record

    def report(self) -> str:
        """生成评估报告。"""
        if not self.results:
            return "无评估结果。"
        n = len(self.results)
        lines = ["=== 上下文工程评估报告 ==="]
        lines.append(f"测试样本数：{n}")
        lines.append(f"平均压缩率：{sum(r['compression_ratio'] for r in self.results) / n * 100:.1f}%")
        lines.append(f"平均回答准确率：{sum(r['accuracy'] for r in self.results) / n * 100:.1f}%")
        lines.append(f"平均检索命中率：{sum(r['recall_at_k'] for r in self.results) / n * 100:.1f}%")
        lines.append(f"平均幻觉率：{sum(r['hallucination'] for r in self.results) / n * 100:.1f}%")
        lines.append(f"平均单次对话 token 成本：{sum(r['token_cost'] for r in self.results) / n:.0f} token")
        return "\n".join(lines)


# ==================== 运行示例 ====================

if __name__ == "__main__":
    evaluator = ContextEngineeringEvaluator()

    # 案例 1：压缩后准确率高
    evaluator.evaluate(
        question="单餐报销上限是多少？",
        answer="单餐报销上限是 200 元。",
        original_context="单餐餐饮报销上限为 200 元，需提供发票。交通费报销：出租车单程上限 100 元，地铁公交实报实销。住宿费报销：出差住宿单晚上限 500 元。",
        compressed_context="单餐报销上限 200 元。",
        retrieved_docs=["单餐餐饮报销上限为 200 元，需提供发票。"],
        relevant_docs=["单餐餐饮报销上限为 200 元，需提供发票。"],
        ground_truth="单餐报销上限是 200 元。",
    )

    # 案例 2：压缩过度，准确率下降
    evaluator.evaluate(

        answer="报销上限不详。",

## Q21. 上下文工程与安全的关系？

**回答**

上下文工程涉及把大量信息（包括用户输入、工具输出、检索片段、历史对话）都放进模型的上下文窗口。如果这些信息里包含敏感数据（手机号、身份证、银行卡、商业机密、个人隐私），就可能被模型“学进去”或在输出中泄露。**上下文工程与安全的关系** 就是：在管理上下文的同时，做好敏感数据的脱敏、访问控制、审计日志，防止泄露和滥用。

---

### 安全相关的核心措施

| 措施 | 大白话解释 | 作用 |
|------|-----------|------|
| 敏感数据脱敏 | 上下文写入前，把手机号、身份证号等隐去一部分 | 防止隐私在上下文中明文暴露 |
| 不把机密写进系统提示词 | 提示词里不放公司机密、用户隐私 | 防止模型把机密泄露给其他用户或学进去 |
| 访问控制 | 不同用户/租户只能看自己该看的上下文 | 防止越权查看他人上下文 |
| 审计日志 | 记录谁、什么时候、把什么信息放进了上下文 | 出事可追溯 |
| 上下文隔离 | 不同用户的上下文物理或逻辑隔离 | 租户 A 的上下文不泄露给租户 B |

用大白话：上下文安全就像“给档案柜加锁”。敏感信息涂抹（脱敏）、重要文件不带进会议室（不写提示词）、只有授权人才能看（访问控制）、每次翻阅都登记（审计日志）、不同租户的档案放不同柜子（上下文隔离）。

---

### 手撕安全上下文（Python 概念版）

下面是一个用 Python 演示安全上下文的概念版：上下文写入前自动脱敏敏感信息，按用户 ID 隔离访问，开启审计日志。

```python
"""
概念版：安全上下文系统
上下文写入前自动脱敏，按用户 ID 隔离，开启审计日志
"""

import re
from typing import List, Dict, Any, Optional
from datetime import datetime


def desensitize(text: str) -> str:
    """对文本中的敏感信息进行脱敏。"""
    # 脱敏手机号：13800138000 -> 138****8000
    text = re.sub(r"1[3-9]\d{9}", lambda m: m.group()[:3] + "****" + m.group()[-4:], text)
    # 脱敏身份证号：110101199001011234 -> 110101********1234
    text = re.sub(r"\d{17}[\dXx]", lambda m: m.group()[:6] + "********" + m.group()[-4:], text)
    # 脱敏银行卡号（16 位数字）
    text = re.sub(r"\b\d{16}\b", lambda m: "**** **** **** " + m.group()[-4:], text)
    return text


class SecureContext:
    """带安全保护的上下文系统：脱敏 + 访问控制 + 审计日志。"""

    def __init__(self):
        self.user_contexts: Dict[str, List[Dict[str, Any]]] = {}  # user_id -> 上下文
        self.audit_log: List[Dict[str, Any]] = []  # 审计日志

    def add(
        self,
        user_id: str,
        role: str,
        content: str,
        operator: Optional[str] = None,
    ) -> None:
        """
        添加一条上下文记录：写入前自动脱敏，按用户隔离，记录审计日志。
        """
        safe_content = desensitize(content)
        self.user_contexts.setdefault(user_id, []).append({
            "role": role,
            "content": safe_content,
            "timestamp": datetime.now().isoformat(),
        })
        # 审计日志
        self.audit_log.append({
            "user_id": user_id,
            "operator": operator or "system",
            "role": role,
            "content_preview": safe_content[:50],
            "timestamp": datetime.now().isoformat(),
        })
        print(f"[安全上下文] 用户 {user_id} 添加（脱敏后）：{safe_content}")

    def get_context(self, user_id: str, operator: Optional[str] = None) -> List[str]:
        """
        获取用户上下文：访问控制，只返回当前用户的上下文。
        """
        # 访问控制：只能看自己的上下文（演示版）
        contexts = self.user_contexts.get(user_id, [])
        # 审计：记录查询行为
        self.audit_log.append({
            "user_id": user_id,
            "operator": operator or "system",
            "role": "read",
            "content_preview": f"查询 {len(contexts)} 条记录",
            "timestamp": datetime.now().isoformat(),
        })
        return [c["content"] for c in contexts]

    def get_audit_log(self) -> List[Dict[str, Any]]:
        """获取审计日志。"""
        return self.audit_log


# ==================== 运行示例 ====================

if __name__ == "__main__":
    ctx = SecureContext()

    # 用户 A 的输入含敏感信息
    ctx.add(
        "user_a",
        "user",
        "我的手机号是 13800138000，身份证号是 110101199001011234，银行卡是 6228480402564690018。",
        operator="user_a",
    )

    # 用户 B 的输入
    ctx.add("user_b", "user", "我喜欢窗边座位，不喝咖啡。", operator="user_b")

    print("\n=== 用户 A 获取自己的上下文 ===")
    for c in ctx.get_context("user_a", operator="user_a"):
        print(f"  - {c}")

    print("\n=== 用户 B 获取上下文（看不到用户 A 的）===")
    for c in ctx.get_context("user_b", operator="user_b"):
        print(f"  - {c}")
    print("  (访问控制生效，用户 B 看不到用户 A 的上下文)")

    print("\n=== 审计日志 ===")
    for log in ctx.get_audit_log():
        print(f"  {log['timestamp']} {log['operator']} 操作了用户 {log['user_id']} 的 {log['role']}")
```

**运行输出示例：**

```
[安全上下文] 用户 user_a 添加（脱敏后）：我的手机号是 138****8000，身份证号是 110101********1234，银行卡是 **** **** **** 0018。
[安全上下文] 用户 user_b 添加（脱敏后）：我喜欢窗边座位，不喝咖啡。

=== 用户 A 获取自己的上下文 ===
  - 我的手机号是 138****8000，身份证号是 110101********1234，银行卡是 **** **** **** 0018。

=== 用户 B 获取上下文（看不到用户 A 的）===

  (访问控制生效，用户 B 看不到用户 A 的上下文)

=== 审计日志 ===

  2026-01-15T10:30:00 user_b 操作了用户 user_b 的 user
  2026-01-15T10:30:00 user_a 操作了用户 user_a 的 read

可以看到，写入时敏感信息已被脱敏，用户 B 无法获取用户 A 的上下文，所有操作都记录在审计日志里。

## Q22. 上下文工程与多模态的配合？

**回答**

现在的大模型不只处理文本，很多模型（如 GPT-4o、Claude 3、通义千问 VL）也能看懂图片、听懂音频、理解视频。**上下文工程与多模态的配合** 就是把图片、音频、视频等多模态内容也纳入上下文管理——把它们转成模型能接受的表示，与文本一起放进上下文窗口，并控制 token 预算。

### 多模态上下文的处理方式

| 模态 | 大白话解释 | 典型处理方式 |

| 文本 | 普通文字 | 直接放进上下文 |

### 手撕多模态上下文（Python 概念版）

下面是一个用 Python 演示多模态上下文的概念版：把图片（Base64/URL）和文字组合成多模态消息，并控制 token 预算。不依赖真实模型 API，直接运行即可看懂多模态上下文的组织方式。

```python
"""
概念版：多模态上下文
把图片（Base64/URL）和文字组合成多模态消息，并控制 token 预算
"""

import base64
from typing import List, Dict, Any, Optional


class MultiModalContext:
    """多模态上下文：支持文字 + 图片，控制 token 预算。"""

    def __init__(self, max_tokens: int = 4000):
        self.max_tokens = max_tokens
        self.contents: List[Dict[str, Any]] = []  # 每项 {"type": "text", ...} 或 {"type": "image_url", ...}

    def add_text(self, text: str, token_estimate: Optional[int] = None) -> None:
        """添加一段文字内容。"""
        tokens = token_estimate or max(1, len(text) // 4)
        self.contents.append({
            "type": "text",
            "text": text,
            "tokens": tokens,
        })

    def add_image_base64(self, image_path: str, token_estimate: int = 1000) -> None:
        """把本地图片转成 Base64，添加为图片内容。"""
        with open(image_path, "rb") as f:
            b64 = base64.b64encode(f.read()).decode("utf-8")
        self.contents.append({
            "type": "image_url",
            "image_url": {"url": f"data:image/png;base64,{b64}"},
            "tokens": token_estimate,  # 图片通常占用较多 token
        })

    def add_image_url(self, image_url: str, token_estimate: int = 1000) -> None:
        """直接添加一张网络图片 URL。"""
        self.contents.append({
            "type": "image_url",
            "image_url": {"url": image_url},
            "tokens": token_estimate,
        })

    def total_tokens(self) -> int:
        """计算当前多模态上下文的总 token 数。"""
        return sum(c.get("tokens", 1) for c in self.contents)

    def compress_if_over_budget(self) -> None:
        """超预算时，挤掉最旧的非系统内容，保留文字优先。"""
        while self.total_tokens() > self.max_tokens and len(self.contents) > 1:
            removed = self.contents.pop(1)
            print(f"[多模态上下文] 超预算，挤掉：{removed['type']}")

    def to_openai_format(self) -> List[Dict[str, Any]]:
        """转成 OpenAI 多模态消息格式。"""
        return [
            {
                "type": c["type"],
                **({"text": c["text"]} if c["type"] == "text" else {"image_url": c["image_url"]}),
            }
            for c in self.contents
        ]


# ==================== 运行示例 ====================

if __name__ == "__main__":
    ctx = MultiModalContext(max_tokens=2000)

    ctx.add_text("请描述这张图片里有什么？", token_estimate=50)
    ctx.add_image_url("https://example.com/cat.jpg", token_estimate=1000)
    ctx.add_text("这张图拍在哪里？", token_estimate=30)

    print("=== 多模态上下文 ===")
    for c in ctx.contents:
        if c["type"] == "text":
            print(f"  [文字] {c['text']} ({c['tokens']} token)")
        else:
            print(f"  [图片] image_url ({c['tokens']} token)")

    print(f"\n总 token：{ctx.total_tokens()}（预算 {ctx.max_tokens}）")

    print("\n=== OpenAI 格式输出 ===")
    import json
    print(json.dumps(ctx.to_openai_format(), ensure_ascii=False, indent=2))
```

## Q23. 上下文工程与成本控制？

**回答**

上下文工程直接影响 token 消耗，而 token 消耗直接对应成本。上下文越长、调用越频繁，成本越高。**上下文工程与成本控制** 就是通过优化上下文（压缩、截断、缓存、选对模型）来降低 token 消耗，控制成本。

---

### 成本控制的核心手段

| 手段 | 大白话解释 | 作用 |
|------|-----------|------|
| 上下文压缩 | 把冗长历史压缩成摘要 | 减少 token，降低成本 |
| 截断工具输出 | 工具返回只保留关键字段 | 减少冗余 token |
| 缓存中间结果 | 常见问题缓存答案，不必每次都调模型 | 零 token 成本 |
| 选对模型 | 简单任务用便宜模型，复杂任务才用贵模型 | 按需付费，避免杀鸡用牛刀 |
| 动态检索 | 只放 Top-K 相关片段，不全量塞 | 减少无关 token |
| 设置 token 预算 | 超预算自动压缩或拒绝 | 防止无限烧钱 |

用大白话：成本控制就像“省水”。上下文压缩像“节水龙头”，缓存像“水循环”，选对模型像“不用大锅煮小菜”，动态检索像“只取需要的水”。

### 手撕成本控制（Python 概念版）

下面是一个用 Python 演示上下文工程成本控制的概念版：缓存中间结果、选对模型、动态检索、上下文压缩，计算 token 成本。

```python
"""
概念版：上下文工程成本控制
缓存 + 选对模型 + 动态检索 + 上下文压缩，计算 token 成本
"""

from typing import List, Dict, Any, Optional
import hashlib


def estimate_tokens(text: str) -> int:
    """粗略估算 token（演示版）。"""
    chinese = len([c for c in text if '一' <= c <= '鿿'])
    others = len(text) - chinese
    return chinese + others // 4 + 1


class CostController:
    """成本控制器：缓存 + 选对模型 + 动态检索 + 上下文压缩。"""

    def __init__(self):
        self.cache: Dict[str, str] = {}  # 查询缓存
        self.total_tokens = 0
        self.total_cost = 0.0  # 元
        # 演示版模型单价（元 / 1K token）
        self.model_prices = {
            "cheap": 0.001,
            "expensive": 0.03,
        }

    def _cache_key(self, question: str) -> str:
        return hashlib.md5(question.encode()).hexdigest()

    def get_cached_answer(self, question: str) -> Optional[str]:
        """查询缓存，命中返回缓存答案，零 token 成本。"""
        return self.cache.get(self._cache_key(question))

    def cache_answer(self, question: str, answer: str) -> None:
        """把答案缓存起来。"""
        self.cache[self._cache_key(question)] = answer

    def select_model(self, question: str) -> str:
        """
        选对模型：简单任务用便宜模型，复杂任务用贵模型。
        演示版：用关键词匹配。
        """
        complex_keywords = ["代码", "调试", "架构", "算法", "重构"]
        if any(kw in question for kw in complex_keywords):
            return "expensive"
        return "cheap"

    def compress_context(self, context: str, max_tokens: int = 500) -> str:
        """上下文压缩：超过预算就截断。"""
        if estimate_tokens(context) <= max_tokens:
            return context
        # 简单截断（演示版）
        chars = int(max_tokens * 4)
        return context[:chars] + "\n……[上下文已压缩]"

    def estimate_cost(self, model: str, tokens: int) -> float:
        """估算成本（元）。"""
        price = self.model_prices.get(model, 0.001)
        return tokens / 1000 * price

    def process(
        self,
        question: str,
        context: str,
    ) -> Dict[str, Any]:
        """
        处理一个请求：缓存查询 → 选模型 → 压缩上下文 → 估算成本 → 缓存答案。
        """
        # 第一步：缓存查询
        cached = self.get_cached_answer(question)
        if cached:
            return {
                "answer": cached,
                "tokens": 0,
                "cost": 0.0,
                "cached": True,
                "model": None,
            }

        # 第二步：选模型
        model = self.select_model(question)

        # 第三步：压缩上下文
        compressed = self.compress_context(context)

        # 第四步：估算 token 和成本
        tokens = estimate_tokens(compressed + question)
        cost = self.estimate_cost(model, tokens)
        self.total_tokens += tokens
        self.total_cost += cost

        # 第五步：生成答案（演示版：直接返回模拟答案）
        answer = f"[{model} 模型] 基于压缩后的上下文回答：{question}"

        # 第六步：缓存答案
        self.cache_answer(question, answer)

        return {
            "answer": answer,
            "tokens": tokens,
            "cost": cost,
            "cached": False,
            "model": model,
        }

    def get_stats(self) -> Dict[str, Any]:
        """获取成本统计。"""
        return {
            "total_tokens": self.total_tokens,
            "total_cost": round(self.total_cost, 4),
            "cache_size": len(self.cache),
        }


# ==================== 运行示例 ====================

if __name__ == "__main__":
    controller = CostController()

    context = "公司报销制度：单餐餐饮报销上限为 200 元，需提供发票。交通费报销：出租车和网约车单程上限 100 元，地铁和公交实报实销。住宿费报销：出差住宿单晚上限 500 元，需提供酒店发票。所有报销需在当月 25 日前提交，逾期不予受理。"

    print("=== 场景 1：简单任务（查报销上限）===")
    r1 = controller.process("单餐报销上限是多少？", context)
    print(f"模型：{r1['model']}, token：{r1['tokens']}，成本：{r1['cost']:.4f} 元，缓存：{r1['cached']}")

    print("\n=== 场景 2：复杂任务（写代码调试）===")
    r2 = controller.process("写一个 Python 爬虫并调试报错", context)
    print(f"模型：{r2['model']}, token：{r2['tokens']}，成本：{r2['cost']:.4f} 元，缓存：{r2['cached']}")

    print("\n=== 场景 3：重复查询（缓存命中，零 token）===")
    r3 = controller.process("单餐报销上限是多少？", context)
    print(f"模型：{r3['model']}, token：{r3['tokens']}，成本：{r3['cost']:.4f} 元，缓存：{r3['cached']}")

    print("\n=== 成本统计 ===")
    print(controller.get_stats())
```

**运行输出示例：**

```

模型：cheap, token：148，成本：0.0001 元，缓存：False

=== 场景 2：复杂任务（写代码调试）===
模型：expensive, token：166，成本：0.0050 元，缓存：False

=== 场景 3：重复查询（缓存命中，零 token）===

可以看到，简单任务用便宜模型，复杂任务用贵模型，重复查询命中缓存零 token 成本，总成本被有效控制。

**面试要点**：成本控制的核心是“缓存中间结果 + 选对模型 + 动态检索 + 上下文压缩 + 设置 token 预算”。手撕时要体现：get_cached_answer/cache_answer 缓存、select_model 选模型、compress_context 压缩、estimate_cost 计算成本、get_stats 统计。简单任务用便宜模型，复杂任务用贵模型，重复查询走缓存。

## Q24. 上下文工程的常见坑与避坑指南？

**回答**

上下文工程很好用，但新手容易踩一些坑。如果不了解这些坑，上手后可能发现“越优化越差、越压越乱”。下面咱们用大白话把上下文工程的常见坑和避坑方法挑明，帮你少走弯路。

---

### 常见坑与避坑

| 坑 | 大白话解释 | 避坑方法 |
|------|-----------|---------|
| 坑 1：为了用上下文工程而用上下文工程 | 把简单任务也搞成复杂的 RAG+压缩+缓存，反而慢且贵 | 简单任务直接调模型，不需要上下文工程 |
| 坑 2：上下文太长，全量塞进去 | 什么都塞进上下文，token 爆掉，模型视而不见 | 设置 token 预算，超预算自动压缩 |
| 坑 3：few-shot 放太多示例 | 放 20 条罕见案例，上下文被示例占满，正常问题没空间 | 3~5 个常见场景，典型优于边缘 |
| 坑 4：工具输出不截断 | 工具返回整页 HTML，塞满上下文，关键信息被淹没 | 截断工具输出，只保留关键字段 |
| 坑 5：系统提示词被挤掉 | 滑动窗口把系统提示词也挤了，模型丢了人设 | 系统提示词常驻，不挤掉 |
| 坑 6：敏感信息写进上下文 | 把手机号、身份证写进上下文，模型可能泄露 | 写入前脱敏，敏感行业私有化部署 |
| 坑 7：不做评估，凭感觉优化 | 改了压缩策略不知道好不好 | 定期跑评估指标（压缩率/准确率/命中率） |

用大白话：避坑指南就像“驾驶指南”。不要为了开车而开车，简单路走直道；不要超载，设置限重；不要带太多杂物，只带需要的；不要挡住挡风玻璃，系统提示词要常驻；不要带违禁品，敏感信息要脱敏；不要凭感觉开车，要看仪表盘评估。

### 用 Python 做简单的避坑检查（概念版）

下面是一个用 Python 演示避坑检查的概念版：检查上下文是否有常见问题（系统提示词缺失、token 超标、敏感信息未脱敏等）。

```python
"""
概念版：上下文工程避坑检查
检查系统提示词缺失、token 超标、敏感信息未脱敏等常见问题
"""

import re
from typing import List, Dict, Any


def estimate_tokens(text: str) -> int:
    """粗略估算 token（演示版）。"""
    chinese = len([c for c in text if '一' <= c <= '鿿'])
    others = len(text) - chinese
    return chinese + others // 4 + 1


def check_context_issues(
    messages: List[Dict[str, Any]],
    max_tokens: int = 4000,
) -> List[Dict[str, str]]:
    """
    检查上下文的常见问题，返回问题列表。
    """
    issues = []

    # 检查 1：系统提示词缺失
    has_system = any(m["role"] == "system" for m in messages)
    if not has_system:
        issues.append({
            "type": "缺失系统提示词",
            "severity": "高",
            "建议": "添加系统提示词，定义模型人设和规则",
        })

    # 检查 2：token 超标
    total_tokens = sum(estimate_tokens(m["content"]) for m in messages)
    if total_tokens > max_tokens:
        issues.append({
            "type": "token 超标",
            "severity": "高",
            "建议": f"当前 {total_tokens} token，超过预算 {max_tokens}，需要压缩",
        })

    # 检查 3：敏感信息未脱敏
    sensitive_patterns = [
        r"1[3-9]\d{9}",  # 手机号
        r"\d{17}[\dXx]",  # 身份证号
        r"\b\d{16}\b",  # 银行卡号
    ]
    for i, m in enumerate(messages):
        for pattern in sensitive_patterns:
            if re.search(pattern, m["content"]):
                issues.append({
                    "type": "敏感信息未脱敏",
                    "severity": "高",
                    "建议": f"第 {i+1} 条消息包含可能的敏感信息，建议脱敏后再写入",
                })
                break

    # 检查 4：few-shot 示例过多（简单判断：示例条目过多）
    example_count = sum(1 for m in messages if "示例" in m["content"] or "Example" in m["content"])
    if example_count > 10:
        issues.append({
            "type": "few-shot 示例过多",
            "severity": "中",
            "建议": f"当前 {example_count} 条示例，建议精简到 3~5 个典型场景",
        })

    return issues


# ==================== 运行示例 ====================

        {"role": "user", "content": "我的手机号是 13800138000，帮我查天气"},
        {"role": "assistant", "content": "北京今天晴朗，15°C。"},
        {"role": "user", "content": "示例 1：..."},
        {"role": "user", "content": "示例 2：..."},
        {"role": "user", "content": "示例 3：..."},
        {"role": "user", "content": "示例 4：..."},
        {"role": "user", "content": "示例 5：..."},
        {"role": "user", "content": "示例 6：..."},
        {"role": "user", "content": "示例 7：..."},
        {"role": "user", "content": "示例 8：..."},
        {"role": "user", "content": "示例 9：..."},

## Q26. 上下文工程与多语言的配合？

**回答**

智能体可能面对不同语言的用户（中文、英文、日文等）。用户用中文问问题，智能体应该用中文回答；用户用英文问，应该用英文回答。**上下文工程与多语言的配合** 就是让上下文按语言组织、检索和生成，避免中文用户看到英文上下文、英文用户被中文上下文干扰，同时又能在合理的情况下跨语言共享通用知识。

---

### 多语言上下文的核心设计

| 策略 | 大白话解释 | 适合场景 | 优点 | 缺点 |
|------|-----------|---------|------|------|
| 按语言隔离 | 每种语言单独存一份上下文，互不干扰 | 用户语言固定、上下文语言敏感 | 简单、互不干扰 | 同一信息需重复存多份 |
| 按语言共享 + 语言标记 | 所有语言上下文存一起，每条带语言标记，检索时过滤 | 上下文量小、需要跨语言复用 | 存储省、易复用 | 检索可能混入其他语言 |
| 通用知识共享、私有上下文隔离 | 常识/文档等通用知识跨语言共享，用户偏好等私有上下文按语言隔离 | 大多数多语言场景 | 兼顾复用与隔离 | 实现稍复杂 |

用大白话：多语言上下文就像“多语种图书馆”。中文书放中文书架，英文书放英文书架，读者进来按自己语言找；但百科全书这种通用知识，所有语言读者都能查。

---

### 手撕多语言上下文（Python 概念版）

下面是一个用 Python 演示多语言上下文的概念版：每条上下文带语言标记 locale，检索时按用户语言过滤，通用知识跨语言共享。

```python
"""
概念版：多语言上下文系统
每条上下文带 locale 标记，检索按用户语言过滤，通用知识跨语言共享
"""

from typing import List, Dict, Any, Optional


class MultiLingualContext:
    """多语言上下文库：每条上下文带 locale，检索按用户语言过滤。"""

    def __init__(self):
        # 结构：{locale: [上下文列表]}
        self.contexts: Dict[str, List[Dict[str, Any]]] = {}
        # 通用知识库（跨语言共享，不带 locale 限制）
        self.general_kb: List[Dict[str, Any]] = []

    def add(self, content: str, locale: str, is_general: bool = False) -> None:
        """
        添加一条上下文。
        :param content: 上下文内容
        :param locale: 语言代码，如 "zh-CN" / "en-US" / "ja-JP"
        :param is_general: 是否为通用知识（跨语言共享）
        """
        record = {"content": content, "locale": locale}
        if is_general:
            self.general_kb.append(record)
            print(f"[多语言上下文] 已添加通用知识 [{locale}]：{content}")
        else:
            self.contexts.setdefault(locale, []).append(record)
            print(f"[多语言上下文] 已添加私有上下文 [{locale}]：{content}")

    def recall(
        self,
        keyword: str,
        user_locale: str,
        include_general: bool = True,
        limit: int = 5,
    ) -> List[str]:
        """
        检索上下文。
        :param keyword: 关键词
        :param user_locale: 用户语言
        :param include_general: 是否包含通用知识库
        :param limit: 最多返回多少条
        :return: 匹配的上下文内容列表
        """
        results: List[str] = []

        # 1. 先检索用户语言的私有上下文
        for rec in self.contexts.get(user_locale, []):
            if keyword.lower() in rec["content"].lower():
                results.append(rec["content"])
                if len(results) >= limit:
                    return results

        # 2. 再检索通用知识库（跨语言共享）
        if include_general:
            for rec in self.general_kb:
                if keyword.lower() in rec["content"].lower():
                    results.append(rec["content"])
                    if len(results) >= limit:
                        break

        return results


# ==================== 运行示例 ====================

if __name__ == "__main__":
    ctx = MultiLingualContext()

    # 中文用户的私有上下文
    ctx.add("用户喜欢窗边座位", locale="zh-CN")
    ctx.add("报销预算已设为 30 万", locale="zh-CN")

    # 英文用户的私有上下文
    ctx.add("User prefers window seats", locale="en-US")
    ctx.add("Reimbursement budget set to 300k", locale="en-US")

    # 通用知识（跨语言共享）
    ctx.add("公司报销制度：单餐不超过 200 元", locale="zh-CN", is_general=True)
    ctx.add("Company policy: single meal reimbursement not exceeding 200 yuan", locale="en-US", is_general=True)

    print("\n--- 中文用户检索（locale=zh-CN）---")
    for c in ctx.recall("预算", user_locale="zh-CN"):
        print(f"  - {c}")

    print("\n--- 英文用户检索（locale=en-US）---")
    for c in ctx.recall("budget", user_locale="en-US"):
        print(f"  - {c}")

    print("\n--- 中文用户检索通用知识（keyword=报销制度）---")
    for c in ctx.recall("报销制度", user_locale="zh-CN"):
        print(f"  - {c}")
```

**运行输出示例：**

```
[多语言上下文] 已添加私有上下文 [zh-CN]：用户喜欢窗边座位
[多语言上下文] 已添加私有上下文 [zh-CN]：报销预算已设为 30 万
[多语言上下文] 已添加私有上下文 [en-US]：User prefers window seats
[多语言上下文] 已添加私有上下文 [en-US]：Reimbursement budget set to 300k
[多语言上下文] 已添加通用知识 [zh-CN]：公司报销制度：单餐不超过 200 元
[多语言上下文] 已添加通用知识 [en-US]：Company policy: single meal reimbursement not exceeding 200 yuan

--- 中文用户检索（locale=zh-CN）---

--- 英文用户检索（locale=en-US）---

可以看到，中文用户只能检索到中文私有上下文，英文用户只能检索到英文私有上下文，通用知识跨语言共享。

**面试要点**：多语言上下文的核心是“每条上下文带 locale 标记、检索时按用户语言过滤、通用知识跨语言共享”。手撕时要体现：contexts 按 locale 分组、general_kb 跨语言共享、recall 按 user_locale 过滤私有上下文 + 可选包含通用知识。

## Q27. 上下文工程的长期演进？

**回答**

上下文不是静止的，随着时间的推移，大量零散的上下文片段（具体的对话、具体的决策）可以沉淀、提炼成更通用的知识（比如“用户一直喜欢窗边座位”→“用户偏好窗边座位”→“该类用户偏好安静座位”）。**上下文工程的长期演进** 就是把碎片化上下文逐步升级为结构化知识，让智能体越用越聪明。

---

### 上下文演进的层次

| 演进层次 | 大白话解释 | 例子 |
|---------|-----------|------|
| 碎片上下文 | 具体的对话片段、具体的决策 | “用户周一说预算 50 万”，“用户周三说预算改 30 万” |
| 模式提炼 | 从碎片中提炼出规律和偏好 | “用户倾向于较低预算，偏好非窗边座位” |
| 结构化知识 | 把模式固化为可复用的知识条目 | “该用户类别：价格敏感型，偏好安静座位” |
| 知识复用 | 新任务直接应用沉淀的知识 | 新用户如果也是价格敏感型，直接套用该知识 |

### 手撕上下文长期演进（Python 概念版）

下面是一个用 Python 演示上下文长期演进的概念版：从碎片上下文中提炼模式，固化为结构化知识，供新任务复用。

```python
"""
概念版：上下文长期演进
碎片上下文 → 模式提炼 → 结构化知识 → 知识复用
"""

from typing import List, Dict, Any


class ContextEvolution:
    """上下文长期演进：碎片上下文 → 模式提炼 → 结构化知识 → 知识复用。"""

    def __init__(self):
        self.fragment_contexts: List[str] = []  # 碎片上下文
        self.patterns: List[str] = []  # 提炼的模式
        self.structured_knowledge: List[str] = []  # 结构化知识

    def add_fragment(self, fragment: str) -> None:
        """添加一条碎片上下文。"""
        self.fragment_contexts.append(fragment)
        print(f"[碎片上下文] 已添加：{fragment}")

    def extract_patterns(self) -> None:
        """从碎片上下文中提炼模式（演示版：简单关键词规则）。"""
        all_text = " ".join(self.fragment_contexts).lower()
        patterns = []

        if "预算" in all_text and ("30 万" in all_text or "50 万" in all_text):
            patterns.append("用户倾向于较低预算（30~50 万范围）")
        if "窗边" in all_text and ("不喜欢" in all_text or "避开" in all_text):
            patterns.append("用户偏好非窗边座位")
        if "报销" in all_text:
            patterns.append("用户频繁涉及报销流程")

        for p in patterns:
            if p not in self.patterns:
                self.patterns.append(p)
                print(f"[模式提炼] 已提炼：{p}")

    def solidify_knowledge(self) -> None:
        """把提炼的模式固化为结构化知识。"""
        for pattern in self.patterns:
            knowledge = f"[知识条目] {pattern}，来源：碎片上下文聚合"
            if knowledge not in self.structured_knowledge:
                self.structured_knowledge.append(knowledge)
                print(f"[结构化知识] 已固化：{knowledge}")

    def reuse_knowledge(self, new_user_profile: str) -> List[str]:
        """
        知识复用：根据新用户画像，匹配可复用的结构化知识。
        """
        matched = []
        for knowledge in self.structured_knowledge:
            # 演示版：简单关键词匹配
            if any(kw in new_user_profile.lower() for kw in ["预算", "价格敏感", "窗边", "报销"]):
                matched.append(knowledge)
        return matched


# ==================== 运行示例 ====================

if __name__ == "__main__":
    evo = ContextEvolution()

    # 添加碎片上下文
    evo.add_fragment("用户周一说预算 50 万，后来改成 30 万。")
    evo.add_fragment("用户说不喜欢窗边座位，喜欢安静点。")
    evo.add_fragment("用户问了两次报销流程。")

    print("\n=== 模式提炼 ===")
    evo.extract_patterns()

    print("\n=== 知识固化 ===")
    evo.solidify_knowledge()

    print("\n=== 知识复用：新用户画像 ===")
    new_profile = "新用户，价格敏感，关心报销流程，不喜欢窗边座位。"
    matched = evo.reuse_knowledge(new_profile)
    print(f"新用户画像：{new_profile}")
    print("匹配到的可复用知识：")
    for k in matched:
        print(f"  - {k}")
```

```

## Q28. 上下文工程与多智能体记忆共享与上下文的区别？

**回答**

Q16 已经讲了多智能体上下文配合（公共上下文 + 私有上下文 + 交接上下文）。但“上下文”和“记忆”是两个概念，容易混淆。**上下文** 指的是当前对话/任务里喂给模型的信息（短期、即时）；**记忆** 指的是跨会话、长期保存的信息（长期、持久）。多智能体协作时，既要共享上下文（当前任务的中间状态），又要共享记忆（历史决策、用户偏好），两者配合但各有侧重。

---

### 上下文 vs 记忆的区别

| 维度 | 上下文（Context） | 记忆（Memory） |
|------|------------------|---------------|
| 生命周期 | 短期，当前会话/任务内 | 长期，跨会话、跨任务 |
| 存储位置 | 上下文窗口（模型输入） | 向量数据库、JSON、数据库等 |
| 读写频率 | 极高，每轮都读写 | 较低，需要时检索 |
| 容量限制 | 受 token 窗口限制 | 受存储容量限制 |
| 典型内容 | 当前对话历史、工具输出、中间结果 | 用户偏好、历史决策、知识库文档 |
| 多智能体协作 | 公共上下文（当前任务状态）、私有上下文 | 公共记忆（共同结论）、私有记忆 |

用大白话：上下文像“当前的草稿纸”，写满了就擦；记忆像“档案柜”，重要的文件长期保存。多智能体协作时，既要共享当前的草稿（上下文），又要共享存档的文件（记忆）。

### 手撕上下文 vs 记忆区别（Python 概念版）

下面是一个用 Python 演示上下文 vs 记忆区别的概念版：上下文是短期、即时的，记忆是长期、持久的。

```python
"""
概念版：上下文 vs 记忆区别
上下文是短期即时的，记忆是长期持久的
"""

from typing import List, Dict, Any
from datetime import datetime


class Context:
    """上下文：短期、即时，当前会话内有效。"""

    def __init__(self):
        self.messages: List[Dict[str, Any]] = []

    def add(self, role: str, content: str) -> None:
        self.messages.append({
            "role": role,
            "content": content,
            "timestamp": datetime.now().isoformat(),
        })

    def get_recent(self, n: int = 5) -> str:
        """获取最近 n 条上下文。"""
        recent = self.messages[-n:]
        return "\n".join([f"{m['role']}: {m['content']}" for m in recent])

    def clear(self) -> None:
        """会话结束后清空上下文。"""
        self.messages = []


class Memory:
    """记忆：长期、持久，跨会话保存。"""

    def __init__(self):
        self.records: List[Dict[str, Any]] = []

    def remember(self, content: str, source: str = "user") -> None:
        """记住一条信息，长期保存。"""
        self.records.append({
            "content": content,
            "source": source,
            "timestamp": datetime.now().isoformat(),
        })

    def recall(self, keyword: str, limit: int = 5) -> List[str]:
        """长期检索记忆。"""
        results = [r["content"] for r in self.records if keyword.lower() in r["content"].lower()]
        return results[:limit]


# ==================== 运行示例 ====================

if __name__ == "__main__":
    ctx = Context()
    mem = Memory()

    # 第一轮对话
    ctx.add("user", "我的报销预算是 30 万。")
    ctx.add("assistant", "好的，已记录预算 30 万。")
    mem.remember("用户报销预算设为 30 万", source="user")

    print("=== 第一轮对话上下文 ===")
    print(ctx.get_recent())

    # 模拟会话结束，上下文清空
    print("\n--- 会话结束，上下文清空 ---")
    ctx.clear()
    print(f"上下文剩余条数：{len(ctx.messages)}")

    # 第二轮对话（新会话），上下文重新开始，但记忆还在
    ctx.add("user", "帮我查一下报销流程。")
    print("\n=== 第二轮对话上下文 ===")
    print(ctx.get_recent())

    print("\n=== 第二轮检索记忆（跨会话仍能找到）===")
    for r in mem.recall("预算"):
        print(f"  - {r}")
```

**运行输出示例：**

```
=== 第一轮对话上下文 ===
user: 我的报销预算是 30 万。
assistant: 好的，已记录预算 30 万。

--- 会话结束，上下文清空 ---

上下文剩余条数：0

=== 第二轮对话上下文 ===
user: 帮我查一下报销流程。

=== 第二轮检索记忆（跨会话仍能找到）===
  - 用户报销预算设为 30 万
```

可以看到，第一轮对话的上下文在会话结束后被清空，但记忆里的“用户报销预算设为 30 万”在第二轮对话中仍能被检索到，体现了上下文短期、记忆长期的区别。

**面试要点**：上下文 vs 记忆的区别核心是“生命周期（短期 vs 长期）、存储位置（窗口 vs 数据库）、读写频率（极高 vs 较低）、容量限制（token 窗口 vs 存储容量）”。手撕时要体现：Context 类（短期、add/get_recent/clear）、Memory 类（长期、remember/recall）、会话结束后上下文清空但记忆保留。

## Q29. 上下文工程实战案例？

**回答**

### 案例 1：客服智能体（上下文窗口管理 + 动态检索）

**背景：** 一家电商公司想做一个客服聊天机器人，处理用户的退款、物流、产品咨询等问题。公司有大量知识库文档，用户问题多样，上下文不能无脑塞。

**选型与做法：**
- 动态检索（RAG）：根据用户问题检索知识库 Top-3 片段，只放相关片段进上下文；
- 上下文窗口管理：滑动窗口，保留最近 5 轮对话，超预算挤旧消息；
- 系统提示词常驻：定义客服人设和规则，不挤掉。

**搭建步骤（ASCII）：**

```
用户问题 ──→ 动态检索（知识库 Top-3） ──► 相关片段
                                              │
                                              ▼
                                    拼接进上下文（系统提示词 + 相关片段 + 最近 5 轮对话）
                                              │
                                              ▼
                                    模型生成客服回答
```

**效果：** 上下文简洁，模型只看到跟当前问题最相关的片段，不受无关历史干扰，回答准确率高，token 成本低。

---

### 案例 2：代码助手（最小可行工具集 + 截断工具输出）

**背景：** 一家公司想做一个代码助手智能体，帮助开发者写代码、调试、重构。工具包括：搜索、计算器、代码执行器、数据库查询等。

**选型与做法：**
- 最小可行工具集：只放代码执行器和搜索，不放所有工具，模型选工具不犹豫；
- 截断工具输出：代码执行器返回可能很长，只保留关键字段（输出、错误信息），截断冗余；
- 上下文窗口管理：保留最近的代码片段和错误信息，超预算挤旧消息。

**搭建步骤（ASCII）：**

```
用户请求（写代码/调试） ──→ 选最小可行工具集（代码执行器、搜索）
                                              │
                                              ▼
                                    工具输出截断（只保留输出/错误）
                                              │
                                              ▼
                                    拼接进上下文（系统提示词 + 截断后的工具输出 + 最近对话）
                                              │
                                              ▼
                                    模型生成代码或调试建议
```

**效果：** 工具输出不再塞满上下文，模型专注于关键信息，代码生成和调试更准确，token 成本降低。

---

### 案例 3：多智能体协作（公共上下文 + 私有上下文 + 交接上下文）

**背景：** 一家公司想做一个多智能体协作系统，产品经理 Agent、开发者 Agent、测试员 Agent 协作开发功能。

**选型与做法：**
- 公共上下文：项目需求、共同结论、已达成的决策，所有 Agent 共享；
- 私有上下文：每个 Agent 的草稿、中间推理，只属于自己；
- 交接上下文：Agent A 把任务交给 Agent B 时，传递任务状态、已完成步骤、下一步要做什么。

**搭建步骤（ASCII）：```

```
产品经理 Agent ──► [公共上下文：项目需求] ──► 开发者 Agent
                                              │
                                              ▼
                                    [私有上下文：开发者草稿]
                                              │
                                              ▼
                                    [交接上下文：任务=开发，已完成=PRD，下一步=写代码]
                                              │
                                              ▼
                                    测试员 Agent 读取公共上下文 + 交接上下文
```

**效果：** 多个 Agent 协作清晰，公共信息共享，私有信息隔离，交接上下文让任务流转不丢失。

## Q31. 上下文工程怎么和智能体框架集成？

**回答**

Q22-Q24 已经介绍了智能体框架（LangGraph、AutoGen、AgentScope 等）和上下文工程各自的角色。上下文工程不是独立存在的，它需要集成到具体的智能体框架里才能发挥作用。**上下文工程与智能体框架的集成** 就是把上下文窗口管理、提示词工程、动态检索等能力，嵌入到框架的节点、边、状态机里，让框架在运行时自动管理上下文。

### 集成的核心思路

| 集成点 | 大白话解释 | 做法 |
|--------|-----------|------|
| 节点级上下文管理 | 每个节点运行前，根据当前状态管理上下文 | 在框架节点前插入上下文压缩/检索逻辑 |
| 状态级上下文传递 | 框架状态机里带上下文状态，节点间传递 | 状态对象里包含上下文摘要、检索片段 |
| 提示词模板化 | 框架节点里用结构化提示词模板 | 每个节点用 XML/Markdown 模板拼接提示词 |
| 工具输出截断 | 节点调用工具后，截断输出再放进状态 | 工具节点后加截断逻辑 |

用大白话：上下文工程集成到框架，就像“给汽车装导航系统”。框架是汽车（跑任务），上下文工程是导航（决定路线、避开拥堵），两者结合，汽车才能高效到达目的地。

### 手撕集成代码（Python 概念版）

下面是一个用 Python 演示上下文工程集成到智能体框架的概念版：以 LangGraph 风格的状态机为例，节点前置做上下文压缩和提示词拼接，节点后置做工具输出截断和状态更新。不依赖真实 LangGraph，直接运行即可看懂集成骨架。

```python
"""
概念版：上下文工程集成到智能体框架（LangGraph 风格状态机）
节点前置：上下文压缩 + 提示词拼接；节点后置：工具输出截断 + 状态更新
"""

from typing import Dict, Any, List, Optional
from datetime import datetime


def estimate_tokens(text: str) -> int:
    """粗略估算 token（演示版）。"""
    chinese = len([c for c in text if '一' <= c <= '鿿'])
    others = len(text) - chinese
    return chinese + others // 4 + 1


class FrameState:
    """框架状态：包含上下文、检索片段、工具输出等。"""

    def __init__(self):
        self.context_messages: List[Dict[str, Any]] = []
        self.retrieved_chunks: List[str] = []
        self.tool_outputs: List[str] = []
        self.final_answer: Optional[str] = None


class ContextEngineeringNode:
    """带上下文工程的框架节点：前置压缩+提示词拼接，后置截断+状态更新。"""

    def __init__(self, name: str, max_tokens: int = 2000):
        self.name = name
        self.max_tokens = max_tokens

    def pre_process(self, state: FrameState, user_question: str, system_prompt: str) -> str:
        """
        节点前置：上下文压缩 + 动态检索 + 提示词拼接。
        返回拼接好的提示词。
        """
        # 上下文压缩：超预算挤旧消息
        total = sum(estimate_tokens(m["content"]) for m in state.context_messages)
        compressed = list(state.context_messages)
        while total > self.max_tokens and len(compressed) > 1:
            compressed.pop(1)
            total = sum(estimate_tokens(m["content"]) for m in compressed)

        # 动态检索片段（演示版：直接用已有的 retrieved_chunks）
        chunks = state.retrieved_chunks[:3]

        # 提示词拼接
        parts = [f"<系统提示词>\n{system_prompt}\n</系统提示词>"]
        if chunks:
            parts.append("<检索片段>")
            for i, c in enumerate(chunks, 1):
                parts.append(f"{i}. {c}")
            parts.append("</检索片段>")
        if compressed:
            parts.append("<历史对话>")
            for m in compressed:
                parts.append(f"{m['role']}: {m['content']}")
            parts.append("</历史对话>")
        parts.append(f"<用户问题>\n{user_question}\n</用户问题>")
        return "\n".join(parts)

    def post_process(self, state: FrameState, tool_output: Optional[str] = None) -> None:
        """
        节点后置：工具输出截断 + 状态更新。
        """
        if tool_output:
            # 截断工具输出，只保留前 500 字符
            if len(tool_output) > 500:
                tool_output = tool_output[:500] + "\n……[工具输出已截断]"
            state.tool_outputs.append(tool_output)
            print(f"[框架节点 {self.name}] 工具输出已截断并存入状态")


class FrameworkOrchestrator:
    """框架编排器：状态机驱动，节点间传递状态。"""

    def __init__(self):
        self.nodes: Dict[str, ContextEngineeringNode] = {}
        self.edges: Dict[str, str] = {}

    def add_node(self, name: str, node: ContextEngineeringNode) -> None:
        self.nodes[name] = node

    def add_edge(self, frm: str, to: str) -> None:
        self.edges[frm] = to

    def run(self, start_node: str, user_question: str, system_prompt: str,
            retrieved_chunks: List[str], initial_tool_output: Optional[str] = None) -> str:
        """运行框架：从起始节点开始，按边流转。"""
        state = FrameState()
        state.retrieved_chunks = retrieved_chunks
        if initial_tool_output:
            state.tool_outputs.append(initial_tool_output)

        current = start_node
        while current in self.nodes:
            node = self.nodes[current]
            print(f"[框架] 进入节点：{current}")

            # 节点前置：拼接提示词
            prompt = node.pre_process(state, user_question, system_prompt)
            print(f"[框架] 节点 {current} 提示词长度：{len(prompt)} 字符")

            # 模拟节点执行（调模型生成答案）
            answer = f"[{current}] 基于上下文回答：{user_question}"

            # 节点后置：截断工具输出 + 状态更新
            node.post_process(state, initial_tool_output if current == start_node else None)
            state.context_messages.append({"role": "assistant", "content": answer})

            # 流转到下一节点
            nxt = self.edges.get(current)
            if nxt is None:
                break
            current = nxt

        state.final_answer = answer
        return answer


# ==================== 运行示例 ====================

if __name__ == "__main__":
    orchestrator = FrameworkOrchestrator()

    # 创建两个节点
    node1 = ContextEngineeringNode("节点1：理解意图", max_tokens=1500)
    node2 = ContextEngineeringNode("节点2：生成回答", max_tokens=1500)

    orchestrator.add_node("节点1：理解意图", node1)
    orchestrator.add_node("节点2：生成回答", node2)
    orchestrator.add_edge("节点1：理解意图", "节点2：生成回答")

    # 运行
    answer = orchestrator.run(
        start_node="节点1：理解意图",
        user_question="单餐报销上限是多少？",
        system_prompt="你是一个公司报销制度助手。",
        retrieved_chunks=["单餐餐饮报销上限为 200 元，需提供发票。",
                          "交通费报销：出租车单程上限 100 元。"],
        initial_tool_output="工具返回：报销制度文档共 50 页，相关条款在第 3 页……" + "x" * 600,
    )

    print("\n=== 最终答案 ===")
    print(answer)
```

**运行输出示例：**

```
[框架] 进入节点：节点1：理解意图
[框架] 节点 1 提示词长度：420 字符
[框架节点 节点1：理解意图] 工具输出已截断并存入状态
[框架] 进入节点：节点2：生成回答
[框架] 节点 2 提示词长度：520 字符

可以看到，上下文工程集成到框架后，节点前置做压缩和提示词拼接，节点后置做工具输出截断和状态更新，状态在节点间流转。

**面试要点**：上下文工程与框架集成的核心是“节点前置做上下文压缩+提示词拼接，节点后置做工具输出截断+状态更新，状态机驱动节点间流转”。手撕时要体现：FrameState 状态对象、ContextEngineeringNode 节点（pre_process/post_process）、FrameworkOrchestrator 编排器（add_node/add_edge/run）。

## Q32. 上下文工程与 A2A / MCP 协议的关系？

**回答**

Q19-Q20 已经介绍了 MCP（模型上下文协议）和 A2A（智能体间协议）。上下文工程和这些协议是什么关系？**上下文工程与 A2A/MCP 协议的关系** 就是：协议负责“上下文在不同系统/智能体之间怎么传递”，上下文工程负责“上下文在单个系统内部怎么管理”，两者配合，实现跨系统的上下文流转。

---

### 关系对比表

| 维度 | 上下文工程 | A2A 协议 | MCP 协议 |
|------|-----------|---------|---------|
| 职责 | 单个系统内上下文怎么管理（压缩、检索、截断） | 多智能体之间上下文怎么交换 | 大模型与外部工具/数据怎么连接 |
| 范围 | 单系统内部 | 多智能体间 | 大模型 ↔ 外部系统 |
| 关注点 | token 预算、上下文质量、检索策略 | 上下文序列化、传输、状态同步 | 工具接口、数据格式、认证 |

用大白话：上下文工程像“公司内部文件管理”，A2A 像“公司之间文件交换”，MCP 像“公司与外部供应商对接”。三者配合，信息才能在内部、公司间、外部之间顺畅流转。

### 手撕 A2A 上下文交换（Python 概念版）

下面是一个用 Python 演示 A2A 协议上下文交换的概念版：智能体 A 把上下文序列化发给智能体 B，智能体 B 反序列化后继续使用。不依赖真实 A2A 协议，直接运行即可看懂交换骨架。

```python
"""
概念版：A2A 协议上下文交换
智能体 A 序列化上下文 → 传输 → 智能体 B 反序列化 → 继续使用
"""

import json
from typing import List, Dict, Any
from datetime import datetime


class AgentContext:
    """智能体上下文：可序列化，用于 A2A 交换。"""

    def __init__(self, agent_id: str):
        self.agent_id = agent_id
        self.messages: List[Dict[str, Any]] = []
        self.retrieved_chunks: List[str] = []

    def add_message(self, role: str, content: str) -> None:
        self.messages.append({
            "role": role,
            "content": content,
            "timestamp": datetime.now().isoformat(),
        })

    def add_chunk(self, chunk: str) -> None:
        self.retrieved_chunks.append(chunk)

    def serialize(self) -> str:
        """序列化为 JSON 字符串，用于 A2A 传输。"""
        data = {
            "agent_id": self.agent_id,
            "messages": self.messages,
            "retrieved_chunks": self.retrieved_chunks,
        }
        return json.dumps(data, ensure_ascii=False, indent=2)

    @classmethod
    def deserialize(cls, json_str: str) -> "AgentContext":
        """从 JSON 字符串反序列化。"""
        data = json.loads(json_str)
        ctx = cls(data["agent_id"])
        ctx.messages = data["messages"]
        ctx.retrieved_chunks = data["retrieved_chunks"]
        return ctx

    def summary(self) -> str:
        return f"Agent {self.agent_id}: {len(self.messages)} 条消息，{len(self.retrieved_chunks)} 个检索片段"


class A2AProtocol:
    """A2A 协议：智能体之间交换上下文。"""

    def __init__(self):
        self.transported: List[Dict[str, Any]] = []  # 传输记录

    def send(self, from_agent: AgentContext, to_agent_id: str) -> str:
        """
        从 from_agent 序列化上下文，准备发给 to_agent。
        返回序列化后的字符串（模拟网络传输）。
        """
        payload = from_agent.serialize()
        self.transported.append({
            "from": from_agent.agent_id,
            "to": to_agent_id,
            "payload": payload,
            "timestamp": datetime.now().isoformat(),
        })
        print(f"[A2A] {from_agent.agent_id} → {to_agent_id}: 上下文已序列化，{len(payload)} 字符")
        return payload

    def receive(self, to_agent: AgentContext, payload: str) -> None:
        """
        to_agent 反序列化接收到的上下文，合并到自己的上下文中。
        """
        received = AgentContext.deserialize(payload)
        # 合并消息和检索片段
        to_agent.messages.extend(received.messages)
        to_agent.retrieved_chunks.extend(received.retrieved_chunks)
        print(f"[A2A] {to_agent.agent_id} 接收并合并：{len(received.messages)} 条消息，{len(received.retrieved_chunks)} 个片段")


# ==================== 运行示例 ====================

if __name__ == "__main__":
    # 智能体 A
    agent_a = AgentContext("产品经理Agent")
    agent_a.add_message("user", "开发一个登录功能。")
    agent_a.add_message("assistant", "已理解，需要 PRD 和代码实现。")
    agent_a.add_chunk("用户登录需求：支持账号密码登录、第三方登录。")

    # 智能体 B
    agent_b = AgentContext("开发者Agent")

    # A2A 协议交换
    protocol = A2AProtocol()
    payload = protocol.send(agent_a, "开发者Agent")
    protocol.receive(agent_b, payload)

    print("\n=== 智能体 B 接收后的上下文 ===")
    print(agent_b.summary())
    for m in agent_b.messages:
        print(f"  {m['role']}: {m['content']}")
    for c in agent_b.retrieved_chunks:
        print(f"  检索片段：{c}")
```

**运行输出示例：**

```

[A2A] 开发者Agent 接收并合并：2 条消息，1 个检索片段

=== 智能体 B 接收后的上下文 ===
Agent 开发者Agent: 2 条消息，1 个检索片段

可以看到，智能体 A 把上下文序列化发给智能体 B，B 反序列化后合并到自己的上下文中，可以继续基于 A 的上下文开展工作。

**面试要点**：上下文工程与 A2A/MCP 协议的关系核心是“协议负责上下文在系统间传递，上下文工程负责单系统内上下文管理”。手撕时要体现：AgentContext 序列化/反序列化、A2AProtocol send/receive、上下文在智能体间合并。

## Q33. 上下文工程的边界与局限？

**回答**

上下文工程不是万能药，有其边界和局限。了解这些局限，能避免“为了用上下文工程而用上下文工程”，也能避免过度优化。

---

### 上下文工程的边界与局限

| 局限 | 大白话解释 | 适用场景 | 替代方案 |
|------|-----------|---------|---------|
| 简单任务不需要上下文工程 | 查天气、算加法这种简单任务，直接调模型就行，不需要 RAG+压缩+缓存 | 单次问答、简单指令 | 直接调模型 |
| 上下文压缩会丢失细节 | 摘要压缩可能丢失重要细节，导致回答不准 | 需要精确信息的场景 | 不压缩，或增加 token 预算 |
| 动态检索可能漏检 | 向量检索可能检不到相关片段，导致回答错误 | 对准确率要求极高的场景 | 人工干预、多路召回 |
| 多模态上下文 token 昂贵 | 图片/音频/视频占用大量 token，成本高 | 多模态场景 | 先提取关键帧/文本，再放入上下文 |
| 上下文工程不能解决模型本身能力不足 | 模型不懂某个领域，上下文再好也答不好 | 领域专业问答 | 微调模型、专家知识库 |
| 过度优化会增加复杂度 | 太多压缩、缓存、检索逻辑，系统复杂，难维护 | 小型项目 | 简单上下文管理即可 |

用大白话：上下文工程像“给汽车加涡轮增压”。跑长途（复杂任务）很有用，但跑超市（简单任务）没必要；加太多涡轮（过度优化）反而容易坏；涡轮也不能让不会开车的人（模型能力不足）开出 F1 成绩。

---

### 手撕自动上下文管理（Python 概念版）

下面是一个用 Python 演示“自动上下文管理”的概念版：系统根据任务复杂度和对话长度，自动决定上下文压缩策略和预算，不需要人工手动设计。

```python
"""
概念版：自动上下文管理
根据任务复杂度和对话长度，自动调整预算和策略
"""

from typing import List, Dict, Any
from datetime import datetime


def estimate_tokens(text: str) -> int:
    """粗略估算 token（演示版）。"""
    chinese = len([c for c in text if '一' <= c <= '鿿'])
    others = len(text) - chinese
    return chinese + others // 4 + 1


class AutoContextManager:
    """自动上下文管理器：根据任务复杂度和对话长度，自动调整预算和策略。"""

    def __init__(self):
        self.history: List[Dict[str, Any]] = []

    def classify_complexity(self, user_input: str) -> str:
        """自动分类任务复杂度（演示版：关键词匹配）。"""
        complex_keywords = ["代码", "调试", "架构", "算法", "重构", "优化", "分析"]
        medium_keywords = ["文案", "总结", "翻译", "写作"]
        text = user_input.lower()
        if any(kw in text for kw in complex_keywords):
            return "complex"
        if any(kw in text for kw in medium_keywords):
            return "medium"
        return "simple"

    def auto_adjust(self, user_input: str, conversation_length: int) -> Dict[str, Any]:
        """
        自动调整上下文预算和压缩策略。
        返回：{预算, 策略, 理由}
        """
        complexity = self.classify_complexity(user_input)

        # 基础预算
        base = {"simple": 800, "medium": 2000, "complex": 4000}[complexity]

        # 根据对话长度动态调整
        length_factor = max(0.5, 1.0 - conversation_length * 0.02)
        budget = int(base * length_factor)

        # 决定压缩策略
        if complexity == "simple" and conversation_length < 5:
            strategy = "无需压缩"
        elif complexity == "medium":
            strategy = "滑动窗口"
        else:
            strategy = "摘要压缩"

        reason = f"任务={complexity}, 对话长度={conversation_length}, 预算={budget}, 策略={strategy}"
        print(f"[自动上下文管理] {reason}")

        self.history.append({
            "user_input": user_input,
            "complexity": complexity,
            "conversation_length": conversation_length,
            "budget": budget,
            "strategy": strategy,
            "timestamp": datetime.now().isoformat(),
        })

        return {
            "budget": budget,
            "strategy": strategy,
            "reason": reason,
        }

    def get_history(self) -> List[Dict[str, Any]]:
        return self.history


# ==================== 运行示例 ====================

if __name__ == "__main__":
    manager = AutoContextManager()

    print("=== 场景 1：简单任务 ===")
    r1 = manager.auto_adjust("北京今天天气怎么样？", conversation_length=2)
    print(f"  预算：{r1['budget']}，策略：{r1['strategy']}")

    print("\n=== 场景 2：复杂任务 ===")
    r2 = manager.auto_adjust("写一个 Python 爬虫并调试报错", conversation_length=8)
    print(f"  预算：{r2['budget']}，策略：{r2['strategy']}")

    print("\n=== 场景 3：长对话复杂任务 ===")
    r3 = manager.auto_adjust("重构这个 Python 模块", conversation_length=20)
    print(f"  预算：{r3['budget']}，策略：{r3['strategy']}")
```

**运行输出示例：**

```
[自动上下文管理] 任务=simple, 对话长度=2, 预算=784, 策略=无需压缩
[自动上下文管理] 任务=complex, 对话长度=8, 预算=3296, 策略=摘要压缩
[自动上下文管理] 任务=complex, 对话长度=20, 预算=2640, 策略=摘要压缩
```

可以看到，系统根据任务复杂度和对话长度，自动决定了不同的预算和压缩策略，不需要人工手动设计。
