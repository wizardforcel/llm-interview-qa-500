## Q1. 什么是混合检索（Hybrid Search）？为什么单一向量检索不够？

**回答**

混合检索是指同时使用“稠密向量检索（语义检索）”和“稀疏关键词检索（如 BM25）”，再把两路结果融合成一个最终排序。

单一向量检索虽然擅长语义匹配（比如“退款流程”能查到“如何把钱退回来”），但有个致命弱点：**对精确匹配较弱**。产品型号、错误代码、函数名、罕见专有名词、数字这些词，在向量空间里语义信息弱，很容易被“稀释”掉，导致检索不到。

稀疏检索（BM25）正好相反：它擅长精确关键词匹配（比如“DL/T 596”这样的标准号能直接命中），但不懂语义，同义词（“报销”和“报销单”）就查不到了。

把两者混合，就能互补：

```
用户提问
    │
    ├────────▶ 稠密检索（语义，向量数据库） ──┐
    │                                         │
    └────────▶ 稀疏检索（关键词，BM25/倒排） ─┤
                                              ▼
                                    结果融合（RRF / 加权）
                                              │
                                              ▼
                                    重排序（Cross-encoder）
                                              │
                                              ▼
                                    最终 Top-K 片段
```

> 面试要点：混合检索＝稠密语义检索＋稀疏关键词检索＋结果融合。稠密擅长同义语义，稀疏擅长精确关键词/代码/数字，两者互补，生产环境主流做法是“稠密＋稀疏＋RRF 融合＋Cross-encoder 重排”。

## Q2. 稠密检索和稀疏检索有什么区别？

**回答**

| 维度 | 稠密检索（Dense） | 稀疏检索（Sparse，如 BM25） |
|------|------------------|---------------------------|
| 原理 | 文本→Embedding 向量，向量空间相似度搜索 | 词频×逆文档频率，关键词重叠匹配 |
| 擅长 | 语义匹配、同义词、模糊表达 | 精确关键词、代码、型号、数字 |
| 弱点 | 精确匹配差、罕见专有名词容易被稀释 | 不懂同义词、不懂语义、多词必须全命中 |
| 索引 | 向量数据库（HNSW、IVF 等） | 倒排索引（Elasticsearch、SQLite FTS5、BM25 库） |
| 示例 | “退款流程”→命中“如何把钱退回来” | “DL/T 596”→命中含“DL/T 596”的文档 |

大白话比喻：

- **稠密检索**像“懂行的老员工”：你描述大概意思，他能联想到相关文档，哪怕你没用原话。
- **稀疏检索**像“索引员”：你给精确关键词，他能翻到包含该词的页码，但你换个说法他就找不到了。

ASCII 示意：

```
稠密检索（语义）                    稀疏检索（关键词）
┌──────────────┐                  ┌──────────────┐
│ 用户：“退钱咋办？” │              │ 用户：“DL/T 596” │
│     │                    │              │     │
│     ▼                    │              │     ▼
│  向量相似搜索            │              │  倒排索引精确匹配 │
│     │                    │              │     │
│     ▼                    │              │     ▼
│  “如何办理退款流程”      │              │  “DL/T 596 标准文档” │
│  （语义相关，命中）      │              │  （关键词精确，命中） │
└──────────────┘                  └──────────────┘
```

> 面试要点：稠密检索基于 Embedding 向量相似度，擅长语义和同义；稀疏检索基于 BM25 关键词重叠，擅长精确匹配（型号、代码、数字）。两者优势互补，单用任何一方都有盲区。

## Q3. 什么是 BM25？它怎么打分？

**回答**

BM25 是一种经典的稀疏检索排序算法，基于“词袋模型”。核心思想是：一篇文档里某个词出现得越频繁，该词对文档的贡献越大；但这个词在整个语料库里出现得越频繁（越常见），它的区分度越低，贡献越小。同时还会对文档长度做归一化，避免长文档仅因为长就得分高。

简化版打分公式：

```
score(D, Q) = Σ_{词 q ∈ Q} IDF(q) × [ f(q,D) × (k1 + 1) / (f(q,D) + k1 × (1 - b + b × |D| / avgdl)) ]
```

- `f(q,D)`：查询词 q 在文档 D 里的词频
- `IDF(q)`：q 的逆文档频率，越罕见的词权重越大
- `|D|` / `avgdl`：文档长度与平均长度之比（长度归一化）
- `k1`：词频饱和度参数（常用 1.2～2.0）
- `b`：长度归一化参数（常用 0.75）

### Python 示例（rank_bm25）

```python
from rank_bm25 import BM25Okapi
import re

def tokenize(text: str):
    return re.findall(r"\w+", text.lower())

corpus = [
    "单餐报销不超过200元，需提供发票。",
    "出差住宿可报销，每晚不超过500元。",
    "员工入职后享有5天带薪年假，需提前申请。",
]

bm25 = BM25Okapi([tokenize(doc) for doc in corpus])
query = "报销 上限"
scores = bm25.get_scores(tokenize(query))

for i, s in enumerate(scores):
    print(f"文档{i}: {s:.4f}")
```

> 面试要点：BM25 是稀疏检索的基准算法，基于词频和逆文档频率打分，擅长精确关键词匹配，支持长度归一化。Python 可用 `rank_bm25.BM25Okapi` 快速使用。

## Q4. 什么是 RRF（倒数排名融合，Reciprocal Rank Fusion）？为什么混合检索常用它？

**回答**

混合检索的难点在于：**稠密检索的得分（如余弦相似度，范围 0～1）和稀疏检索的得分（BM25，可能是 0 到几十的任意值），尺度和分布完全不同，不能直接相加。**

RRF 完全抛开原始得分，只看**排名**。每个文档的融合得分是它在各路检索结果里排名的平滑倒数之和：

```
RRF 分数 = Σ 1 / (k + rank)
```

其中 `rank` 是文档在某条检索列表中的排名（从 0 开始），`k` 是平滑常数，常取 **60**。

公式展开（两路：稠密 + 稀疏）：

```
score(d) = 1 / (k + rank_dense(d)) + 1 / (k + rank_sparse(d))
```

**RRF 的优点：**

1. **无需归一化**：不需要把两路得分映射到同一尺度。
2. **无需每查询校准权重**：k=60 已经是一个经过验证的稳定默认值。
3. **奖励多路同意**：一个文档如果在两路里都排名靠前，融合得分会显著高于只在一路靠前的文档。

### Python 示例

```python
def rrf_fuse(rankings: list, k: int = 60):
    """
    rankings: [[doc_id, ...], [doc_id, ...]] 多条按排名排序的 doc_id 列表
    返回：{doc_id: rrf_score} 按得分降序
    """
    scores = {}
    for ranking in rankings:
        for rank, doc_id in enumerate(ranking):
            scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (k + rank + 1)
    return sorted(scores.items(), key=lambda x: x[1], reverse=True)


# 示例：稠密 Top-3 和 稀疏 Top-3
dense = ["doc_a", "doc_b", "doc_c"]
sparse = ["doc_b", "doc_a", "doc_d"]

fused = rrf_fuse([dense, sparse], k=60)
print(fused)
# 输出示例：[('doc_b', 0.0323), ('doc_a', 0.0323), ('doc_c', 0.0161), ('doc_d', 0.0161)]
# doc_a 和 doc_b 在两路都靠前，得分最高
```

> 面试要点：RRF 抛开原始得分，只按排名做 `1/(k+rank)` 求和，k 常取 60。优点是无需归一化、无需每查询校准权重、奖励多路结果一致的文档，是 2026 年混合检索融合的事实标准。

## Q5. 混合检索的完整流水线分哪几个阶段？

**回答**

工业界的混合检索流水线通常分三个阶段，层层递进：

**阶段 1：并行检索（候选召回）**

系统同时向稠密引擎（向量数据库）和稀疏引擎（BM25/倒排索引）发送查询，各自召回 Top-K 候选（比如各 50 条）。

**阶段 2：结果融合（统一候选池）**

把两路排名列表用 RRF 融合成一个统一的候选池，去重。

**阶段 3：重排序（精排）**

用 Cross-encoder 对融合后的候选池（比如 Top-50）逐一打分，产生最终排序，取 Top-K（比如 Top-5）送给大模型。

ASCII 示意：

```
阶段1：并行检索              阶段2：结果融合              阶段3：重排序
┌─────────┐                ┌─────────┐                ┌─────────┐
│ 稠密Top50 │                │  RRF 融合 │                │ Cross-  │
│ 稀疏Top50 │───────────────▶│  去重   │───────────────▶│ encoder │
└─────────┘                └─────────┘                │ 重排    │
                                                        └─────────┘
                                                           │
                                                           ▼
                                                   最终 Top-K
```

> 面试要点：混合检索三阶段＝并行检索（稠密+稀疏各召回 Top-K）→结果融合（RRF 去重统一排序）→重排序（Cross-encoder 精排，取最终 Top-K）。三者各司其职，融合负责产生候选池，重排序负责在候选池上精排。

## Q6. 稠密和稀疏得分不可直接比较，除了 RRF 还有什么融合方法？

**回答**

除了 RRF，另一种常见方法是**归一化加权融合**：

1. 把稠密得分和稀疏得分分别归一化到 [0,1] 区间（比如用 min-max 归一化，或 sigmoid 压缩）。
2. 加权求和：`最终得分 = w_dense × 稠密归一化得分 + w_sparse × 稀疏归一化得分`。

**两种方法对比：**

| 方法 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| RRF | 只看排名，`1/(k+rank)` 求和 | 无需归一化、无需每查询校准权重、鲁棒 | 只利用排名信息，丢失原始得分的细粒度相关性 |
| 归一化加权 | 得分归一化后加权求和 | 保留原始得分信号 | 两路尺度对齐本身不好调，每种数据集可能要重新调权重 |

**生产建议：** 默认先用 RRF（简单、鲁棒、无需调参），作为 baseline。如果有足够标注数据，再尝试归一化加权融合并线上 A/B 测试。

> 面试要点：融合方法有 RRF（按排名求和，无需归一化和调权重，推荐 baseline）和归一化加权融合（保留得分细粒度但需调参）。RRF 是生产中更常见的选择。

## Q7. 用 Python 实现一个完整的混合检索（稠密 + BM25 + RRF），代码长什么样？

**回答**

下面是一个不依赖云端 API、完全在本地运行的最小混合检索示例。稠密用 `sentence-transformers` + 简单的余弦相似度搜索（作为向量数据库的替代演示），稀疏用 `rank_bm25`，融合用 RRF。

先安装依赖：

```bash
pip install sentence-transformers rank_bm25 numpy
```

完整代码：

```python
import re
import numpy as np
from sentence_transformers import SentenceTransformer
from rank_bm25 import BM25Okapi

def tokenize(text: str):
    return re.findall(r"\w+", text.lower())

# 知识库片段
chunks = [
    "单餐报销不超过200元，需提供发票。",
    "出差住宿可报销，每晚不超过500元。",
    "员工入职后享有5天带薪年假，需提前申请。",
    "办公室空调温度统一设定为26度，请勿私自调节。",
]

# ---------- 1. 稠密检索 ----------
model = SentenceTransformer("BAAI/bge-small-zh-v1.5")
doc_embeddings = model.encode(chunks, normalize_embeddings=True)  # (N, 384)

def dense_search(query, top_k=3):
    q_emb = model.encode([query], normalize_embeddings=True)[0]
    sims = np.dot(doc_embeddings, q_emb)  # 已归一化，点积=余弦相似度
    order = np.argsort(-sims)[:top_k]
    return [chunks[i] for i in order], order.tolist()

# ---------- 2. 稀疏检索（BM25） ----------
bm25 = BM25Okapi([tokenize(c) for c in chunks])

def sparse_search(query, top_k=3):
    scores = bm25.get_scores(tokenize(query))
    order = np.argsort(-scores)[:top_k]
    return [chunks[i] for i in order], order.tolist()

# ---------- 3. RRF 融合 ----------
def rrf_fuse(rankings, k=60):
    scores = {}
    for ranking in rankings:
        for rank, doc_id in enumerate(ranking):
            scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (k + rank + 1)
    return sorted(scores.items(), key=lambda x: x[1], reverse=True)

# ---------- 混合检索入口 ----------
def hybrid_search(query, top_k=3, candidate_k=3):
    # 并行检索（这里串行演示，生产可用 asyncio.gather 并发）
    _, dense_ids = dense_search(query, candidate_k)
    _, sparse_ids = sparse_search(query, candidate_k)

    # RRF 融合
    fused = rrf_fuse([dense_ids, sparse_ids], k=60)
    top_ids = [doc_id for doc_id, _ in fused[:top_k]]

    return [chunks[i] for i in top_ids]


# 使用示例
query = "单餐报销上限是多少？"
results = hybrid_search(query, top_k=2)
print(f"问题：{query}")
print("混合检索结果：")
for i, r in enumerate(results, 1):
    print(f"{i}. {r}")
```

运行效果示例：

```
问题：单餐报销上限是多少？
混合检索结果：
1. 单餐报销不超过200元，需提供发票。
2. 出差住宿可报销，每晚不超过500元。
```

> 面试要点：混合检索代码＝稠密检索（Embedding+余弦相似度）+ 稀疏检索（BM25）+ RRF 融合。生产环境中稠密检索用向量数据库（Milvus/Chroma 等）、稀疏检索用倒排索引（Elasticsearch/SQLite FTS5），两路并行（`asyncio.gather`），再 RRF 融合。

## Q8. 什么是重排序（Re-ranking / Cross-encoder）？它和检索阶段的 Bi-encoder 有什么区别？

**回答**

重排序是检索阶段之后的“精排”环节，用来把融合后的候选池（比如 Top-50）按和查询的相关性重新打分，取最终 Top-K。

**Bi-encoder（检索阶段，双编码器）**

把查询和文档分别编码成两个向量，再算相似度：

```
查询 → Encoder → 向量 q
文档 → Encoder → 向量 d
相似度 = cos(q, d)
```

优点：所有文档向量可离线预计算并存储，查询时只需算查询向量，向量数据库做近邻搜索，速度极快。适合第一阶段召回。

**Cross-encoder（重排序阶段，交叉编码器）**

把查询和文档**拼在一起**同时输入模型，直接输出相关性分数：

```
[查询 + 文档] → Encoder → 相关性分数
```

优点：模型能充分交互查询和文档的细节，判断更精准。缺点：每个查询-文档对都要过一次模型，不能离线预计算，速度慢，只能对少数候选做重排序。

ASCII 示意：

```
Bi-encoder（初筛，快）              Cross-encoder（面试，准）
查询 → 向量                      [查询+文档] → 模型 → 分数
文档 → 向量                         (逐个面对面比对)
cos(q, d)                          慢，但判断更准确
适合召回 Top-100                    适合对 Top-50 精排到 Top-5
```

> 面试要点：Bi-encoder 分别编码查询和文档，可离线预计算向量，用于第一阶段快速召回；Cross-encoder 把查询和文档拼在一起一起编码，更精准但慢，用于第二阶段重排序。生产 RAG 常见“Bi-encoder 召回 + Cross-encoder 重排”组合。

## Q9. 怎么用 Python 调用 Cross-encoder 重排序模型？

**回答**

常用的重排序模型是 `BAAI/bge-reranker-v2-m3`（中英文都强），通过 `sentence-transformers` 的 `CrossEncoder` 加载。

先安装依赖：

```bash
pip install sentence-transformers
```

完整代码：

```python
from sentence_transformers import CrossEncoder

# 加载重排序模型
reranker = CrossEncoder("BAAI/bge-reranker-v2-m3")

query = "单餐报销上限是多少？"
candidates = [
    "单餐报销不超过200元，需提供发票。",
    "办公室空调温度统一设定为26度，请勿私自调节。",
    "出差住宿可报销，每晚不超过500元。",
]

# Cross-encoder 输入是 [(query, doc), ...] 对，输出相关性分数
pairs = [[query, doc] for doc in candidates]
scores = reranker.predict(pairs)

# 按分数降序排序
ranked = sorted(zip(candidates, scores), key=lambda x: x[1], reverse=True)
for doc, score in ranked:
    print(f"分数：{score:.3f} | {doc}")
```

> 面试要点：用 `sentence-transformers.CrossEncoder` 加载重排序模型（如 `bge-reranker-v2-m3`），输入 `[[query, doc], ...]` 对，输出相关性分数，按分数降序取 Top-K。重排序只对融合后的少量候选（如 Top-50）进行，避免对全量文档重排导致延迟过高。

## Q10. 什么是 MMR（最大边际相关性，Maximal Marginal Relevance）？检索中怎么用？

**回答**

MMR 用于在检索结果中平衡**相关性**和**多样性**。纯相似度检索可能返回多条高度重复的片段（比如同一段话的不同切片），浪费上下文窗口且信息冗余。

MMR 的核心公式（简化）：

```
MMR 分数 = λ × 相关性(查询, 文档) - (1 - λ) × 最大相似度(文档, 已选文档)
```

- `λ` 控制相关性与多样性的权重（常用 0.5～0.7）。
- 每次从剩余候选里选 MMR 分数最高的文档加入已选集合，直到凑够 Top-K。

**什么时候用？**

当检索结果中可能有大量语义重复的片段，或者希望返回的片段覆盖多个不同角度时，用 MMR 做多样性选 Top-K。

> 面试要点：MMR 在相关性和多样性之间权衡（λ 控制权重），每次选与查询相关且与已选文档差异大的片段，避免 Top-K 里全是重复内容。适合检索结果有大量语义冗余的场景。

## Q11. 什么是小块到大块（Small-to-Big / 父子分块）检索？

**回答**

小块到大块检索（也叫父子分块检索）的核心思想是“小块检索，大块喂模型”：

- **子块（Child）**：切成较小的片段（比如 200～400 字），用于向量化检索，检索精准，容易命中具体答案细节。
- **父块（Parent）**：子块所属的更大片段（比如整节、整章，1000～2000 字）。检索命中子块后，返回其父块作为 Prompt 上下文喂给大模型，保证模型看到完整上下文。

优点：既保住了“检索精准”（小块容易命中细节），又保住了“回答完整”（大块给模型足够上下文）。即使子块检索稍有偏差，返回的父块通常也还包含合理信息，降级优雅。

ASCII 示意：

```
父子分块：
父块（大，喂模型）：[## 退款政策
                    退款时效为7个工作日。VIP用户可加急至24小时。
                    运费不退。特殊商品不支持退款。]
                    ▲
              检索命中子块
子块（小，向量化检索）：[退款时效为7个工作日。VIP用户可加急至24小时。]
```

> 面试要点：小块到大块＝小块向量化检索（精准命中），命中后返回其父大块喂模型（完整上下文）。兼顾“查得准”和“答得全”，代价是存储父子两份（开销稍大）。

## Q12. 混合检索适合什么场景？什么场景可以只用稠密或只用稀疏？

**回答**

| 场景 | 推荐检索方式 | 理由 |
|------|-------------|------|
| 企业知识库（含术语、代码、型号、数字） | 混合检索（稠密+稀疏+RRF） | 既要语义匹配，又要精确关键词 |
| 纯语义问答（如“心情不好怎么办”） | 稠密检索 | 无精确关键词需求，稠密即可 |
| 精确代码/错误码查询（如“Error 404”） | 稀疏检索（BM25） | 精确匹配最重要，语义检索容易稀释 |
| 延迟极度敏感、资源受限 | 稠密检索（单路） | 省去稀疏索引构建和 RRF 融合开销 |
| 对召回率要求极高（法律、医疗） | 混合检索 + 重排序 + 多查询扩展 | 多路召回提升覆盖率 |

> 面试要点：混合检索适合企业知识库等既要语义又要精确关键词的场景；纯语义问答可只用稠密；精确代码/错误码可只用稀疏；延迟极度敏感可单路稠密；对召回要求极高用混合＋重排序＋多查询扩展。

## Q13. 混合检索的代价是什么？怎么控制延迟？

**回答**

混合检索比单一稠密检索多开销：

1. **两路索引维护成本**：既要维护向量数据库，又要维护倒排索引/BM25 索引，数据写入要同步两路。
2. **查询延迟**：两路检索串行的话延迟叠加；并行可用 `asyncio.gather` 把延迟压到“较慢的那路”。
3. **融合与重排开销**：RRF 融合和 Cross-encoder 重排都增加额外计算。

**控制延迟的方法：**

- 两路检索**并发执行**（`asyncio.gather`），延迟取 max(稠密, 稀疏) 而非两者之和。
- 稀疏检索对**短术语/标准引用**可单独走（跳过稠密 Embedding）；稠密对**口语/同义词**可单独走（跳过 BM25），实现智能路由，60%+ 查询可跳过冗余分支。
- 重排序只对融合后的少量候选（如 Top-50）进行，不做全量重排。
- 重排序失败时**降级**（保持融合后原序），避免重排序挂掉导致整个链路不可用。

> 面试要点：混合检索代价是双索引维护、查询延迟叠加、融合重排开销。控制延迟：两路并发、智能路由（短术语走稀疏、口语走稠密，60%+ 查询可跳过一路）、重排只做少量候选、重排失败降级。

## Q14. 怎么评测检索质量？核心指标有哪些？

**回答**

检索质量评测需要带标注答案的测试查询集。核心指标有三个：

| 指标 | 直觉解释 | 公式/含义 |
|------|---------|----------|
| Recall@K（召回率@K） | 包含正确答案的文档出现在前 K 个检索结果中的查询比例 | “该找的找到了吗”，是 RAG 最贴近需求的指标 |
| MRR（平均倒数排名） | 每个查询取第一个相关文档排名的倒数再平均 | 排第 1 得 1 分，排第 10 得 0.1 分，“找到得够不够靠前” |
| nDCG（归一化折损累积增益） | 综合所有相关文档的排名与相关程度，越靠后折扣越大 | “整个排序列表质量如何” |

### Python 示例（Recall@K）

```python
def recall_at_k(retriever, eval_set, k=10):
    """
    eval_set: [(query, set_of_relevant_doc_ids), ...]
    """
    hits = 0
    for query, relevant_ids in eval_set:
        retrieved_ids = set(retriever.search(query, top_k=k))
        if retrieved_ids & relevant_ids:
            hits += 1
    return hits / len(eval_set)


eval_set = [
    ("单餐报销上限是多少？", {"chunk_0"}),
    ("出差住宿怎么报销？", {"chunk_1"}),
]
r = recall_at_k(my_retriever, eval_set, k=5)
print(f"Recall@5 = {r:.2%}")
```

**怎么看结果？**

- Recall@10 达到 0.85～0.95 以上，说明检索基础较好。
- 如果 Recall@10 只有 0.5，那不管大模型多强，答案也不会准——证据根本没检索到。这时候应优化检索（Embedding/分块/混合/重排序），而不是只改 Prompt。

> 面试要点：检索质量核心指标＝Recall@K（找没找到）、MRR（找到靠不靠前）、nDCG（排序质量整体好坏）。Recall@K 是 RAG 最终答案准确率的上限，低于预期时应优化检索而非只改 Prompt。

## Q15. 检索进阶常见的坑有哪些？怎么避免？

**回答**

| 常见坑 | 后果 | 避免方法 |
|--------|------|---------|
| 只用稠密检索，忽略精确关键词 | 代码/型号/数字查不到 | 加入稀疏 BM25 做混合检索 |
| 稠密和稀疏得分直接相加 | 尺度不一致，融合结果乱 | 用 RRF 或归一化后加权 |
| 对全量文档做 Cross-encoder 重排 | 延迟极高，不可用 | 只对融合后 Top-50 候选重排 |
| 重排序模型挂掉，链路中断 | 整个检索不可用 | 重排序失败降级，保持融合原序 |
| 查询太模糊（口语、缩写） | 召回率低 | 查询改写 / HyDE / 多查询扩展 |
| 检索结果大量重复片段 | 浪费上下文窗口 | MMR 多样性选 Top-K |
| 不做检索质量评测 | 不知道检索好不好 | 用 Recall@K/MRR/nDCG 带标注集评测 |

> 面试要点：检索进阶常见坑包括只用稠密漏精确关键词、得分直接相加尺度不一、全量 Cross-encoder 重排太慢、重排序失败不降级、模糊查询不改写、结果重复不用 MMR、不做 Recall@K 评测。各有对应避免方法。

## Q16. 什么是查询重构（Query Rewriting）？为什么用户原始问题不适合直接检索？

**回答**

查询重构是在把用户问题送进检索系统前，先用 LLM 或规则把问题改写成更适合检索的形式。

用户原始问题常有三个问题：

1. **口语化、缩写**：比如“退钱咋办”、“报销额度是多少来着”，检索系统可能看不懂缩写和口语。
2. **指代不明**：多轮对话里的“这个”“那个”指代不明，单轮检索时缺乏上下文。
3. **表达不完整**：用户只说了半截，关键信息缺失。

查询重构把这些问题转成更结构化、语义清晰、自包含的查询，再送入检索，能显著提升召回率。

ASCII 示意：

```
用户原始问题              查询重构              送入检索
┌─────────────┐         ┌─────────────┐      ┌─────────────┐
│ “报销额度咋 │─────────▶│ “公司单餐   │─────▶│ 向量检索 + BM25 │
│ 回事？”     │         │ 报销上限是   │      │ （改写后的查询） │
└─────────────┘         │ 多少？”       │      └─────────────┘
                        └─────────────┘
                          (自包含、结构化)
```

> 面试要点：查询重构是在检索前把用户问题改写成更适合检索的形式，解决口语化、缩写、指代不明、表达不完整等问题，提升召回率。

## Q17. 怎么用 Python 实现查询改写？给一个可运行示例。

**回答**

下面用一个轻量规则分类器 + LLM 改写的组合，演示查询改写。对不需要改写的“正常”查询直接跳过，省延迟和成本。

```python
import re
import hashlib
from typing import Dict, Optional

# 模拟 LLM 改写（实际替换为真实 LLM API 调用）
def llm_rewrite(query: str, strategy: str) -> str:
    # 这里用简单规则模拟，实际应调用大模型 API
    if strategy == "colloquial":
        return query.replace("咋办", "怎么办").replace("啥", "什么")
    if strategy == "abbreviation":
        return query.replace("CT", "互感器").replace("PT", "电压互感器")
    return query

# 缓存（实际用 Redis）
rewrite_cache: Dict[str, str] = {}

def classify(query: str) -> Dict:
    """纯规则分类，判断 query 类型，决定是否改写及用哪个 prompt"""
    colloquial_words = {"咋", "咋办", "咋整", "啥", "啥叫", "啥样", "嘛"}
    abbrev_words = {"CT", "PT", "SF6", "GIS", "VT", "AVR", "RTU", "SCADA"}
    q = query.lower()
    if len(query) < 8 or any(w in q for w in colloquial_words):
        return {"type": "colloquial", "skip": False, "hint": "口语化，建议改写"}
    if any(w in query for w in abbrev_words):
        return {"type": "abbreviation", "skip": False, "hint": "含缩写，建议改写"}
    return {"type": "normal", "skip": True, "hint": "正常表达，可跳过改写"}

def rewrite_query(query: str) -> str:
    """带缓存和自适应开关的查询改写"""
    cache_key = "rewrite:" + hashlib.md5(query.encode()).hexdigest()
    if cache_key in rewrite_cache:
        return rewrite_cache[cache_key]

    cls = classify(query)
    if cls["skip"]:
        rewrite_cache[cache_key] = query
        return query

    rewritten = llm_rewrite(query, cls["type"])
    rewrite_cache[cache_key] = rewritten
    return rewritten


# 使用示例
for q in ["报销额度咋办？", "DL/T 596 标准是什么？", "单餐报销上限是多少？"]:
    print(f"原始：{q} -> 改写：{rewrite_query(q)}")
```

运行效果示例：

```
原始：报销额度咋办？ -> 改写：报销额度怎么办？
原始：DL/T 596 标准是什么？ -> 改写：互感器/电压互感器 标准是什么？
原始：单餐报销上限是多少？ -> 改写：单餐报销上限是多少？
```

> 面试要点：查询改写示例＝纯规则分类器（口语/缩写/正常）+ LLM 改写 + Redis 缓存。正常查询直接跳过改写，省延迟和成本；缓存相同查询的改写结果，避免重复调用 LLM。

## Q18. 什么是 HyDE（假设文档嵌入，Hypothetical Document Embedding）？原理是什么？

**回答**

HyDE 的核心思路是：**与其对“问题”做 Embedding，不如让 LLM 先根据问题生成一个“假设答案”（假想的完美文档），再用这个假设答案的 Embedding 去检索真实文档。**

用户的原始问题往往很短、很模糊，直接向量化后和文档向量的语义差距可能较大。HyDE 先生成一个详细的假设答案，这个假设答案的内容和语气更接近真实文档，用它去向量数据库搜索，能缩小“查询—文档”的语义 gap，提升召回率。

流程：

```
用户问题
    │
    ▼
LLM 生成假设答案（“如果这是一篇文档，应该怎么写”）
    │
    ▼
把假设答案 Embedding 向量化
    │
    ▼
在向量数据库里搜索最相近的真实文档
    │
    ▼
返回真实文档给大模型生成最终答案
```

### Python 示例

```python
from sentence_transformers import SentenceTransformer
import numpy as np

model = SentenceTransformer("BAAI/bge-small-zh-v1.5")

# 知识库
docs = ["单餐报销不超过200元，需提供发票。",
        "出差住宿可报销，每晚不超过500元。",
        "员工入职后享有5天带薪年假，需提前申请。"]
doc_embs = model.encode(docs, normalize_embeddings=True)

# HyDE：先用 LLM 生成假设答案（这里用模拟函数）
def generate_hypothetical_answer(query: str) -> str:
    # 实际应调用 LLM API
    if "报销" in query and "上限" in query:
        return "单餐报销上限为200元，员工需提供合法发票才能报销。"
    return query

query = "单餐报销上限是多少？"
hypothetical = generate_hypothetical_answer(query)  # "单餐报销上限为200元..."
hyp_emb = model.encode([hypothetical], normalize_embeddings=True)[0]

# 用假设答案向量去搜真实文档
sims = np.dot(doc_embs, hyp_emb)
best_idx = int(np.argmax(sims))
print(f"HyDE 检索到：{docs[best_idx]}")
```

**优缺点：**

- 优点：从“答案相似性”而非“问题相似性”匹配，更贴近用户潜在意图，对短/模糊查询效果好。
- 缺点：多一次 LLM 调用，增加延迟和成本；生成的假设答案可能有偏差，导致检索方向错。

> 面试要点：HyDE 先让 LLM 生成假设答案，再用假设答案的 Embedding 去检索真实文档，缩小查询—文档语义 gap。适合短/模糊查询，代价是多一次 LLM 调用。建议配合缓存和置信度门控（只有基线检索效果差时才启用 HyDE）。

## Q19. 什么是多查询（Multi-Query）？一问多查怎么融合？

**回答**

多查询是指把一个用户问题扩展成多个不同角度的子查询，分别检索，再把结果合并。一个问题可能有多种表述方式，单一查询可能漏掉部分相关文档；多查询能提升覆盖率。

例子：

- 原问题：“对比主变和配变温度处置”
- 扩展为：
  1. “主变压器温度处置规定”
  2. "配变压器温度处置标准"

分别检索后，结果走 **RRF 融合** 合并成一个统一排名。

### Python 示例

```python
def multi_query_decompose(query: str, n: int = 2):
    """把一个问题拆成 n 个子查询（实际应调用 LLM）"""
    if "对比" in query and "主变" in query and "配变" in query:
        return [
            "主变压器温度处置规定",
            "配变压器温度处置标准",
        ]
    return [query]

def multi_query_search(query, retriever, top_k=5, candidate_k=10):
    sub_queries = multi_query_decompose(query, n=2)
    all_rankings = []
    for sq in sub_queries:
        _, ids = retriever.search(sq, top_k=candidate_k)  # 返回按排名排序的 doc_id
        all_rankings.append(ids)

    # RRF 融合多路结果
    fused = rrf_fuse(all_rankings, k=60)
    top_ids = [doc_id for doc_id, _ in fused[:top_k]]
    return top_ids
```

**优缺点：**

- 优点：覆盖多种表述，召回率更高，对复杂/多方面问题效果好。
- 缺点：每个子查询都要检索一次，延迟和成本随子查询数量线性增长；建议配合缓存和置信度门控（只有基线检索效果差时才扩展多查询）。

> 面试要点：多查询＝把一个问题扩展成多个子查询分别检索，再用 RRF 融合结果。提升召回覆盖率，但延迟和成本随子查询数增加，建议配合缓存和置信度门控。

## Q20. 什么是 Step-back Prompting？在检索里怎么用？

**回答**

Step-back Prompting（退一步提示）的核心思想是把原始问题“抽象上推”一层，生成一个更高层、更通用的问题，同时检索原问题和抽象问题，再融合结果。

例子：

- 原问题：“2023 年 GPT-4 架构是怎样的？”
- 抽象后：“大语言模型架构是如何演进的？”

抽象问题能检索到更宽泛的背景知识，帮助模型理解原问题的上下文；两路结果合并后，既有宏观背景，又有具体答案。

**什么时候用？** 当原问题过于具体、检索不到足够背景知识时，用 Step-back 补齐上下文。

ASCII 示意：

```
原问题（具体）          抽象问题（上推一层）
┌─────────────┐        ┌──────────────────┐
│ GPT-4架构？ │        │ LLM架构演进？     │
└──────┬──────┘        └────────┬─────────┘
       │                       │
       ▼                       ▼
   检索具体细节              检索宏观背景
       │                       │
       └─────────┬─────────────┘
                 ▼
           融合结果 → 大模型生成答案
```

> 面试要点：Step-back Prompting 把具体问题抽象成更高层的问题，同时检索两路并融合，补齐背景知识。适合原问题过于具体、缺乏上下文场景。

## Q21. 什么是查询分解（Query Decomposition）？复杂问题怎么拆子问题？

**回答**

查询分解是指把一个复杂的多跳问题拆成多个简单的子问题，分别检索，再把子问题的答案合并回答原问题。

例子：

- 复杂问题：“对比主变和配变温度处置的异同”
- 拆分为：
  1. “主变压器温度处置规定是什么？”
  2. “配变压器温度处置标准是什么？”

分别检索出两个子问题的答案，再合并对比。

**拆分策略：**

- 单步分解：一次拆成多个独立子问题，分别检索，答案合并。
- 多步分解：每一步的检索结果作为下一步查询的输入，直到无法再拆。

> 面试要点：查询分解把复杂多跳问题拆成多个简单子问题，分别检索再合并答案。单步分解适合独立子问题，多步分解适合需要前一步结果才能进行下一步的场景。

## Q22. 什么是查询路由（Query Routing）？怎么把查询分发到不同检索路径？

**回答**

查询路由是指根据查询内容，将其分配到最适合的检索子系统或索引，避免每条查询都走全量稠密＋稀疏链路，省延迟和成本。

常见路由策略：

1. **元数据路由（Metadata Router）**：从查询中提取实体（如商品名、时间、类别），基于 chunk 元数据筛选。比如查询含“2023年财报”，只检索带“2023”时间戳的文档块。
2. **语义路由（Semantic Router）**：通过语义理解把查询归类到不同通道。比如“法律相关问题”走法律文档索引，“技术问题”走技术百科。
3. **混合路由（Hybrid Routing）**：综合元数据和语义信息，先粗过滤候选集，再语义细分路由。

路由决策示例：

```
查询特征          路由路径
─────────────────────────────
短术语/标准号    → 稀疏检索（BM25），跳过稠密 Embedding
口语/同义词      → 稠密检索，跳过 BM25
默认/复杂        → 混合检索（稠密+稀疏+RRF）
```

> 面试要点：查询路由按查询特征分发到不同检索路径（稀疏/稠密/混合），60%+ 查询可跳过冗余分支，p95 检索延迟可降 30～50%。常见策略：元数据路由、语义路由、混合路由。

---

## Q23. 语义路由和元数据路由有什么区别？分别适合什么？

**回答**

| 路由方式 | 依据 | 实现方式 | 适合场景 |
|---------|------|---------|---------|
| 元数据路由 | 查询中的实体、时间、类别等结构化信息 | 提取实体 → 基于 chunk 元数据过滤 | 文档有清晰标签（部门、日期、文档类型）、企业知识库 |
| 语义路由 | 查询的语义意图 | 语义分类模型或 LLM 做路由决策 | 文档分领域明显（法律/技术/医疗）、意图区分明显 |

**例子：**

- 元数据路由：用户问“2023 年 Q3 财报”，路由到元数据里 `year=2023, quarter=Q3` 的文档块。
- 语义路由：用户问“离职赔偿怎么算”，语义识别为“HR/法律”，路由到 HR 法规索引。

两者可混合：先元数据粗过滤，再语义细分。

> 面试要点：元数据路由基于结构化标签（部门、日期、类型），适合有清晰元数据的企业知识库；语义路由基于查询意图，适合领域明显的文档集。生产上常混合：先元数据粗过滤，再语义细分路由。

## Q24. 查询路由的 Python 代码示例长什么样？

**回答**

下面是一个轻量查询路由示例，根据查询特征决定走稀疏、稠密还是混合路径：

```python
from enum import Enum
from typing import NamedTuple

class Route(str, Enum):
    SPARSE = "sparse"       # 只走 BM25
    DENSE = "dense"         # 只走向量
    HYBRID = "hybrid"       # 稠密+稀疏+RRF

class RoutingDecision(NamedTuple):
    route: Route
    reason: str

def route_query(query: str) -> RoutingDecision:
    # 短术语/标准号：走稀疏，跳过稠密 Embedding（省延迟）
    if len(query) <= 20 and any(ch.isdigit() for ch in query):
        return RoutingDecision(Route.SPARSE, "短术语含数字，走 BM25")

    # 口语/同义词：走稠密，跳过 BM25
    colloquial = {"咋办", "啥", "怎么", "怎样", "如何"}
    if any(w in query for w in colloquial):
        return RoutingDecision(Route.DENSE, "口语化表达，走向量检索")

    # 默认：混合检索
    return RoutingDecision(Route.HYBRID, "默认走稠密+稀疏+RRF")


# 使用示例
for q in ["DL/T 596", "报销额度咋办？", "单餐报销上限和出差住宿标准分别是多少？"]:
    decision = route_query(q)
    print(f"查询：{q} -> 路由：{decision.route.value} ({decision.reason})")
```

运行效果示例：

```
查询：DL/T 596 -> 路由：sparse (短术语含数字，走 BM25)
查询：报销额度咋办？ -> 路由：dense (口语化表达，走向量检索)
查询：单餐报销上限和出差住宿标准分别是多少？ -> 路由：hybrid (默认走稠密+稀疏+RRF)
```

> 面试要点：查询路由示例＝根据查询长度、是否含数字、是否含口语词，决定走 sparse/dense/hybrid。生产上可把规则替换为 LLM 分类器，并加缓存避免重复路由决策。

## Q25. 缓存在检索进阶里怎么用？缓存什么？

**回答**

检索链路中可以缓存三类内容，显著降低延迟和成本：

1. **Embedding 缓存**：按文本内容哈希（MD5）缓存向量，相同文本不重复向量化。
2. **查询改写缓存**：按 `rewrite:{策略}:{md5(查询)}` 缓存 LLM 改写结果，相同查询不重复调用 LLM。
3. **问答缓存**：按「命名空间版本号 + 问题哈希」缓存完整问答结果，文档变更后版本号自增，旧缓存自动失效。仅对无历史上下文的独立问题生效。

Redis 不可用时自动降级（直接走真实检索），保证链路可用。

> 面试要点：缓存三类＝Embedding 缓存（文本哈希）、查询改写缓存（策略+查询哈希）、问答缓存（命名空间版本+问题哈希）。Redis 不可用时降级到真实检索，保证链路可用。

## Q26. 什么是 CRAG（检索增强生成的自纠错）？检索不足时怎么处理？

**回答**

CRAG（Corrective RAG）是在检索后增加一个“自纠错”环节：对检索到的片段进行分级，如果判断召回不足或检索结果与问题无关，不直接送大模型生成，而是触发查询改写并重新检索，最多重试 N 次。

流程：

```
检索 → 评估检索质量（相关/部分相关/无关）
    │
    ├─ 相关 ──▶ 送大模型生成答案
    │
    ├─ 部分相关 ──▶ 尝试生成，但标注不确定性
    │
    └─ 无关/不足 ──▾ 查询改写 → 重新检索 → 再评估
                       │
                       └─ 达到最大重试次数 ──▶ 兜底回答（告知无相关信息）
```

**评估方法：** 可用轻量模型或规则判断检索片段与问题的相关性；也可用重排序最高分作为阈值，低于阈值就判定为不足。

> 面试要点：CRAG＝检索后自纠错，评估检索片段相关性，不足时查询改写＋重新检索，最多重试 N 次，最后兜底。避免基于无关检索结果生成幻觉答案。

## Q27. 检索进阶的完整流水线（7 步）长什么样？

## Q28. 检索进阶的代价是什么？怎么做成本控制？

**回答**

检索进阶比基础 RAG 多开销：

1. **查询改写/多查询/HyDE**：每条都要多调用一次 LLM，延迟和成本随使用频率线性增长。
2. **双索引维护**：向量索引＋倒排索引，写入要同步两路。
3. **重排序**：Cross-encoder 对 Top-50 候选逐一打分，增加计算。
4. **MMR/small-to-big/RAPTOR**：额外的后处理逻辑。

**成本控制方法：**

- **置信度门控**：只有基线检索效果差（如重排序最高分低于阈值）时，才启用改写/HyDE/多查询，可省 <40% 查询的改写成本。
- **缓存**：Embedding 缓存、改写缓存、问答缓存，相同查询不重复计算。
- **智能路由**：短术语走稀疏、口语走稠密，60%+ 查询跳过冗余分支，p95 延迟降 30～50%。
- **重排序降级**：重排序失败时保持融合原序，不中断链路。
- **Redis 不可用降级**：缓存层挂了直接走真实检索，保证可用性。

> 面试要点：检索进阶代价是多次 LLM 调用、双索引维护、重排序和后处理开销。成本控制：置信度门控（<40% 查询走改写）、三级缓存、智能路由（60%+ 查询跳过一路）、重排序降级、缓存层挂了降级真实检索。

---

## Q29. 重排序失败了怎么办？如何保证链路可用性？

**回答**

重排序（Cross-encoder）可能因模型服务挂掉、输入过长、解析失败等原因失败。保证可用性的做法：

1. **降级（Fallback）**：重排序失败时，保持 RRF 融合后的原序，直接取 Top-K 送大模型，不中断链路。
2. **超时控制**：给重排序调用设置超时，超时即视为失败并降级。
3. **异常捕获**：把重排序调用包在 `try/except` 里，任何异常都记录日志并降级。
4. **健康检查**：定期探测重排序服务健康度，不可用时自动标记为降级模式，恢复后自动重启。

> 面试要点：重排序失败降级＝保持融合原序、设置超时、try/except 捕获异常、健康检查自动标记降级。确保重排序不可用时链路仍能返回结果，不中断 RAG 服务。

## Q30. 本章小结：一个初学者该怎么做 RAG 检索进阶？

**回答**

检索进阶不是一次性堆砌所有技术，建议按这个路径逐步上：

1. **先跑通基础 RAG**：稠密检索 + 大模型生成，能回答简单问题。
2. **加混合检索**：稠密 + BM25 + RRF，解决精确关键词漏检问题，召回率明显提升。
3. **加重排序**：Cross-encoder 对 Top-50 候选精排，提升答案准确率（失败时降级）。
4. **加查询重构**：查询改写 + HyDE + 多查询，解决口语/模糊查询召回低（配合置信度门控和缓存控制成本）。
5. **加查询路由**：按查询特征分发稀疏/稠密/混合路径，60%+ 查询跳过冗余分支，降低延迟。
6. **加多样性与父子检索**：MMR 避免重复片段，small-to-big 兼顾精准与完整。
7. **加自纠错与评测**：CRAG 自纠错，Recall@K/MRR/nDCG 持续评测调优。

一句话总结：**检索进阶的核心是“召回更全、排序更准、延迟更低、成本可控”。先混合检索＋重排序建 baseline，再按需加查询重构、路由、MMR、父子分块和 CRAG，每一步都要带指标评测，别为技术而技术。**

> 面试要点：入门路径＝基础 RAG→混合检索（稠密+稀疏+RRF）→重排序（Cross-encoder）→查询重构（改写/HyDE/多查询）→查询路由→MMR+small-to-big→CRAG+指标评测。每一步都要带 Recall@K 等指标验证，避免为技术而技术。
