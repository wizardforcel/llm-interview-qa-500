## Q1. 什么是 GraphRAG？它和传统向量 RAG 有什么核心区别？

**回答**

GraphRAG（Graph-based Retrieval-Augmented Generation，图增强检索生成）是由 Microsoft Research 提出的一种 RAG 架构。它的核心思想是：**先把非结构化文本转成知识图谱（实体＋关系），再基于图结构做检索和生成**，而不是只做“向量相似度匹配文本块”。

传统向量 RAG 把文档切成文本块（Chunk），向量化后存入向量数据库，查询时找语义最相近的若干块。这种方式擅长“局部事实、条款、定义、操作步骤”，但对**跨文档多跳推理**和**全局性主题归纳**较弱。

GraphRAB 用知识图谱显式存储实体之间的关联，检索可以沿着关系路径走；图社区的摘要则能覆盖整个语料库。它擅长“主题归纳、趋势、跨文档冲突、全局综述”。

两者对比表：

| 维度 | 向量 RAG | GraphRAG |
|------|---------|---------|
| 索引单位 | 文本块（chunk） | 实体、关系、社区摘要 |
| 检索单位 | 语义最相近的若干块 | 相关社区 / 实体邻域 |
| 擅长问题 | 局部事实、条款、定义、操作步骤 | 主题归纳、趋势、跨文档冲突、全局综述 |
| 答案形态 | 基于片段的直接回答 | 基于多来源聚合的总结，带主题结构 |
| 索引成本 | 低，一次 embedding 即可 | 高，LLM 抽取＋社区检测＋逐社区摘要耗时耗 token |
| 查询延迟 | 毫秒到秒级 | 秒到数十秒，map-reduce 放大调用量 |
| 增量更新 | 单块重插即可 | 可能触发社区重划与摘要重算 |
| 可解释性 | 靠引用溯源 | 额外提供社区、关系路径与证据链 |

> 面试要点：GraphRAG 是用知识图谱替代或补充纯文本块做检索，擅长多跳推理和全局主题归纳，代价是索引成本和查询延迟都更高。它和向量 RAG 不是替代关系，而是可组合的零件。

## Q2. GraphRAG 适合什么场景？什么场景不适合？

**回答**

**适合上 GraphRAG 的场景：**
- 语料是“一批互相关联、需要整体理解的文档”，比如研报、舆情、访谈记录、案件卷宗、事故报告、竞品资料；
- 用户真会问全局性问题，比如“这 5,000 份事故报告的主要主题是什么？”、“甲公司与乙公司签了竞业限制，乙后来被丙收购，条款对丙是否有效？”（需要跨文档多跳推理）；
- 能接受更高的索引成本和查询延迟；
- 对可解释性有要求，需要给出可审计的关系路径与证据链。

**不适合上 GraphRAG 的场景：**
- FAQ 与知识条目问答、精确条款与编号查询；
- 预算或交付周期紧张；
- 数据每小时都在变（增量更新代价高）；
- 团队还没有把基础 RAG 的切分与评测做扎实。

**务实的折中：混合路由。** 事实型问题走向量＋关键词＋重排；主题型问题走社区摘要；用分类器或规则分流，两套索引共享同一份文档底座。

> 面试要点：GraphRAG 适合“互相关联、需整体理解”的语料和全局性/多跳问题；不适合 FAQ、精确条款查询、高频变更数据、预算紧张场景。务实做法是混合路由：事实型走向量 RAG，主题型走 GraphRAG 社区摘要。

## Q3. GraphRAG 的核心工作流程分哪两个阶段？

**回答**

GraphRAG 的整体流程分为“离线索引构建”与“在线查询检索”两大阶段，形成“先建图、再检索”的完整闭环。

### 阶段一：离线索引构建（建图）

1. **文本块切分**：源文档切成若干文本块（TextUnit），作为后续处理的基本单元。
2. **实体与关系抽取**：LLM 对每个文本块识别实体（名称、类型、描述）与关系（源实体、目标实体、关系描述），输出结构化的图元素。
3. **图聚合与去重**：各文本块抽取出的实体与关系聚合为统一的无向加权图；边的权重反映共现频率与强度；不同名称变体的同一实体归并为规范节点。
4. **社区检测**：用社区检测算法（如 Leiden、Louvain）对图做层次化聚类，形成不同粒度的图社区。
5. **社区摘要**：LLM 为每个社区生成自然语言摘要，构建可被查询复用的“社区层级索引”。

### 阶段二：在线查询检索（查图）

1. 用户提出问题，系统根据问题类型选择检索模式（Local 局部搜索 / Global 全局搜索 / Basic 基础检索）。
2. 从知识图谱与社区摘要中定位相关内容，组装为增强上下文。
3. LLM 基于组装后的上下文生成最终回答，并可追溯到具体的实体、关系与源文本。

ASCII 示意：

```
离线索引构建（建图）                    在线查询检索（查图）
┌─────────────┐                        ┌─────────────┐
│ 原始文档    │                        │ 用户提问    │
│   │         │                        │   │         │
│   ▼         │                        │   ▼         │
│ 文本块切分  │                        │ 选择检索模式│
│   │         │                        │   │         │
│   ▼         │                        │   ▼         │
│ LLM抽取实体 │                        │ 图检索      │
│ 与关系      │───────────────────────▶│（社区摘要   │
│   │         │                        │ ＋实体邻域）│
│   ▼         │                        │   │         │
│ 知识图谱    │                        │   ▼         │
│ 社区检测    │                        │ LLM 生成    │
│ 社区摘要    │───────────────────────▶│ 回答        │
└─────────────┘                        └─────────────┘
```

> 面试要点：GraphRAG 分两阶段。离线阶段：切分→LLM 抽取实体关系→图聚合去重→社区检测（Leiden）→社区摘要；在线阶段：选检索模式→图检索（社区摘要＋实体邻域）→LLM 生成回答。

## Q4. GraphRAG 的知识图谱由哪三类核心元素组成？

**回答**

GraphRAG 的图索引由三类核心元素构成，分别对应图的节点、边和协变量：

1. **实体（Entity，节点）**：代表文本中出现的具体对象，如人物、组织、地点、技术、概念。每个实体包含名称、类型、描述信息，描述由 LLM 基于源文本抽象生成。实体是社区划分与检索推理的基本锚点。
2. **关系（Relationship，边）**：描述两个实体之间的明确联系。每条关系包含源实体、目标实体和对联系的描述。关系将分散在不同文档中的实体连接起来，是支撑多跳推理的结构基础。
3. **声明（Claim，协变量）**：附着在实体上的协变量，表示与实体相关的可核验的陈述，用于辅助推理和验证。

ASCII 示意（三元组）：

```
实体A（人物：张三） ──[关系：就职于]──> 实体B（组织：某公司）
      │                                      │
      ▼                                      ▼
  声明：张三是某公司技术部经理          声明：某公司总部在北京
```

> 面试要点：GraphRAG 图谱三类核心元素＝实体（节点）、关系（边）、声明（协变量）。实体和关系由 LLM 从文本中抽取，声明附着在实体上提供可核验的陈述。

## Q5. 什么是社区检测？GraphRAG 里常用什么算法？社区摘要有什么用？

**回答**

社区检测是指把知识图谱中联系紧密的实体分组成“社区”，形成层次化的社区结构。GraphRAG 里常用 **Leiden 算法**（也可用 Louvain）做社区聚类。

社区摘要的作用：
- LLM 为每个社区生成自然语言摘要，描述该社区内实体及其关系的核心语义；
- 层次化社区支持自底向上的摘要：底层社区摘要先生成，高层社区摘要通过综合子社区摘要生成，形成层次化摘要体系；
- 高层摘要既保持对底层细节的感知，又提供更整合的全局视角，这是实现“全局理解”的关键。

> 面试要点：社区检测把联系紧密的实体分组成社区，GraphRAG 常用 Leiden 算法；社区摘要由 LLM 生成，支持层次化自底向上抽象，是 GraphRAG 实现全局主题归纳的关键。

## Q6. GraphRAG 的查询有哪几种模式？Local 局部搜索和 Global 全局搜索怎么选？

**回答**

GraphRAG 提供两种主要查询模式（部分实现还有 Basic 基础检索）：

**Local 模式（局部搜索）**：用于针对具体事实的提问。从问题中提到的实体出发，收集其邻居、关系、社区报告，以及提及这些实体的原始文本单元，沿图路径做多跳推理。

**Global 模式（全局搜索）**：用于支持全局型查询任务。基于 map-reduce 框架，将查询映射到各个社区摘要，并行生成局部答案，再通过 reduce 阶段整合为最终回答。适合“这 5,000 份事故报告的主要主题是什么？”这类需要整体洞察的问题。

怎么选：
- 问题**提到了具体实体**（如“哪些工厂依赖某个供应商”）→ 走 **Local 模式**；
- 问题**询问整个语料库的主题/趋势**（如“主要主题是什么？”）→ 走 **Global 模式**；
- 不确定时，可用意图分类器先判断是否命名了具体实体，再分流。

ASCII 示意（路由决策）：

```
用户提问
    │
    ▼
┌─────────────────┐
│ 提到具体实体？   │──是──▶ Local 模式（图遍历多跳）
│（意图分类/ NER） │        收集邻居、关系、社区报告
└────────┬────────┘        │
     否                     ▼
     │              LLM 基于图上下文生成答案
     ▼
┌─────────────────┐
│ Global 模式      │
│（社区摘要 map-reduce） │
└─────────────────┘
```

> 面试要点：GraphRAG 查询模式＝Local 局部搜索（从提到的实体出发沿图遍历，适合具体事实）和 Global 全局搜索（社区摘要 map-reduce，适合全局主题归纳）。选型依据：提到具体实体选 Local，询问整体主题选 Global。

## Q7. 什么是图遍历？GraphRAG 怎么用图遍历做多跳推理？

**回答**

图遍历是指从知识图谱中的某个实体节点出发，沿着关系边向外扩展，收集相连的实体和关系。GraphRAG 的 Local 模式本质上就是图遍历：从问题中提到的实体出发，沿关系向外遍历若干跳，收集上下文。

例子：问题“哪些工厂可能受台风影响？”知识图谱里有“台风关闭高雄港”“高雄港给供应商 A 运零件”“供应商 A 给俄亥俄工厂供应轴承”。没有任何单份源文档陈述了这种关联，但图遍历可以沿路径“台风 → 高雄港 → 供应商 A → 俄亥俄工厂”做四跳推理，发现俄亥俄工厂面临风险，同时排除无关的德州工厂。

### Python 示例（NetworkX 图遍历）

```python
import networkx as nx

# LLM 从不同文档中抽取的三元组
triples = [
    ("台风", "关闭", "高雄港"),
    ("高雄港", "给", "供应商A 运零件"),
    ("供应商A", "给", "俄亥俄工厂供应轴承"),
    ("台风", "关闭", "德州港"),   # 无关分支
    ("德州港", "给", "德州工厂运零件"),
]

graph = nx.DiGraph()
for head, relation, tail in triples:
    graph.add_edge(head, tail, relation=relation)

# 局部搜索：从问题实体“台风”出发，沿关系向外遍历（BFS）
edges = list(nx.bfs_edges(graph, "台风", depth_limit=4))
context = [f"{head} --[{graph[head][tail]['relation']]}--> {tail}" for head, tail in edges]

print("图遍历上下文：")
for c in context:
    print(c)
```

运行效果示例：

```
图遍历上下文：
台风 --[关闭]--> 高雄港
台风 --[关闭]--> 德州港
高雄港 --[给]--> 供应商A 运零件
德州港 --[给]--> 德州工厂运零件
供应商A --[给]--> 俄亥俄工厂供应轴承
```

LLM 收到这些图遍历上下文作为依据，据此回答“俄亥俄工厂面临风险”。

> 面试要点：图遍历＝从实体节点沿关系边向外扩展，GraphRAG Local 模式用它做多跳推理。Python 可用 NetworkX 的 `bfs_edges` 做宽度优先遍历，限制深度防止无限扩张。

## Q8. GraphRAG 的优势和劣势分别是什么？

**回答**

**优势：**
- 支持跨文档多跳推理，向量 RAG 做不好的“绕几个弯”的问题能回答；
- 全局主题归纳能力强，社区摘要能覆盖整个语料库；
- 可解释性更好，能提供社区、关系路径与证据链，便于审计；
- 与向量 RAG 互补，可混合路由。

**劣势：**
- 索引成本高：LLM 抽取实体关系、社区检测、逐社区摘要都耗时耗 token；
- 查询延迟高：秒到数十秒，map-reduce 放大模型调用量；
- 增量更新复杂：新数据可能触发社区重划与摘要重算，不像向量 RAG 单块重插即可；
- 对本体和图谱质量要求高，团队需要有人能维护本地、写 Cypher、盯图谱质量。

> 面试要点：GraphRAG 优势是多跳推理、全局归纳、可解释性；劣势是索引成本高、查询延迟高、增量更新复杂、对团队能力要求高。不适合作为所有场景的默认选型，而是“问题类型变了”后的升级。

## Q9. 什么时候应该上 GraphRAG？什么时候别上？给一个务实的决策建议。

**回答**

**应该上 GraphRAG：**
- 语料互相关联、需整体理解（研报、舆情、访谈、案件卷宗、事故报告、竞品资料）；
- 用户真会问全局性或多跳问题；
- 能接受更高索引成本和延迟；
- 对可解释性/可审计性有要求。

**别上 GraphRAG：**
- FAQ 与知识条目问答、精确条款与编号查询；
- 预算或交付周期紧张；
- 数据每小时都在变；
- 基础 RAG 的切分与评测还没做扎实。

**决策八问**（按这八问过一遍比看榜单更管用）：
1. 问题类型：用户主要问事实、问关系，还是问全局趋势？
2. 数据形态：是规整条目、长文档，还是天然带实体关系的记录？
3. 更新频率：季度更新的制度库，还是每天新增的工单流？
4. 规模：十万块、千万块，还是十亿向量？
5. 延迟与成本预算：能否接受一次问答几十秒、几十次模型调用？
6. 可解释要求：是否必须给出可审计的推理路径？
7. 团队能力：有没有人能维护本体、写 Cypher、盯图谱质量？
8. 验收方式：有没有真实问题评测集来证明新方案确实更好？

> 面试要点：GraphRAG 不是“技术更先进”的默认选型，而是“问题类型变了”后的升级。务实决策建议是先把朴素 RAG（清洗、切分、混合检索、重排、引用、评测集）做扎实，再按上述八问判断是否引入 GraphRAG。

## Q10. GraphRAG 与向量 RAG 怎么做混合路由？

**回答**

GraphRAG 不是彻底推翻向量检索，而是通过知识图谱的确定性关联补齐向量模型的概率模糊性。工业级事实标准正在变成“图谱定骨架、向量充血肉、LLM 做表达”。

混合路由架构：

```
用户输入 Query
    │
    ▼
┌─────────────────┐
│ 意图分析与实体识别 │（NER / 分类器）
└────────┬────────┘
         │
    ┌────┴────┐
    │         │
    ▼         ▼
向量召回分支   图谱多跳与社区召回分支
（稠密＋稀疏）   （Local/Global 检索）
    │         │
    └────┬────┘
         ▼
┌─────────────────┐
│ 混合结果融合与 RRF │
│ 重排            │
└────────┬────────┘
         ▼
┌─────────────────┐
│ Prompt 上下文装配  │
└────────┬────────┘
         ▼
┌─────────────────┐
│ 生成式大模型 LLM  │
└────────┬────────┘
         ▼
   返回结构化答案与引用
```

路由规则示例：
- 短术语/标准号（“DL/T 596”）→ 走向量检索分支（或稀疏 BM25），跳过图谱；
- 口语/同义词（“报销额度咋办”）→ 走向量检索分支；
- 明确提到多个实体及其关系（“甲公司与乙公司……乙被丙收购……条款对丙是否有效”）→ 走图谱分支；
- 默认/复杂 → 混合两路，RRF 融合后重排。

> 面试要点：GraphRAG 与向量 RAG 做混合路由＝意图分类器分流，事实型/短术语走向量，关系型/多跳走图谱，复杂问题两路并行 RRF 融合＋重排。架构口诀：“图谱定骨架、向量充血肉、LLM 做表达”。

## Q11. GraphRAG 的索引成本和查询延迟高在哪里？怎么优化？

**回答**

**索引成本高的原因：**
- LLM 抽取每个文本块的实体与关系，需要大量模型调用；
- 社区检测（Leiden）和逐社区摘要生成也消耗 token；
- 分块越短，实体召回率越高，但 LLM 调用次数更多，需在召回率与效率之间权衡。

**查询延迟高的原因：**
- Global 模式用 map-reduce，每个社区摘要都要生成部分答案，模型调用量被放大；
- 图遍历多跳也增加计算。

**优化方法：**
- **轻量化抽取**：用更小的抽取模型或传统 NLP 管道配合 LLM，降低索引成本；
- **分块粒度权衡**：不盲目追求短分块，在实体召回率和 LLM 调用数之间找平衡；
- **增量更新**：只更新受影响的社区和摘要，不重建全图（如 LightRAG 的增量式图谱更新）；
- **Fast-GraphRAG**：融合 PageRank 算法，降低运营成本并提高准确率，支持实时更新；
- **缓存社区摘要**：未变更的社区摘要复用，0 LLM 成本。

> 面试要点：GraphRAG 索引成本高在 LLM 抽取＋社区检测＋逐社区摘要，查询延迟高在 map-reduce 多轮模型调用。优化手段：轻量化抽取、分块粒度权衡、增量更新只改受影响社区、Fast-GraphRAG 引入 PageRank、社区摘要缓存复用。

## Q12. GraphRAG 能做增量更新吗？怎么做？

**回答**

GraphRAG 的知识图谱不是一次性建好的，文档新增、修改、删除时需要增量更新，但比向量 RAG 复杂：

- **新增文档**：抽取新文档的实体与关系，合并到现有图谱；涉及的社区可能需要重新检测和摘要。
- **修改文档**：先删掉该文档在图谱里的旧实体/关系，再重新抽取入库；相关社区可能重划。
- **删除文档**：从图谱里删除该文档对应的实体与关系，并重算相关社区摘要。

**优化做法**：只更新受影响的部分图谱结构，不重建全图（如 LightRAG 的增量式图谱更新算法）；对未变更的社区摘要复用，0 LLM 成本；新旧文档用内容哈希（MD5）或修改时间判断是否已处理。

> 面试要点：GraphRAG 能做增量更新，但比向量 RAG 复杂。新增直接合并入图；修改先删旧实体关系再重入库；删除按文档从图谱里删对应实体关系。优化：只改受影响部分社区，不重建全图；社区摘要缓存复用。

## Q13. GraphRAG 的可解释性体现在哪里？

**回答**

GraphRAG 比向量 RAG 多了一层可解释性：

- **关系路径**：答案不是凭空来的，可以追溯到具体的图路径，比如“台风 → 高雄港 → 供应商 A → 俄亥俄工厂”，用户能看清推理链条；

- **可审计**：适合合规、风控、法律等需要审计推理路径的场景。

> 面试要点：GraphRAG 可解释性体现在关系路径可追溯、社区归属可说明、实体关系可溯源到原文。适合合规、风控、法律等需要可审计推理路径的场景。

## Q14. 用 Python 和 NetworkX 搭建一个最小 GraphRAG 原型，代码长什么样？

**回答**

下面是一个极简 GraphRAG 原型：用 NetworkX 构建知识图谱，从问题实体出发做图遍历（Local 搜索），把遍历得到的关系路径作为上下文喂给 LLM 生成答案。

```python
import networkx as nx
from typing import List, Tuple

# 构建知识图谱
def build_graph(triples: List[Tuple[str, str, str]]) -> nx.DiGraph:
    g = nx.DiGraph()
    for head, relation, tail in triples:
        g.add_edge(head, tail, relation=relation)
    return g

# 局部图遍历检索（Local Search）
def local_search(graph: nx.DiGraph, start_entity: str, depth_limit: int = 3) -> List[str]:
    edges = list(nx.bfs_edges(graph, start_entity, depth_limit=depth_limit))
    context = [
        f"{head} --[{graph[head][tail]['relation']]}--> {tail}"
        for head, tail in edges
    ]
    return context

# LLM 生成答案（此处用模拟函数，实际接入真实 LLM API）
def generate_answer(query: str, context: List[str]) -> str:
    ctx_text = "\n".join(context) if context else "无相关图谱信息。"
    return f"""基于以下图谱关系路径回答问题：

{ctx_text}

问题：{query}

答案：(由大模型基于上述图谱上下文生成)
"""

# 使用示例
if __name__ == "__main__":
    triples = [
        ("台风", "关闭", "高雄港"),
        ("高雄港", "给", "供应商A 运零件"),
        ("供应商A", "给", "俄亥俄工厂供应轴承"),
    ]
    graph = build_graph(triples)

    query = "哪些工厂可能受台风影响？"
    context = local_search(graph, "台风", depth_limit=4)
    answer = generate_answer(query, context)

    print("图遍历上下文：")
    for c in context:
        print(f"  {c}")
    print("\n生成的回答：")
    print(answer)
```

> 面试要点：最小 GraphRAG 原型＝NetworkX 构建有向图（实体关系三元组）→从问题实体出发 BFS 图遍历（Local 搜索）→把关系路径作为上下文喂给 LLM 生成答案。生产环境还需加社区检测、社区摘要、Global 模式、向量检索混合等。

## Q16. 什么是多模态 RAG？它和传统文本 RAG 有什么区别？

**回答**

多模态 RAG（Multimodal RAG）是指 RAG 系统不仅处理文本，还能处理图像、音频、视频等多模态内容，做到“以图搜文”“以文搜图”“跨模态检索”。传统文本 RAG 只处理文本文档块，多模态 RAG 把图像、音频、视频也编码到向量空间里，与文本统一检索。

核心区别：

| 维度 | 传统文本 RAG | 多模态 RAG |
|------|-------------|-----------|
| 处理内容 | 仅文本 | 文本＋图像＋音频＋视频等 |
| 向量化 | 文本 Embedding | 多模态 Omni Embedding（一个模型编码多种模态到同一向量空间）|
| 检索方式 | 文本相似度 | 跨模态相似度（图文/音文/视文互查） |
| 典型模型 | BGE、sentence-transformers | Jina v5-omni、Ovis-Omni-Embedding、Omni-Embed-Nemotron |

大白话比喻：传统 RAG 给模型一本“只能看文字的书”；多模态 RAG 给模型一本“带图片、有录音、有视频的多媒体书”，模型能把图片里的内容和文字里的内容一起检索、一起理解。

> 面试要点：多模态 RAG 扩展了 RAG 的处理范围，从纯文本到图像/音频/视频，核心是用一个多模态 Embedding 模型把不同模态编码到同一向量空间，实现跨模态检索。

## Q20. 多模态 RAG 的优势和劣势分别是什么？

**回答**

**优势：**
- 打破模态壁垒，用一种方式查所有类型内容；

> 面试要点：多模态 RAG 优势是打破模态壁垒、丰富知识库、交互更自然；劣势是模型和存储开销大、跨模态对齐质量不一（视频尤甚）、数据处理复杂。生产落地需权衡收益与成本。

## Q21. 多模态 Embedding 的检索原理是什么？（以余弦相似度为例）

**回答**

多模态 Embedding 把不同模态的内容都编码成同一维度的向量，查询时用余弦相似度（或点积）衡量查询向量与各候选向量的距离，取 Top-K 最相近的。

检索公式（已 L2 归一化后，点积即余弦相似度）：

```
相似度 = cos(θ) = (Q · D) / (|Q| × |D|)
```

其中 Q 是查询向量（可以是文本、图像、音频或视频编码），D 是候选内容向量。因为所有内容都在同一向量空间，所以文本查询可以去匹配图像候选，图像查询可以去匹配文本候选，实现跨模态检索。

### Python 示例（概念版）

```python
import numpy as np

def cosine_similarity(q, d):
    return np.dot(q, d) / (np.linalg.norm(q) * np.linalg.norm(d))

# 假设已经用 Omni Embedding 模型编码好了
query_vec = np.array([0.23, -0.45, 0.87, ...])   # 用户用文字提问编码出的向量
image_vec = np.array([0.20, -0.40, 0.90, ...])    # 一张图片编码出的向量
text_vec  = np.array([0.50, -0.10, 0.20, ...])    # 一段文字编码出的向量

print("文字查询与图片的相似度：", round(cosine_similarity(query_vec, image_vec), 3))
print("文字查询与文字的相似度：", round(cosine_similarity(query_vec, text_vec), 3))
```

> 面试要点：多模态 Embedding 检索原理＝所有内容编码到同一向量空间，查询时用余弦相似度（或点积）衡量距离，取 Top-K。因为在同一空间，文本可查图片、图片可查文本，实现跨模态检索。

## Q22. Jina v5-omni 有什么特点？为什么说它“无需重建索引”？

**回答**

Jina v5-omni 是 Jina AI 发布的全模态嵌入模型，支持文本、图像、音频、视频。它的关键特点是：

> 面试要点：Jina v5-omni 特点＝全模态支持（文本/图像/音频/视频）、文本向量与 v5-text 逐字节一致、无需重建已有文本索引、小参数高性能。适合已有 v5-text 文本索引、想低成本扩展多模态检索的场景。

## Q23. Ovis-Omni-Embedding-3B 有什么特点？

**回答**

Ovis-Omni-Embedding-3B 是一个 3B 参数的全模态嵌入模型，基于 Qwen2.5-Omni-3B 初始化，支持文本、图像、视频、音频和交织多模态输入。

特点：
- 保留原生文本 tokenizer、视觉编码器、音频编码器和共享 Thinker 骨干，移除语音生成 Talker 和语言建模头；
- 把各模态输入格式化为交织的 token 序列，由共享因果 Transformer 处理；最后一层非填充 token 的隐藏状态直接作为检索向量，不附加模态专用投影头；
- 是 bi-encoder 而非 cross-encoder，查询和候选独立编码，推理时按余弦相似度排序，可扩展性强；
- 在 MMEB-v3 全模态检索基准（190 个数据集，涵盖图像、视频、视觉文档、文本、音频、代理检索）上总分 58.46，超过最强对比基线 5.19 分，各模态组平均分均排名第一。

> 面试要点：Ovis-Omni-Embedding-3B 特点＝基于 Qwen2.5-Omni、共享 Thinker 骨干编码多模态、bi-encoder 架构可扩展、MMEB-v3 基准表现优异（总分 58.46，各模态组均第一）。适合对多模态检索质量要求高的场景。

## Q24. 多模态 RAG 怎么选模型？选型参考

**回答**

| 场景 | 推荐模型 | 理由 |
|------|---------|------|
| 已有 v5-text 文本索引，低成本扩展多模态 | Jina v5-omni-small/nano | 文本向量与 v5-text 一致，无需重建文本索引，小参数高性能 |
| 多模态检索质量要求高，资源充足 | Ovis-Omni-Embedding-3B | MMEB-v3 各模态组第一，质量最强 |
| 极度受限的部署环境（边缘设备） | Omni-Embed-Mini（0.9B） | 体积极小，且不回退文本检索质量 |
| 需要跨模态和联合模态检索（如文本+音频→图像+视频） | Omni-Embed-Nemotron | NVIDIA 推出，支持任意模态组合查询 |

> 面试要点：多模态 RAG 选型按场景：已有文本索引低成本扩展选 Jina v5-omni；质量优先选 Ovis-Omni-Embedding-3B；边缘受限选 Omni-Embed-Mini；任意模态组合查询选 Omni-Embed-Nemotron。

## Q26. 多模态 RAG 与文本 RAG 的关系？是替代还是互补？

**回答**

多模态 RAG 不是替代文本 RAG，而是互补和扩展：

- 绝大多数企业知识仍以文本为主（文档、邮件、Wiki、代码），文本 RAG 足够且更轻量、更便宜；
- 当知识库里包含大量图像、音频、视频，或者用户需要“用图片提问”“用语音检索”时，多模态 RAG 才有必要；
- 实务中常见的做法是**双索引并存**：文本索引继续用 BGE 等文本 Embedding，多模态内容用 Omni Embedding 单独建索引，查询时根据查询模态选择或混合检索。

> 面试要点：多模态 RAG 与文本 RAG 是互补而非替代。文本知识为主时文本 RAG 足够；有多模态内容或跨模态检索需求时再引入多模态 RAG。实务上常做双索引并存，按查询模态选择或混合检索。

## Q27. 多模态 RAG 目前的主要短板是什么？

**回答**

多模态 RAG 虽然前景广阔，但还有明显短板：

1. **视频检索是短板**：多模态模型在视频检索上仍落后于端到端训练方案，时序推理更依赖端到端训练；
2. **模型体积和推理开销大**：全模态 Embedding 模型通常几十亿参数，部署成本高；
3. **多模态向量存储成本高**：图像/视频向量比文本向量大，存储和检索开销大；
4. **跨模态对齐质量参差不齐**：不同模态之间的语义对齐不如同模态内那么精确；
5. **多模态数据处理复杂**：清洗、分块、元数据管理比纯文本复杂得多。

> 面试要点：多模态 RAG 主要短板＝视频检索弱、模型体积大、多模态向量存储成本高、跨模态对齐参差不齐、多模态数据处理复杂。生产落地需权衡收益与成本，先从文本为主的场景起步。

## Q28. 多模态 RAG 怎么评估？有哪些基准？

**回答**

多模态 RAG 的评估可以参考文本 RAG 的评估体系（Faithfulness、Answer Relevancy、Context Recall 等），并增加多模态特有维度：

- **跨模态检索质量**：用文字查图像、用图像查文本，检索是否命中正确内容；
- **多模态基准**：MMEB-v3（190 个数据集，涵盖图像、视频、视觉文档、文本、音频、代理检索）、MMTEB（文本）、MIEB（图像）、MMEB-Video（视频）、MAEB（音频）；
- **端到端答案质量**：多模态答案是否准确、引用是否正确、是否有幻觉。

常用评估指标与文本 RAG 一致：Recall@K、MRR、NDCG、Faithfulness 等。

> 面试要点：多模态 RAG 评估＝沿用文本 RAG 指标（Recall@K/MRR/NDCG/Faithfulness 等）＋增加跨模态检索质量（以图查文、以文查图是否命中）。常用多模态基准：MMEB-v3、MMTEB、MIEB、MMEB-Video、MAEB。

## Q29. 多模态 RAG 生产落地的成本控制建议

**回答**

1. **双索引并存**：文本继续用轻量文本 Embedding（如 BGE-small），只把真正需要的多模态内容用 Omni Embedding 建索引，避免全量升级成本；
2. **模型选型按需**：不需要最高质量时选小参数模型（如 Jina v5-omni-nano 0.9B、Omni-Embed-Mini 0.9B）；
3. **查询路由**：纯文本查询走文本索引，只在检测到多模态需求时才调用多模态检索，减少昂贵模型调用；
4. **缓存**：多模态 Embedding 结果按内容哈希缓存，相同图片/音频不重复编码；
5. **分阶段落地**：先做文本 RAG 基线，再逐步引入多模态内容，按效果评估决定投入程度。

> 面试要点：多模态 RAG 成本控制＝双索引并存（文本轻量＋多模态按需）、选型按需（小参数模型）、查询路由（纯文本走文本索引）、Embedding 缓存（内容哈希）、分阶段落地（先文本后多模态）。

## Q30. 本章小结：高级 RAG 架构怎么选？

**回答**

高级 RAG 架构的核心是“按需选型，不要为技术而技术”：

1. **基础 RAG 先做扎实**：清洗、切分、混合检索（稠密＋稀疏＋RRF）、重排序、引用溯源、评测集，这是所有进阶架构的基础；
2. **GraphRAG 选型**：当语料互相关联、用户问全局性或多跳问题时引入，口诀“图谱定骨架、向量充血肉、LLM 做表达”；注意索引成本和查询延迟高，做混合路由和增量更新；
3. **多模态 RAG 选型**：当知识库包含图像/音频/视频或用户需要跨模态检索时引入，用 Omni Embedding 把不同模态编码到同一空间；注意视频检索是短板、模型和存储开销大，做双索引并存和查询路由；
4. **持续评估**：无论哪种架构，都要用 RAG Triad（Faithfulness/Context Relevance/Answer Relevancy）和检索侧指标（Recall@K/MRR/NDCG）持续评估，按数据优化。

一句话总结：**高级 RAG 没有银弹，文本 RAG 是基础，GraphRAG 解多跳与全局问题，多模态 RAG 解图文音视频跨模态问题，三者可组合，关键是看业务场景和成本预算，并用评估体系验证效果。**

> 面试要点：高级 RAG 架构选型＝基础 RAG 做扎实→GraphRAG 解多跳/全局（图谱定骨架、向量充血肉、LLM 做表达）→多模态 RAG 解图文音视频（Omni Embedding 同一空间）→三者可组合，按业务场景和成本预算选，用 RAG Triad 和检索侧指标持续评估验证。
